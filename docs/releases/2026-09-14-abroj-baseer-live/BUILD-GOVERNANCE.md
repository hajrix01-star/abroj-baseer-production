يستعمل هذا العقد مهارات **ألفا للبناء** لمرشح الواجهات والتشغيل، و**ألفا
للترحيل** لفصل قرار ترقية البيانات، ثم **ألفا للتسليم** لحكم الإطلاق المستقل.

## G0 — الهدف، النطاق، والقبول

### الهدف والرحلات الحرجة

1. يفتح زائر `https://abroj.sa` الموقع العربي/الإنجليزي بتصميم أبرج المعتمد.
2. يفتح مستخدم `https://baseer.abroj.sa` صفحة دخول بصير ذات الهوية نفسها، ثم
   يستعمل **مسار دخول Odoo الأصلي** بما فيه reset/MFA/passkey إن كان مثبتًا؛
   الواجهة لا تستبدل نظام المصادقة أو منطق الصلاحيات.
3. تعمل قاعدة بيانات بصير الحية وfilestoreها داخل مشروع Docker خاص بها وحده.
4. يمكن إيقاف المشروع أو استعادة نسخته من دون أثر على تطبيقات Hostinger الأخرى.

### داخل النطاق

- إنشاء مرشح مصدر موحد ومجمد من `candidate-v14` المحدد، ثم إدخال موديولي
  الواجهة المثبتين بالمقارنة.
- إصلاح dependency صريح فقط إذا أثبت فحص Odoo أن قالب `website.login_layout`
  يتطلب `website` مباشرة.
- اختبار الواجهتين في بيئة معزولة، توثيق artifact/hash، GitHub، ثم Hostinger
  وفق عقد Docker/Nginx مستقل.
- ترقية قاعدة rehearsal إلى قاعدة الإنتاج الجديدة **فقط** عقب إغلاق لجنة
  الترحيل، في backup+restore متسقين خارج Git.

### خارج النطاق

- تعديل `baseer_dev` أو قواعد QA أو أي مشروع/شبكة/volume لتطبيق آخر.
- وضع DB أو filestore أو `.env` أو ملفات مرفقة أو أدلة تشغيل حساسة في GitHub.
- إعادة تصميم `.theme_abroj_review` أو تغيير دورة المحاسبة/الرواتب/المخزون.
- افتراض DNS أو TLS أو صلاحيات Hostinger قبل فحصها حيًا.

### قبول المستخدم

- العزل عن التطبيقات الأخرى كامل: compose project وDB وvolumes وnetworks
  منفصلة، ولا PostgreSQL ولا Odoo مكشوفين علنًا.
- الموقعان يعملان عبر HTTPS الصحيح، ويعيد `www.abroj.sa` إلى `abroj.sa`.
- `baseer.abroj.sa` يفتح صفحة الدخول؛ لا يكون مدير قواعد البيانات متاحًا.
- توجد نسخة قبل الترقية، restore smoke، وخطة rollback محددة بالمشروع وحده.

**سؤال المسار المباشر:** إعادة استخدام Website/Odoo الحالي في عملية واحدة
مع موقعين هو الأقصر والأقل مخاطرة؛ العزل المقصود هو عن تطبيقات VPS الأخرى.
فصل أبرج كموقع مستقل عن Odoo يتطلب إعادة بناء غير مصرح بها، لذلك ليس ضمن هذا
الإصدار.

## G1 — السعة والاستمرارية

- افتراض تشغيلي مثبت من عقد Hostinger: 15 مستخدمًا متزامنًا، VPS 2 vCPU/8GB
  RAM، Odoo worker=2 وcron=1، واحتفاظ طويل للـERP.
- الرحلات الأعلى خطورة: login، إنشاء/دفع مستند Odoo، تقارير مالية، واستعادة
  DB+filestore كوحدة متسقة. لا ينفذ اختبار حمل على الإنتاج.
- يمنع النقل إن أصبح هامش القرص أقل من 10GB؛ تؤخذ نسخة قبل الترقية، وتنفذ
  restore smoke في قاعدة/volume منفصلين قبل تحويل DNS.

## G2 — حدود المعمارية والبيانات

```text
Internet
  -> Hostinger nginx (vhost مستقل + TLS)
     -> 127.0.0.1:18069 Odoo الخاص ببصير
        -> شبكة baseer-odoo-prod_frontend
        -> شبكة baseer-odoo-prod_database (internal)
           -> PostgreSQL baseer_prod + volume خاص
        -> filestore volume خاص
```

- `abroj.sa` و`baseer.abroj.sa` يخدمان من **نفس Odoo/DB الخاصين ببصير**؛ لا
  ينضمان إلى شبكات أو DB أو volumes تطبيقات Hostinger الأخرى.
- الحقيقة المحاسبية تبقى Odoo/PostgreSQL؛ لا يعدل addon الواجهة أي رقم أو
  حساب أو صلاحية. ترقية الداتا هي restore للنسخة المتسقة فقط، لا import من
  Git ولا merge إلى قاعدة أصلية أثناء النشر.
- Nginx هو حد المضيف المشترك الوحيد: vhost قابل للحذف لبصير فقط، يمرر Host و
  X-Forwarded-* وWebSocket، يحجب `/web/database/*`، ويعيد HTTP إلى HTTPS.
- `dbfilter=^baseer_prod$`, `list_db=False`, `proxy_mode=True`; PostgreSQL
  بلا port مضيف وOdoo على loopback فقط.

## G3 — الرصة والتبعيات وأوامر التحقق

- الرصة المسموح بها: Odoo 19 وصورته المثبتة، PostgreSQL 16، Docker Compose
  الحالي وNginx الموجود؛ لا مكتبة أو runtime أو قالب ثالث جديد.
- مصدر المرشح هو شجرة copy مستقلة ومجمدة؛ لا mount لمجلد التطوير ولا addon
  rehearsal ولا `.theme_abroj_review`.
- يلزم أن يعتمد `baseer_abroj_login` على `website` إن كان يرث قالب Website؛
  هذا تعديل manifest وحيد متوقع، يتحقق منه install في DB نظيفة.
- أدلة G3 المطلوبة: `docker compose config`، فحص اسم المشروع/الشبكات/volumes
  والمنافذ، Python/XML parse، Odoo install/upgrade للواجهتين في DB معزولة،
  hash artifact، ثم commit Git نظيف بلا أسرار.

## WS-1 — استعادة قناة WebSocket في الإنتاج

### G0 — العقد والنطاق

- **المشكلة المثبتة:** سجّل Odoo الحي أخطاء `Couldn't bind the websocket`
  لأن Nginx يمرر `/websocket` إلى منفذ HTTP `8069` بدلاً من منفذ gevent
  `8072` عند تشغيل workers متعددة.
- **التغيير المصرح به:** إضافة ربط Docker محلي فقط
  `127.0.0.1:18072 -> 8072` لخدمة Odoo، وupstream Nginx محلي مستقل لهذا
  المنفذ، وتوجيه `/websocket` إليه. لا تغيير على قاعدة البيانات أو
  filestore أو الإضافات أو الصلاحيات أو نطاقات HTTPS.
- **القبول:** يعمل الدخول والواجهات الحالية كما هي؛ ينجح WebSocket عبر
  `baseer.abroj.sa`؛ لا يظهر خطأ bind جديد بعد الاختبار؛ لا يصل المنفذ
  `18072` من عنوان عام؛ وتبقى PostgreSQL بلا منفذ وOdoo/WebSocket على
  loopback فقط.
- **التراجع:** إعادة compose وvhost السابقين فقط ثم `docker compose up -d`
  وreload آمن لـNginx؛ لا توجد ترحيلات أو كتابة بيانات، لذلك لا يوجد تراجع
  لقاعدة البيانات.

### G1 — السعة والاستمرارية

- الحمل الحالي لا يثبت عنق موارد: Odoo `0.05%` CPU و`877.8MiB`، PostgreSQL
  `0.00%` و`276.2MiB`، والذاكرة المتاحة `3.6GiB` وقت القياس. صفحة الدخول
  الدافئة كانت نحو `0.41s` وجهات الاتصال نحو `0.48s`.
- الرحلة الحرجة هي إنشاء جلسة حية بعد الدخول. لا يغير WS-1 عدد العمال أو
  قاعدة البيانات؛ يضيف قناة محلية موجودة أصلاً داخل Odoo. لا يُنفذ اختبار
  حمل على الإنتاج.

### G2 — الحدود والعقد

```text
Internet -> Nginx/TLS -> 127.0.0.1:18069 -> Odoo HTTP 8069
                     -> 127.0.0.1:18072 -> Odoo gevent 8072
Odoo -> baseer-odoo-prod-backend (internal) -> PostgreSQL
```

- Nginx هو المستهلك الوحيد لمنفذ gevent، وDocker لا ينشره إلى أي عنوان
  عام. لا تنضم خدمة جديدة إلى أي شبكة أو volume، وتبقى الحقيقة المحاسبية
  وبيانات Noorix دون لمس.

### G3 — المسار المباشر والتحقق

- لا dependency أو runtime جديد: يستخدم التكوين القياسي الموثق لـOdoo 19
  (upstream HTTP منفصل عن upstream websocket). البدائل المرفوضة: تعطيل
  workers أو توجيه websocket إلى HTTP، لأنهما يخفيان سبب الربط ولا يحلان
  القناة الحية.
- قبل النشر: `docker compose config` وفحص diff للمنافذ والشبكات. بعده:
  `nginx -t`، تحقق 101/سجل WebSocket، فحص المنفذ من عنوان عام، smoke HTTPS
  للموقع والدخول، ثم فحص logs والحاويات.
