# BCH-PUSH-CHAT-SOUND-20261016 — BChat: رسائل وتنبيهات موثوقة

**النطاق:** مرشح QA فقط، من فرع `codex/bchat-push-v56` المنطلق من `official/main` عند `11a9752a`. لا نشر Live ولا تعديل يدوي على QA بهذا العقد.

## عقد البناء

- **الهدف:** إكمال تنبيهات BChat الفعلية: المهام والرسائل الخاصة والقروبات، بصوت افتراضي بعد ترقية التطبيق، وفتح الوجهة الصحيحة بعد تحقق الخادم. كما يعالج هذا المرشح التقطيع عند إرسال رسالة، قفز صفحة التنبيهات/القوائم أثناء التحميل، عدم تطابق تبويبات المهام مع تبويبات الطلبات، وتعليق الدخول عند انقطاع الشبكة بعد وجود نسخة محفوظة.
- **المستخدم:** موظف داخلي سبق تسجيله في BChat وله إذن محادثات أو مهام في شركة واحدة أو أكثر.
- **قرار خصوصية صريح من المالك (2026-10-16):** يظهر اسم مرسل الرسالة ومعاينة نصها القصيرة في إشعار Android مثل واتساب. لذلك تنتقل المعاينة المختصرة عبر Firebase إلى جهاز المستلم؛ لا تسجل في سجلات BChat أو event rows. يتحقق الخادم من العضوية عند إنشاء/إرسال الحدث وعند الفتح، لكن لا يمكن سحب معاينة وصل إرسالها مسبقًا إذا سُحبت العضوية لاحقًا. إعدادات شاشة القفل في Android تبقى السلطة النهائية لإخفائها.
- **المسموح:** معاينة نصية منظّفة ومحدودة إلى 160 محرفًا، واسم مرسل محدود إلى 120 محرفًا؛ للمرفقات بلا نص تظهر صياغة عامة محلية في Android. لا توجد معاينة لمهام أو طلبات.
- **خارج النطاق:** تجاوز حجب Android لتنبيه التطبيق بعد `Force stop`، رسائل دون اتصال، مزامنة كتابة جديدة، تغيير محاسبة/طلبات، تغيير إعدادات كتم غرفة لم توجد له سياسة خادم موثقة، أو نشر Live.

| الرحلة | القبول |

| فتح الإشعار | لا يفتح إلا بعد طلب event موثق وإعادة تحقق الشركة والعضوية و`chat_view`؛ عضوية مسحوبة أو حدث مزور لا يكشف الرسالة. |

## G1 — السعة والاستمرارية — قيد المراجعة المستقلة

- أساس QA المعروف: حتى 35 مستخدمًا و10 متزامنين، وحد أقصى 5 أجهزة نشطة لكل مستخدم. أكبر رسالة قروب ضمن هذه الفرضية تنتج بحد أقصى `34 × 5 = 170` event (المؤلف مستثنى).
- المسار الحرج: `message create → durable per-device event → cron كل دقيقة → FCM → Android`. يبقى cron محدودًا بـ100 event/دورة: لفرضية 170 event، هدف dispatch هو دورتان كحد أقصى (≤ دقيقتين قبل إعادة المحاولة)، لا وعد لحظي ولا ادعاء دعم مجموعة غير محدودة.
- نمو البيانات: event واحد لكل جهاز/رسالة، من دون نسخ نص الرسالة في قاعدة البيانات. لا تغير هذه الشريحة احتفاظ الأحداث القائم؛ يجب أن يبقى الفهرس على `(state, next_attempt_at, id)` لمسار dispatcher.
- التزامن: يربط event فريدًا بالرسالة والجهاز؛ إعادة إرسال HTTP ذات `client_uuid` قائمة لا تنشئ رسالة أو تنبيهًا ثانيًا. يختار dispatcher صفوفه بقفل PostgreSQL `FOR UPDATE SKIP LOCKED` ضمن transaction حتى لا يرسل عاملان الحدث نفسه، وتثبت ذلك حالة اختبار مستقلة بقفل منافس وحد 170 event.
- الاستعادة: تعطل FCM لا يعيد كتابة رسالة ولا يلغيها؛ يسجل state/retry القائم. لا اختبار حمل على QA المشتركة؛ الاختبارات المعزولة تثبت الحدود ومنع التكرار فقط.

## G2 — المعمارية والبيانات — قيد المراجعة المستقلة

1. يوسّع `baseer.bchat.push.event` المصدر الواحد للـ wake-ups: حدث المهمة يملك `task_id`، وحدث الرسالة يملك `message_id`؛ يفرض check أن واحدًا فقط موجود. يجعل `task_id` و`task_revision` nullable عبر upgrade صريح، ويضيف `event_kind='message'` لمسار الرسالة. يفرض check أن المهمة وحدها تحمل revision و`assigned|updated`، وأن الرسالة وحدها تحمل `message` وrevision فارغًا. ينشأ كل event بجهاز غير فارغ (مع بقاء `ondelete=set null` للأحداث التاريخية عند حذف التسجيل)، ويحافظ على uniqueness المهمة القائم ويضيف unique partial index للرسالة `(message_id, device_id) WHERE message_id IS NOT NULL`.
2. بعد نجاح إنشاء رسالة وإيصالاتها داخل نفس savepoint، يحدد `baseer.bchat.push.event` الأعضاء النشطين المؤهلين (`company`, `chat_view`, عضوية الغرفة) ويستثني المؤلف، ثم ينشئ events للأجهزة النشطة فقط.
3. قبل الإرسال وقبل الفتح، يعيد الخادم التحقق من الجهاز والمستخدم والشركة والإذن والعضوية. رسالة صارت غير متاحة تصبح `discarded` ولا تفتحها النقرة.
4. تصنع FCM payload من الرسالة غير القابلة للتعديل وقت dispatch فقط: `account_key`, `kind`, `event_id`, اسم المرسل، ومعاينة نصية منظّفة ومحدودة. لا تستخدم notification payload ولا تسجل النص أو token. لقبول قرار المالك، تنقل البيانات النصية إلى Firebase، وهو أثر خصوصية معلن هنا.
5. `notifications/<id>` يبقى مصدر الحقيقة للوجهة: رسالة تعيد `destination=chat`, `room_id`, `message_id`؛ ومهمة تعيد عقدها القائم. Android لا يثق في extras أو معاينة push لفتح المحتوى.
6. Android ينشئ channel `bchat-events-v3` منفصلة مع `IMPORTANCE_HIGH`، الصوت الافتراضي، vibration، و`VISIBILITY_PRIVATE`. تغيير المعرّف لازم لأن Android لا يحدّث إعدادات قناة منشأة سابقًا. يتحقق العميل من طول/محارف المعاينة ولا يستخدمها للملاحة.
7. لا أرقام تجارية أو قيود أو مخزون في هذا التغيير. مصدر الحقيقة للصلاحيات والعضوية والرسالة هو Odoo، لا العميل أو Firebase.

## G3 — الطريق المباشر والتبعيات — قيد المراجعة المستقلة

- يعاد استخدام Odoo ORM، جدول events وcron وFirebase HTTP v1 وFirebase Messaging الموجودة. لا مكتبة جديدة ولا تعديل اعتماد.
- البديل المرفوض: أن يجلب service Android النص من API قبل الإشعار؛ لا يحمل service جلسة Odoo الموثقة، ويضيف دخولًا خفيًا وتأخرًا. المسار المباشر هو payload صغير اختاره المالك صراحة، ثم تحقق موثق عند الفتح.
- أوامر التحقق المقصودة: اختبارات Odoo المركزة لـ push/message، compile/lint Android، وفحص APK الموقّع. لا يوصف اختبار جهاز أو QA بأنه ناجح قبل تنفيذه.

## G4 — تجربة الاستخدام — قيد المراجعة المستقلة

- المعاينة: عنوانها اسم المرسل، سطرها نص الرسالة حتى 160 محرفًا، وقناة Android تسميتها محلية `BChat` من دون نص ثابت غير مترجم. المرفق بلا نص يستخدم مورد Android عربي/إنجليزي.
- الشاشة الصغيرة وسطح المكتب: التعديل محصور في Android؛ تبويبات المهام تعيد استخدام primitive التبويبات القائم للطلبات بدل بناء تصميم ثانٍ.
- حالات التحميل تحجز مساحة notice/list ولا تستبدل الشاشة أو تغير موضع scroll الموجود.
