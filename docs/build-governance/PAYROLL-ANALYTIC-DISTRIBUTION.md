# PAD-1 — التحليل الافتراضي للرواتب

## عقد البناء — G0–G3 (مُعتمد للتنفيذ على QA)

### الهدف

لكل شركة سعودية جديدة تُحمّل شجرتها المحاسبية، تُجهّز بنية تحليلية أصلية في
Odoo لتكلفة الرواتب. يختار مسؤول الشركة من إعدادات الحسابات السعودية تفعيل
التوزيع الافتراضي؛ وعند اعتماد مسير رواتب جديد تُوزّع **سطور مصروف الرواتب
فقط** بنسبة 100% إلى الحساب التحليلي المعتمد.

### المستخدمون والرحلة

1. مدير ERP يفتح نافذة تهيئة الشركة أو إعدادات الرواتب في الشركة.
2. النظام يعرض جاهزية التحليل ولا ينشئ فاتورة أو دفعة أو قيداً.
3. الشركة الجديدة: البذرة تجهّز خطة/حساب التحليل الافتراضي مع الشجرة السعودية.
4. الشركة القائمة: المدير يختار «تجهيز تحليل الرواتب»؛ ينشئ النظام الناقص فقط.
5. اعتماد مسير راتب مستقبلي: الخادم يضع التوزيع على سطر المصروف، ثم يتحقق من
   أن القيد متوازن وأن ذمة الراتب لا تحمل توزيعاً تحليلياً.

### داخل النطاق

- `baseer_payroll`: إعداد الشركة، فرض التوزيع عند إنشاء القيد، واختبارات
  الرواتب والتحليل.
- `baseer_company_setup`: عرض/تطبيق الجاهزية في نافذة تهيئة الشركة والبذرة
  للشركة السعودية الجديدة.
- التحليل الأصلي `account.analytic.plan` و`account.analytic.account` فقط؛ لا
  دفتر تحليلي موازٍ ولا تقرير مخصص.

### خارج النطاق

- تعديل قيود أو مسيرات أو مدفوعات أو فواتير تاريخية.
- تحويل الراتب إلى فاتورة مورد.
- توزيع يدوي شهري أو تغيير سياسة الأوفر تايم/السلف/الإجازات.
- تغيير قاعدة التقييم أو الضريبة أو شجرة الحسابات السعودية.

### مصدر الحقيقة والضوابط المالية

- `hr.payslip` ومسير الرواتب يظلان مصدر حساب الراتب؛ `account.move` الأصلي
  هو مصدر القيد والترحيل؛ `account.move.line.analytic_distribution` هو مصدر
  التحليل.
- لا يكتب العميل أي مبلغ أو نسبة. الخادم يثبت `{analytic_account_id: 100}`
  فقط على سطر مصروف الرواتب، بعد تحقق الشركة والحساب ونشاطه.
- لا يحمل سطر ذمة الموظف ولا سطر السلف/الخصم توزيعاً تحليلياً افتراضياً.
- المسير المعتمد غير قابل للتعديل؛ تغير الإعداد يؤثر المسيرات التي لم تعتمد
  بعد فقط.

### معايير القبول

1. شركة سعودية جديدة تملك بنية تحليل رواتب جاهزة بعد تحميل الشجرة، بلا أي قيد.
2. الشركة القائمة تجهز الناقص من نافذة الشركة فقط، من دون تغيير أي قيد سابق.
3. عند إيقاف التفعيل لا يحمل المسير الجديد توزيعاً افتراضياً.
4. عند التفعيل يظهر 100% من مصروف الراتب في التقرير التحليلي الأصلي، ولا يظهر
   توزيع على ذمة الموظف.
5. رفض خادمي للحساب المؤرشف أو التابع لشركة أخرى أو توزيع غير مكتمل.
6. إعادة المحاولة أو فتح النافذة مرة أخرى لا تنشئ خطة أو حساباً مكرراً.
7. عزل الشركات، توازن القيد، السداد الجزئي، وتأجيل السلفة تبقى كما هي.

### قرار المسار المباشر

نعيد استخدام `account.analytic.plan` و`account.analytic.account` و
`analytic_distribution` الأصلية، مع امتداد ضيق لمسار رواتب بصير. لا نضيف
مكتبة أو نموذج توزيع موازياً؛ البذرة تجهز المتطلبات والإعداد يقرر تطبيقها.

### تصميم التنفيذ المقفل

- خطة أصلية مشتركة ثابتة الهوية: `baseer_payroll.payroll_cost_plan`.
- حساب تحليلي فعّال واحد خاص بكل شركة سعودية جذرية، وتحكمه حقلا الشركة
  `baseer_payroll_analytic_enabled` و`baseer_payroll_analytic_account_id`.
- البذرة تجهز الحساب للشركات السعودية الجديدة. نافذة التهيئة للشركات القائمة
  تعرض الحالة وتضيف الناقص فقط عند تطبيق المدير.
- اعتماد المسير يقرأ الإعداد لحظته؛ لا يحدّث مسيراً أو قيداً سابقاً.
- لا يقبل النظام حساباً مؤرشفاً أو تابعاً لشركة أخرى أو خارج خطة الرواتب.

### بوابة التحقق قبل النشر

1. اختبارات الوحدة للبذرة، حالة الشركة القائمة، وعزل الشركات.
2. مسير راتب جديد: 100% على المصروف فقط، وصفر على الذمة والسلفة والخصم.
3. مسير مع سلفة مؤجلة/غير مؤجلة وسداد جزئي: التوازن والذمم لا تتغير.
4. مراجعة XML وترقية الموديولين على QA، ثم اختبار مرئي للإعداد قبل أي نشر حي.
