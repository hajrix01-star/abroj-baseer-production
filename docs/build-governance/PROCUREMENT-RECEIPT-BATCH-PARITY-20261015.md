# PROCUREMENT-RECEIPT-BATCH-PARITY — عقد بناء QA

**التاريخ:** 2026-10-15
**الحالة:** G0–G4 معتمدة قبل التعديل
**النطاق:** QA فقط، لا نشر حي ولا تغيير بيانات تشغيلية.

## G0 — الهدف والحدود

### هدف المستخدم

عند اختيار طلب شراء مكتمل الاستلام في «دفعات إدخال المشتريات»، يرى المحاسب قبل الاعتماد:

1. إجمالي الاستلام الفعلي للطلب.
2. إجمالي فواتير الموردين التي أدخلها في الدفعة.
3. الفرق المتبقي أو الزائد وحالة المطابقة.

كما يجب أن يملك دور **Accountant / المحاسب** دخول «دفعات إدخال المشتريات» وإنشاء الفواتير فيها، من دون منحه إنشاء أو استلام طلبات المشتريات التشغيلية.

### مصدر الحقيقة ودورة ERP

`طلب مواد خام → استلام المدير → تأكيد الكاشير للكميات/الأسعار الفعلية → طلب بحالة purchased → دفعة إدخال فواتير الموردين → اعتماد الدفعة → فواتير الموردين ودفعاتها الأصلية في Odoo`.

مصدر مبلغ الاستلام هو `baseer.procurement.request.actual_total`. مصدر إجمالي الفواتير هو `baseer.purchase.batch.amount_gross`. لا يتغير أي منهما من المتصفح؛ الموافقة الخلفية تبقى الحاجز النهائي الذي يرفض أي فرق.

### حدود صريحة

- لا تغيير للكمية أو السعر أو ضريبة أو قيد أو دفعة أو تسوية قائمة.
- لا تغيير لسير حالات الطلب أو قواعد عزل الشركات.
- لا تغيير لمسار العهدة؛ بطاقته الخاصة تبقى ظاهرة عند اختيار العهدة فقط.
- لا صلاحية طلب أو استلام لكاشير/مدير من خلال دور المحاسب.
- لا إنشاء مجموعة أمنية جديدة إن كان الدور المحاسبي الحالي يحقق أقل صلاحية مطلوبة؛ يثبت الاختبار ذلك.

### معايير القبول

- تظهر بطاقات الإجمالي الثلاث لكل دفعة مرتبطة بطلب مستلم، سواء كانت طريقة الدفع نقدية أو بنكية أو آجلًا أو عهدة.
- الفرق موجب عندما ينقص الإدخال، وسالب عندما يتجاوز، وصفر عند المطابقة؛ الحساب من الخادم وبعملة الشركة.
- زر الاعتماد ينجح فقط عند تطابق `amount_gross` و`actual_total`، ويترك الدفعة مسودة عند عدم التطابق.
- لا تظهر بطاقة المطابقة في دفعة عادية بلا طلب مستلم.
- دور المحاسب يستطيع قراءة/إنشاء/تعديل دفعة وفواتيرها ضمن شركته ويصل لقائمة الدفعات، ولا يكتسب صلاحيات طلب/استلام تشغيلي.

## G1 — السعة والاستمرارية

لا جدول ولا فهرس ولا استعلام جديد: الفرق حقل محسوب غير مخزن يعتمد على قيمتين موجودتين في رأس الدفعة. الحد العملي الحالي للدفعة 50 فاتورة، ويفترض حتى 10 محاسبين متزامنين لكل شركة. قفل الطلب والدفعة والتحقق الحالي عند الاعتماد يبقون مصدر منع التكرار والتعارض؛ لا يلزم اختبار حمل جديد لأن القراءة لا تضيف استعلام صفوف أو RPC.

## G2 — الأرقام والصلاحيات

- المقارنة النقدية تستخدم عملة الشركة (`compare_amounts`)؛ لا مقارنة عائمة في الواجهة.
- طلب واحد يرتبط بدفعة واحدة فقط بالقيد الفريد الحالي.
- صلاحية المحاسب تعتمد على `account.group_account_invoice` التي تمنح ACL لدفعة الإدخال، ويضمها preset `baseer_access_roles.group_accountant`.
- عزل الشركة الحالي في الدفعة والطلب لا يتغير.

## G3 — التقنية والتبعيات

تغيير محدود في `baseer_procurement_requests`: حقل محسوب غير مخزن، وراثة XML للواجهة، واختبارات Odoo. لا مكتبة أو خدمة أو migration أو dependency جديدة.

## G4 — العرض والجوال

بطاقات مختصرة ثابتة القراءة فوق صفوف الفواتير، مع لون هادئ للمطابقة وتحذير واضح للفرق، وتلتف كصفوف على الجوال. لا رسوم متحركة أو تغيير مخطط الإدخال.
