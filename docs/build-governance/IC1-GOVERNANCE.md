# IC1 — Unified financial correction

## G0 contract / draft for independent approval
User authorizes professional implementation of the researched correction flow across modules with existing roles. Reuse FL2 architecture, deployment baseline e84fcfb96800fe8a655a3e40fb6db3d215085238. Code implementation/QA authorized; do not modify live business transactions as tests. Preserve original data on release. Central entry means source-aware dispatch, not editing every derived journal entry.

Scope: a shared «Correct operation / تصحيح العملية» action on native invoice/payment forms and financial-register rows; approved purchase-batch row entry. Generic manual customer/vendor invoices and manual cash/bank payments use one confirmation wizard. Existing POS summary, payroll/payslip/advance correction workflows are routed to their owning source and keep that source's permissions. Expenses, sale/purchase linked invoices and other derived records retain native owner workflow where generic reset would change stock/approval/invoicing status unexpectedly. Show precise unsupported-state reason instead of silently editing a derived ledger entry. Native manual miscellaneous journal entries retain native edit/reversal workflow, not a cash-amount-only wizard.

Roles: owner/accountant (plus explicitly authorized native accounting manager for compatibility); cashier/read-only/other users cannot execute generic corrections, including direct RPC. Source-specific role restrictions remain authoritative; do not expand payroll visibility, POS correction manager rights or employee data access merely via central action. Audit stores only permitted source data and is not exposed in a cross-module salary history.

Critical examples: recorded400/600 with actual bill500; invoice-only or explicitly selected payment correction; cash↔bank; wrong supplier. Correct bill and actual payment are separate inputs. No automatic refunds or fictitious incoming cash. Batch current values and accounting links must agree with corrected documents, with original values retained in audit. Unrelated batch rows, reconciliations and documents unchanged.

## G2 data/accounting contract / draft
Map: native buttons/register/batch row → common permission+source dispatcher → either owning module's existing action or transient correction wizard → native invoice/payment draft/edit/post/reconcile → batch-specific current-state update + immutable audit → native cash report/ledger. No core edit. A small addon owns the dispatcher/wizard/audit; native account models own tax, currency, balance and journal posting. Decimal validation on raw strings (max2decimalplaces) at input; Odoo Monetary floats remain native boundary only. Invoice line quantity/price/tax uses native tax engine; never write amount_total or add a difference line. Existing batch single gross amount uses its native gross/tax helper.

Wizard source and baseline are created/validated on server and immutable to RPC writes; line IDs must belong to selected source. Confirm rechecks source/roles/company/status, locks affected batch/wizard/moves/payments in stable order, detects stale invoice/payment/reconciliation/source changes, validates input before effects, unlinks only owned simple reconciliation if needed, invokes native actions and reconciles existing payment to corrected invoice. Explicit option to change payment; preserving it is default. All effects+audit are one transaction. Completed wizard repeat does not execute twice. Audit server-created only and source-authorized, with before/after, actor,time,reason; no broad sudo or client context bypass.

Generic eligibility excludes locked/hash/EDI/future periods, statement-matched or electronically processed payments, multi-invoice/shared settlement, credits/write-offs/FX/cash-basis complexity and unsupported operational links. Existing native checks must also execute, never be bypassed. No financial test writes on MAIN. Expected cash totals after correction500 equal actual500; no artificial receipts from technical reversal. Source-owned existing corrections keep their accepted semantics.
