# الميزة التالية — الإدخال الجماعي السريع للمشتريات

حفظ لاتفاق المستخدم فقط، لا كود ولا تثبيت لهذه الميزة ضمن Reports R1.

- طريقتان متاحتان: فاتورة أودو العادية ذات الأصناف والكميات، وإدخال سريع جماعي. الطريقتان تنتجان فواتير موردين أصلية، ولا تُدخل الفاتورة نفسها مرتين.
- واجهة داخل أودو، باستخدام جدول أودو القابل للتحرير، دون Excel أو تطبيق منفصل.
- الشركة وتاريخ الإدخال موحدان للدفعة. كل سطر فاتورة مستقلة ذات مورد من النظام ورقم المورد وتاريخ فاتورة مستقل.
- السطر: مشتريات/مصروفات، فئة، إجمالي شامل الضريبة، اختيار الضريبة، مدفوع بالكامل/آجل، ومصدر الدفع من اليوميات/الحسابات المهيأة للشركة.
- تاريخ دفع السطر المدفوع يساوي تاريخ الفاتورة؛ لا حقل تاريخ دفع إضافي. السطر الآجل لا ينشئ دفعة الآن.
- زر «حفظ واعتماد» ينشئ فواتير أصلية ويرحّلها، ويسجل الدفعات والمطابقة للمدفوع. الآجل يبقى ديناً على الشركة. تحقق قبل التنفيذ، منع التكرار، وتراجع الدفعة كاملة عند فشل أحد الأسطر.
- لا يكفي إنشاء account.payment لادعاء «مدفوعة»؛ يجب اختبار إعداد يوميات الدفع/الحسابات المعلقة والتسوية وحالة الفاتورة الفعلية في Odoo.
- كل سطر ملخص يناسب فئة ومعالجة ضريبية واحدة. الفاتورة متعددة الفئات/الضرائب أو الأصناف المخزنية تُدخل بالطريقة العادية أو تُفصّل. الإجمالي المختصر لا يسجل استلام وكميات مخزون.
- ربط الفئات بحساب/منتج مضبوط لضمان وصولها إلى التقرير النقدي الحالي. هذا قرار ربط يجب إتمامه عند التصميم؛ لا تنشأ محاسبة بديلة.
- ملخص دفعة قابل للطباعة وروابط للفواتير الأصلية. المثال الذي ظهر في المحادثة توضيحي، وليس بيانات مورّدين/حسابات حقيقية أو موافقة على ترحيل معاملات.
- يبدأ التنفيذ لاحقاً في QA، مع بوابات التصميم والاختبارات المناسبة للأثر المالي. لا تُضاف لوحات eh_board أو eh_account_dashboard تلقائياً؛ تمت مناقشتهما فقط.
