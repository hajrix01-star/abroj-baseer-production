# Daily purchase report — architectural impact

- Status: local candidate, not deployed. Baseline `fee40097e441626b66290fe9ab192194ab0d3b04`; classification ARCHITECTURAL.
- `baseer_purchase_daily_report` provides a Baseer-designed OWL action and bounded read-only service. `baseer_basser_workspace` provides role-specific navigation; owner has a dedicated workspace menu. No native accounting model or financial transaction is modified.
- Source of truth: posted `account.move` supplier invoices and credit notes, grouped by invoice date. A purchase batch creates a native invoice and is never separately counted. Aggregates use signed company currency; document detail identifies original currency. Current reconciliation and payment state are not historical payment-date cash flow. Settlement can include noncash reconciliation.
- Scope boundary: owner, accountant and branch manager (`group_cashier`) are allowed; POS cashier is distinct. Each endpoint verifies the acting user and active company before privileged reads, applies the exact company/type/posting domain, and returns a field-limited projection. Details are read-only. Queries are bounded to 366 days and day results to 50 records per page.
- Test evidence and limitations: [build contract](../../build-governance/PURCHASE-DAILY-REPORT.md). No load claim, production install, release approval, or live data modification.
- Custody payment method (2026-11-27, `19.0.1.1.3`, not deployed): a bill counts as paid from representative custody only when its settling counterpart is posted in a journal with `account.journal.baseer_custody_representative_id`, or uses the company's configured representative custody account. Journal or partner names, references, and bank account numbers (for example "أسامة" or "1994") are no longer used. Totals are unchanged. Only the method split changes, for look-alike references that were misclassified before.
- Custody cards and payment-method columns (2026-11-27, `19.0.1.1.4`, not deployed): three cards «دخل للعهدة», «صُرف منها», «المتبقي» read representative custody only through `baseer_procurement_requests` (single source). The period starts on 2026-11-01 and follows the report's date range and active company. In = posted funding − returns − funding reversals (plus historical PCUST transfers), via `_baseer_grouped_amount` and `_legacy_custody_totals`. Out = native custody-journal payments (`_native_custody_spend`) plus custody settlements. Remaining = the sum of `_baseer_representative_available_amount()` per representative (the current balance), and the card opens `baseer_procurement_requests.action_representative_petty_cash` for users with procurement custody access. The main daily purchases table (one row per invoice day, expandable to its bills) has one column per payment method; each bill's company-currency total is split by its reconciled allocations (custody detected exactly as above), and the open residual is shown as «لم تُسدَّد», so the method columns add up to the purchase total. «تحويل للعهدة» appears only on transfer rows and is excluded from purchase totals. On the default filters, the transfer column total equals «دخل للعهدة» and the custody column equals «صُرف منها» when bill dates match payment dates. No data is written.
