# BChat — اعتماد واجهة الطلبات 2026-10-14

## عقد البناء G0

- المصدر: الفرع `codex/bchat-orders-ui-20261014` من `92220f4e`، وصورة المقترح التي اعتمدها المالك في هذه المحادثة. النطاق Android لقسم الطلبات فقط: «المنيو / طلباتي / الاستلام»، البحث والمرشح، صف الصنف، شريط السلة، وحالات التحميل.
- المستخدم: موظف مطعم مخوّل في أودو. الهدف: تبويبات واضحة ثابتة لا تقفز أو تختفي عند التحميل، ومحتوى لا يومض فارغًا عند تحديث الصفحة نفسها، وشكل متسق عربي/إنجليزي عند عرض ضيق.
- القبول: (1) تبقى التبويبات والهيدر ثابتة عند الانتقال والتحميل السريع/البطيء؛ (2) لا يظهر مؤشر التحميل إذا اكتمل الطلب سريعًا؛ (3) تحديث الصفحة نفسها يحتفظ بمحتواها حتى الرد، أما تبديل الشركة أو نوع الصفحة فيعرض حالة انتقال محايدة لا بيانات السياق السابق؛ (4) تظهر حالات الفراغ/الفشل/عدم الصلاحية؛ (5) لا يتغير إرسال الطلب أو استلامه أو أرقامه أو صلاحياته؛ (6) يبقى APK الهاتف والمحاكي من بناء واحد.
- خارج النطاق: تغيير Odoo أو عقود `/bchat/api/v2/orders` أو أسعار/كميات أو مخزون أو مستخدمين أو QA/Live. صورة التصميم توضيحية؛ الأصناف والأسعار فيها ليست بيانات تشغيلية.
- دورة ERP القائمة: أودو يملك الشركات والصلاحيات والكتالوج وعرض السعر المعتمد وإنشاء الطلب واستلامه النهائي. Android يرسل المدخلات الخام ويعرض الرد؛ لا يحسب الإجمالي أو يقرّر الحالة. لا يتغير مسار التدقيق أو المخزون.
- خريطة الأثر `CONTROLLED`: `Odoo orders API → OdooIdentityActivity order modes/renderers → Ui.styleSegment وموارد اللغات → APK`. بقية BChat (المحادثة، الوسائط، المهام) غير متأثرة. المرجع المعماري: `docs/architecture/registry/INDEX.md`.

## ملف G1 — السعة والاستمرارية

- الحمل الفعلي للمالك غير مقاس في هذا الطلب؛ لا شهادة زمن استجابة جديدة. الحدود الحالية التي تبقى كما هي: صفحة كتالوج حتى 24 خيارًا، صفحة الطلبات حتى 50، وصفحة الاستلام حتى 30، مع حدود الاحتفاظ المعروضة في العميل. لا استعلام أو cache أو عملية خلفية جديدة.
- خطر الواجهة: تكرار إعادة البناء على الضغط والرد يسبب قفزًا بصريًا. الحل المقترح يغيّر موضع/توقيت مؤشر التحميل فقط ويبقي حراسة `orderViewSerial` و`companyId` و`account` للردود المتأخرة.
- لا اختبار حمل جديد لأن الفرق لا يغير الخادم أو حجم البيانات أو التزامن؛ الفحص المناسب بناء Android واختبارات عقود المصدر وتجربة عرض 320dp إن توفر جهاز.

## عقد G2 — الملكية والعقود

- لا schema أو endpoint أو صلاحية جديدة. تظل عروض السعر وإجمالي السلة من `POST /bchat/api/v2/orders/quote`؛ لا تُجمع أسعار الصورة التوضيحية في Android.
- حالة التحميل تخص وضعًا واحدًا (`catalog` أو `mine` أو `receiving`) ورقم جيل الطلب. عند تحديث الوضع نفسه يمكن إبقاء البيانات المرئية مع مؤشر صغير داخل المحتوى. عند تبديل الوضع أو الشركة تُحجب بيانات الوضع السابق وتُعرض حالة انتقال ثابتة؛ الرد القديم لا يُطبّق بعد تغير الجيل/الحساب/الشركة.
- يشترط للاحتفاظ بالقائمة تطابق الشركة والوضع وعبارة البحث والفئة ومؤشر الصفحة أيضًا؛ اختلاف أي مفتاح يعرض انتقالًا محايدًا حتى يصل الرد الصحيح.
- فشل التحميل يبقي رسالة واضحة وإعادة محاولة، ولا يحوّل بيانات الشركة الأخرى إلى بديل. منع إنشاء الطلب المكرر/تأكيد الاستلام يبقى في مساراته القائمة؛ لا تمس الشريحة عملاً ماليًا.

## قرار G3 — التقنية والمسار المباشر

- الرصة الحالية Android Java + `Ui` وموارد `strings.xml` وGradle القائمة؛ لا مكتبة جديدة ولا تعديل للخادم. `Ui.styleSegment` مستخدم فقط في تبويبات الطلبات، فيمكن تطويره مركزيًا بدل نسخ ثلاثة أزرار محلية. لا حاجة إلى `$pick-ui-library` لأن القرار لا يختار مكتبة.
- المسار المباشر: تثبيت صف التبويبات، نقل التحميل إلى داخل مساحة المحتوى مع عتبة قصيرة، والمحافظة على نتائج الوضع نفسه حتى الرد؛ تحسين صف الصنف وشريط السلة من مكونات التطبيق القائمة. لا رسوم حركة زخرفية؛ استجابة اللمس فورية.
- الفحوص الموجهة: عقد مصدر لتثبيت التبويبات ومنع تفريغ محتوى التحديث، العربية/الإنجليزية وRTL/LTR، `assembleRelease` و`lintRelease` مع Firebase والتوقيع نفسه، معاينة 320dp إن كان المحاكي متاحًا. لا نشر حتى مراجعة تسليم مستقلة لمرشح APK.

## مواصفة G4 للواجهة

- التبويبات الثلاثة صف أبيض بارتفاع لمس 48dp ومؤشر أزرق ثابت 3dp تحت النشط؛ خطها 15sp، بلا خلفيات كبسولة ولا حركة انتظار تغيّر ارتفاعها.
- تنبيه التحميل/الخطأ طبقة داخل مساحة النتائج لا تؤثر في قياسات الهيدر والتبويبات والبحث. تحميل القائمة يؤخّر إظهار النص 220ms؛ إن وصل الرد سريعًا لا يظهر مؤشر عابر.
- يحتفظ التحديث بنفس النتائج فقط عند تطابق مفتاح الشركة والوضع والفئة والبحث والمؤشر، وتظهر كتلة انتقال محايدة عند اختلافه. ردود الأجيال القديمة لا تعيد رسم الواجهة.
- شريط السلة يفصل عدد الأصناف والإجمالي التقديري القادم من أودو عن زر «عرض السلة»؛ لا حساب قيمة محلي.
- فحص العرض الضيق 320dp والعربية/الإنجليزية إلزامي قبل وصف المرشح بالتسليم. لا تغييرات API أو مخزون أو استلام.

## حدود القبول الحالية

- لا جهاز ADB متصل؛ لم تُنفّذ تجربة بصرية على 320dp أو اختبار لمس عربي/إنجليزي، فلا يُعد نجاح البناء قبولًا نهائيًا للواجهة.
- Android Lint نجح في المحاولة النهائية المستقرة؛ سجل 111 تحذيرًا غير مانع، جميعها خارج مسارات الواجهة المعدلة. لا اختبار حمل لأن الخادم وتدفق البيانات لم يتغيرا.
- القرار: **GO للتجربة المحلية فقط**؛ **NO-GO للنشر أو الاستلام النهائي** حتى معاينة 320dp وRTL/LTR على جهاز، ثم ربط commit المرشح ونتائج CI وملف APK نفسه.
