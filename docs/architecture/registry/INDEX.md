## مصادر الحقيقة

| المجال | مصدر الحقيقة الساري | لا يستخدم كبديل |
| --- | --- | --- |
| كود النظام | فرع `main` في مستودع GitHub الرسمي | نسخ محلية أو أرشيفات قديمة |
| الإصدار الحي | سياسة إصدار مسمّاة ومحفوظة `root-only` على الخادم | SHA أو أسماء موديولات يرسلها المستخدم إلى Action |
| بيانات أودو | PostgreSQL وfilestore في الإنتاج | GitHub أو أرشيف المصدر |
| تصنيف إنفاق فواتير الموردين | `account.move.line.analytic_distribution` | علامة المورد أو فئة المنتج أو خانة الإدخال الجماعي |
| الاسترجاع | زوج متسق: قاعدة البيانات + filestore | symlink للكود وحده |
| عهد مندوبي المشتريات | [PRA-20260917](PURCHASE-REPRESENTATIVE-PETTY-CASH.md) | صندوق عهدة أو حساب كاش جديد |
| خدمات الموظفين | قاعدة توزيع تحليلي أصلية حسب `company + product` بمجموع 100%، تُفحص من نافذة جاهزية الشركة | تخمين التصنيف من المورد أو من نوع الخدمة عند ترحيل الفاتورة |

## الحدود الثابتة

- النشر يدوي ومقصود من GitHub Actions؛ لا يوجد نشر تلقائي عند `push` أو PR.
- لا تقبل Actions إلا `release_id` مسمى وكلمة تأكيد ثابتة؛ الخادم يقرأ بنفسه
  commit والموديولات من سياسة محمية.
- GitHub يحفظ الكود فقط. لا تدخل الأسرار أو قاعدة البيانات أو filestore أو
  النسخ الاحتياطية إلى Git.
- لوحة فواتير الموردين والمصروفات تقرأ التوزيع التحليلي المخزن في سطور القيد؛
  لا تعيد تخمين التصنيف من بيانات المورد.

- النافذة `Employee Service Readiness` تفحص الأنواع الخمسة عشر وتعرض الحالة
  والتصنيف المتوقع ولا تعدّل شيئاً في وضع الفحص.
- لا تضيف النافذة الناقص إلا بطلب صريح من محاسب مخوّل، ولا تستبدل قواعد قائمة
  أو فواتير سابقة.
- نتيجة الفحص المرئي في شركة `شركة فحص نافذة التهيئة QA 20260918` يوم
  2026-09-18: **15/15 جاهزة** بتوزيع متوقع 100%.
- اختبار مرئي موثق: `HRS/2026/00053` أنشأ الفاتورة المرحّلة
  `BILL/2026/09/0001` بقيمة 115 SAR. سطر المصروف مدين 115 على
  `400093 الإقامات وتصاريح العمل` وتحليله `إقامات وجوازات`، والذمم الدائنة
  دائن 115؛ القيد متوازن. هذا اختبار QA ولا يعد ترخيصاً للنشر.
- معالجة الشركات القائمة في QA يوم 2026-09-18: `ARZ` و`المعلم الشامي` و`دوحة
  المستهلك` أصبحت كلّها **15/15 جاهزة** بتوزيع متوقع 100%. أظهر الفحص أن
  منتجات البذرة القديمة كانت إما معطّلة بلا حساب مصروف، أو منتجات مشتركة بين
  الشركات. الإجراء الصريح في النافذة أعاد تفعيل المنتج المطابق فقط وملأ حساب
  المصروف الفارغ فقط؛ وللمنتج المشترك أنشأ بديلاً خاصاً بالشركة وأبقى المنتج
  وقاعدته القديمة دون تغيير للمستندات التاريخية. لم تُعدّل فاتورة أو قيد أو
  حساب مصروف قائم. اختبار `HrServiceAnalyticsSeedCase`: 5/5 ناجح في QA.

## ONB-READINESS-20260918 — مسار تهيئة الشركة (قيد البناء، QA فقط)

- قرار المعمارية: نافذة واحدة تقرأ جاهزية الشركة ثم تضيف الناقص باختيار صريح؛
  ليست بذرة عامة تُشغّل على كل الشركات عند ترقية وحدة.
- تستعمل حسابات ودفاتر ومستودعات وطرق دفع Odoo الأصلية؛ ولا تنشئ النافذة
  فواتير أو دفعات أو قيود أو أرصدة. العهدة اختيار مستقل يتطلب حساباً قابلاً
  للمطابقة ويومية عامة صالحة.
- الشركات القائمة لا تتلقى إلا معاينة وبنوداً مفقودة تملكها البذرة. التعارض
  أو إعداد مستخدم يوقف البند ولا يستبدله. الشركات الجديدة تبدأ بالسعودية/SAR
  والدليل السعودي حسب عقد `ABROJ-SEED-2`.
- `baseer_native_spend` هو التبعية المثبتة لتصنيف الإنفاق الذي تستعمله خدمات
  الموظفين؛ لا يرقى تلقائياً ضمن هذا المرشح ما لم يتغير مصدره. تحقق قراءةً في
  الحية بتاريخ 2026-09-19: حالته `installed` وإصداره `19.0.1.3.0` وجذر
  `spend_plan` موجود. أي إصدار مستقبلي يغير مصدره أو حالته يحتاج سياسة
  منفصلة واختبار فواتير الموردين رجوعياً.
- الدليل الحالي: إعادة تحقق QA بتاريخ 2026-09-19 نجحت بلا فشل/خطأ: **106
  اختبارًا** للموديولات `baseer_company_setup` و`baseer_service_seed` و
  `baseer_hr_services` و`baseer_pos_summary` و`baseer_procurement_requests`
  و`baseer_work_schedule`. والفحص المرئي على «المعلم الشامي» أظهر
  البطاقات العربية الأربع: الأساس، الخدمات، المبيعات والتحصيل، المخزون والعهدة.
  اختبار التحصيل يثبت الإضافة الاختيارية التراكمية فقط، واختبار المخزون/العهدة
  يثبت عدم إنشاء قيد أو دفعة أو حركة مخزون أو تمويل عهدة أثناء التهيئة.
- تحقق جدول الدوام في QA: `FutureScheduleAfterAttendanceCase` يثبت أن الحضور
  السابق لتاريخ السريان لا يمنع جدولاً مستقبلياً، بينما الحضور داخل الفترة
  الجديدة يمنعه؛ النتيجة حالتان ناجحتان بلا فشل أو خطأ.

## RPC-UI-1 — Representative petty-cash settlement picker (2026-09-19; QA-local verification)

The invoice settlement picker no longer keeps a representative balance in a
browser-lifetime cache. It shares only simultaneous RPCs and refreshes the
live company-scoped balance before assigning a representative. The accounting
contract is unchanged: the representative route retains its internal
`is_credit` compatibility marker, but the visible table now shows
Representative Petty Cash rather than a misleading Credit switch and allows
changing the representative or route. A cash/bank replacement is saved
atomically with its source, preventing an invalid intermediate row. Focused
mirror test passed for funding, current-balance RPC, representative change,
cash/bank change, and paid no-direct-payment settlement. Shared QA browser
acceptance with a funded representative remains required before any production
release. [Record](../../build-governance/REPRESENTATIVE-PETTY-CASH-SETTLEMENT-UI-FIX-2026-09-19.md).
