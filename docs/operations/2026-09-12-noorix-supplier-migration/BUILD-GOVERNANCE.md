# Noorix supplier unification — Build and migration governance

Status: G0–G3 draft; no Odoo or source-system data has been written by this workstream.

## Build contract (G0)

- **Objective:** create a local, repeatable supplier-and-supplier-category unification migration slice for all business Noorix companies, then write only canonical suppliers and global supplier tags to an isolated Baseer Odoo QA database.  Every resulting `res.partner` is shared (`company_id=False`) and later financial documents from every mapped company will reference the same canonical partner.
- **Owner instruction:** automate the process with minimal owner involvement.  The system must preserve source evidence and must never silently merge two distinct legal suppliers because names are similar.
- **In scope:** read the single Noorix PostgreSQL archive; exclude only the two test-company records `TEST` and `TEST1` by immutable source IDs captured in the run manifest; extract supplier master data and their referenced categories through `2026-09-12 23:59:59 Asia/Riyadh`; normalize only for matching; build canonical supplier and tag groups with provenance; create shared suppliers and global partner tags in QA; enforce idempotent reruns and produce a reconciliation/exception report.  The archived duplicate `وقت الكرك` company record has 15 supplier rows and stays in source evidence, but creates no Odoo company in this slice.
- **Out of scope:** source edits; production (`baseer_dev`) writes; existing-Odoo partner deletion or broad merging; invoices, payments, accounting entries, stock, payroll, tax/account policy, and category-to-account mapping.
- **Acceptance:** raw-source supplier count equals `automatic + kept_separate + blocked`; every accepted supplier/tag group has an immutable source mapping and a deterministic canonical name; every QA supplier has `company_id=False`; every category is a global partner tag without financial properties; a second run creates no partner, tag or mapping; no protected operational or financial record changes; uncertain or conflicting identities are not merged.
- **ERP control:** suppliers are master data only in this slice.  Payable accounts, taxes, payment terms, journals, outstanding balances and documents remain company-specific and are not assigned or migrated here.

### Critical journey and decision policy

`Noorix archive (read-only) → normalized staging rows → deterministic canonical group → QA shared partner + source map → reconciliation report`.

The original display name, source company, source id, and source identifier fields remain immutable evidence.  Normalized names are search keys only.  The process is fully automatic and legal-identity-only: an exact non-conflicting valid Saudi VAT identifier is the sole automatic canonical-supplier group.  Every other row automatically remains a separate supplier and may be reported as a similarity hint; no user decision is required for it.  Name, phone and near-name similarity never creates a source merge, link or target-field modification.  A conflicting legal identifier, ambiguous match to an existing Odoo vendor, or a source identity violation is blocked and is not written.

**Owner-approved cash exception:** the exact source marker `NO NAME`, with no valid VAT, denotes small cash invoices from unidentified suppliers.  It is not a supplier legal name and is never matched by name.  These rows are intentionally grouped into the one global QA partner `مورد نقدي غير مسمى`; their immutable source rows remain separately mapped.  The exact source category marker `NO NAME` becomes the single global partner tag `فواتير نقدية صغيرة`.  This narrowly-scoped rule does not apply to any other missing, similar, or malformed name.

**Owner-approved public-entity crosswalks:** the following exact Noorix supplier labels are authorized to reuse the indicated existing global Odoo partner.  Each source row retains its own immutable mapping; this exception links rows to an existing target and never merges source rows with one another, changes a target name, or extends to a similar label.  `اقامات` is a supplier label only here; its distinct source category `إقامات وجوازات` remains a global partner-tag category and is not changed.

| Exact Noorix supplier label | Existing Odoo partner | Basis |
| --- | --- | --- |
| `هيئة الزكاة والدخل` | `هيئة الزكاة والضريبة والجمارك` | Owner-approved historic government name. |
| `وزارة البلدية` | `وزارة البلديات والإسكان` | Owner-approved short/historic government name. |
| `GOSI` | `المؤسسة العامة للتأمينات الاجتماعية` | Official agency abbreviation. |
| `اقامات` | `وزارة الموارد البشرية والتنمية الاجتماعية` | Owner instruction: treat residence-permit payments as the current Ministry of Labour / Human Resources entity. |
| `الشركة السعودية للكهرباء` | `الشركة السعودية للطاقة` | Owner-approved current official name.  Noorix has two valid-VAT source groups; both source VAT values stay immutable evidence and the existing Odoo VAT is not overwritten. |

Supplier scope is current through the requested cutoff: include a source supplier if it was created on or before `2026-09-12 23:59:59 Asia/Riyadh` or is referenced by an in-scope transaction.  The supplied archive is the authoritative snapshot and ends before the requested date; that source-freshness limit is reported, never invented.  Deleted source suppliers are retained only when historically referenced and are created inactive if their canonical group has no active source row.

### Exact source-to-target field contract

| Noorix `suppliers` field | Transformation | Odoo target / evidence |
| --- | --- | --- |
| `id`, `company_id`, single `tenants.id` | Stable source identity: `noorix:<tenant-id>:<company-id>:<supplier-id>`; archive hash is snapshot evidence only. | Private mapping row; never used as display text. |
| `name_ar` | Trimmed original retained.  Search normalization applies Unicode NFKC, Arabic alef/ya/ta-marbuta unification, removes diacritics/tatweel/punctuation and legal-designator tokens.  It is never displayed as the official name. | `res.partner.name`: most frequent nonempty active raw name; ties: longest raw name, Unicode sort, smallest source id. |
| `name_en` | Trimmed original retained; no machine translation. | Evidence only in this slice; selected value can be added later only through an approved bilingual-field contract. |
| `tax_number`, `is_tax_registered` | Strip separators; a legal identifier is valid only when it is 15 digits and begins/ends with `3`.  Empty, malformed, repeated-character and conflicting values are not legal identity keys. | `res.partner.vat` only for a valid group; raw value and validation result stay in mapping evidence. |
| `phone` | Digits-only search key with Saudi prefixes normalized for equality; original retained as evidence.  Never a sole merge key. | Canonical phone only when every nonempty active row agrees; otherwise left empty and conflict reported. |
| `is_deleted` | Retained per source row. | Canonical `active=True` if any source row is active; otherwise `active=False`. |
| `supplier_category_id` | Resolve through the supplier-category contract below; do not infer accounting configuration. | Global `res.partner.category` tag membership plus evidence. |
| `category_id`, bookmarks, directory fields and timestamps | Preserve only in private evidence/report; do not infer accounting configuration. | Evidence only. |

The source archive has no supplier email or address column.  The writer must not invent either.  Each canonical partner is created with `supplier_rank=1`, `company_type='company'`, and `company_id=False`.  It must not write `ir.property`, payable-account properties, payment terms, taxes, journals, bank accounts or balances.

### Supplier-category contract

`suppliers.supplier_category_id` references Noorix `categories.id`; 233 of the in-scope supplier rows reference 101 source category ids.  Those categories carry source types `expense` or `purchase`, so they are **not** mapped to an Odoo account, product category, tax or journal.  They become only global `res.partner.category` tags attached to the canonical supplier.

The stable category identity is `noorix:<tenant-id>:<source-company-id>:<category-id>` and is unique in a private category-map model.  Source `type` is evidence only: because the target tag has no accounting behavior, tags are globally unified by an exact normalized display name regardless of `expense`/`purchase`, while every source type remains in the mapping report.  The canonical tag name uses the most frequent active `name_ar`, with the same deterministic tie-breaks as suppliers.  `code`, `name_en`, source company and original labels remain evidence.  A unique exact normalized match to an existing global Odoo partner tag reuses that tag name without changing it; ambiguity creates a separate source tag and a report entry.  The following owner-approved semantic reuse table is the only exception: `اتصالات` → `مقدمو الاتصالات والإنترنت`, `كهرباء` → `مقدمو الكهرباء`, `مياه` → `مقدمو المياه`, and both `رسوم منصات حكومية` and `منصة قوى` → `المنصات الحكومية`.  All other source categories remain distinct global tags to preserve their specific operational meaning.  Tags attach as the union of all accepted source-category memberships of each canonical supplier.  Reconciliation requires `source category ids = reused + created + blocked` and `source memberships = attached + blocked`.

### Existing Odoo partner authority

Existing Baseer partner names are authoritative when an automatic match is proven.  The writer compares every canonical supplier with globally visible, top-level Odoo contacts and maps to an existing partner without changing its name, VAT or contact fields only when exactly one target has the same valid VAT or when its exact source label appears in the narrowly-scoped owner-approved public-entity crosswalk table above.  Name, phone and near-name comparisons can raise a similarity hint only; they never map, merge or rename a partner automatically.

When a proven existing target is a non-supplier entity, QA may raise only its `supplier_rank` to `1`; its name and all company-dependent values remain intact.  A target with multiple legal candidates, a company-scoped target, or contradictory VAT is `blocked` and remains unchanged.  Source canonical names are created only where no existing target is proven.  This makes Odoo's current name the canonical display name wherever an actual shared legal identity exists, without overwriting source evidence or silently renaming production records.

## Capacity and continuity (G1)

- Observed source scale for the current cutoff: archive SHA-256 `024606ADD82DCD78DC1835828A12D7B22C56E34924FF998ABF752134160E79E2`, 3,092,452 bytes compressed and 3,438,449-byte PostgreSQL custom dump.  It has 461 supplier rows; all 449 business-source rows are in scope after excluding 12 test rows.  Of the 449 rows, 359 have a valid Saudi VAT and produce 288 canonical supplier groups; two groups reuse a unique existing global Odoo partner and 286 groups are eligible to create in QA.  The supplier-category slice has 101 referenced category ids, which collapse to 50 global partner tags and 205 canonical memberships.
- Target baseline, read-only at planning time: `baseer_dev` has 21 suppliers, all global; database 108,370,967 bytes and filestore 35,559,279 bytes (665 attachment rows / 35,883,163 referenced bytes).
- Current-cutoff existing-partner comparison: two canonical source groups have a unique exact valid-VAT match to a global top-level Odoo partner and will reuse it without changing its name or contact fields.  No name/phone comparison is an automatic link or merge; no target Odoo entity has been modified.
- Later full migration includes 4,020 invoices and 5,659 ledger rows in the archive.
- The supplier slice runs locally, one operator, one batch at a time.  It uses paged/streamed source reads, deterministic source keys and a PostgreSQL advisory lock in Odoo.
- The run records source archive SHA-256, extractor version, target database, started/finished time, counts and exception hashes.  Reruns resume by source key and never create a second target.
- QA is a separately restored Baseer database and local Odoo service.  Allocate 200 MB for its copied database, 80 MB for filestore, and 50 MB for archive, payload and reports; source-inspection containers are deleted after extraction and private payload/report evidence is retained inside the QA run directory for 90 days with no automatic host deletion.
- One batch is capped at 100 canonical groups; a batch exceeding 60 seconds, any uniqueness conflict, or any failed reconciliation rolls back and ends `FAILED`.  Target RTO is under 20 minutes to discard/recreate QA from its recorded backup; the migration operator owns the local service and reports.  Before later production promotion, a fresh coherent production backup and an isolated final candidate are mandatory.  This slice does not create or modify production data.
- No capacity promise is made before a QA run; the QA report will record observed duration and result for the 449-row representative batch.

## Data architecture and contracts (G2)

| Contract | Authority and invariant |
| --- | --- |
| Noorix source | The SHA-pinned `.tar.gz` is immutable input.  It is restored only into an ephemeral source-inspection database, then destroyed.  The stable source-system identity is the archive tenant id, not the archive hash. |
| Staging row | `(source_system='noorix', tenant_id, source_company_id, source_supplier_id)` is unique and retains raw-field hashes, normalization result, status and a separate `archive_sha256` snapshot reference. |
| Canonical group | Has a deterministic key, chosen display name and a decision (`automatic_valid_vat`, `owner_approved_crosswalk`, `kept_separate`, or `blocked_conflict`). |
| Odoo target | One `res.partner` supplier per accepted canonical group, `company_id=False`; each source row links through the private `baseer.noorix.supplier.map` model with a database uniqueness constraint on the stable source identity. |
| Category target | One global `res.partner.category` tag per accepted category group; each source category links through the private category mapping model and may attach to many canonical suppliers. |
| Accounting | No financial move, payment, balance, account-property, tax, journal or payment-term write is permitted in this slice. |

The private mapping model records source identity, canonical key, target partner, decision/method, source-row hash, run id and archive SHA-256.  Its stable source identity is unique; many rows may target one canonical partner.  The private supplier and category-map models have no operational menu and give no create/write/unlink access to ordinary Odoo users; their identity, canonical key, decision and run-hash fields are write-once by the migration writer, and a changed replay becomes a conflict.  The writer uses the Odoo ORM only, a transaction-scoped advisory lock derived from the target database plus `noorix-suppliers`, and batches of at most 100 canonical groups.  Partner/tag creation and all corresponding source mappings occur in the same batch transaction.  On restart it verifies the existing mapping and canonical target exactly; a changed source-row hash is reported as a conflict rather than silently overwritten.  It records raw source identifiers but excludes personal/contact values from routine logs.

Existing Odoo suppliers are handled automatically for one exact valid-VAT match to one existing global vendor (`company_id=False`) and for the five exact owner-approved crosswalk labels above: the writer maps to that target without changing its name, VAT, phone or properties; when it is not yet a supplier, QA may raise only `supplier_rank` to `1`.  Zero matches create a new global partner.  Multiple matches, any company-scoped match, an invalid VAT or any name/phone-only similarity outside that finite crosswalk are blocked from linking and reported.  Postconditions assert every target has `company_id=False` and `supplier_rank>0`, no company-dependent property was created/changed, each target is readable in the allowed-company context of all target companies, and all attached supplier tags are global `res.partner.category` records with no accounting side effect.

## Technology and direct path (G3)

- Reuse PostgreSQL 16, Docker, Odoo 19 ORM and Python already bundled in the local Odoo image.  Runtime is the verified Odoo image digest `odoo@sha256:f99ffac95cb39a0924622ea4118481c95651d9c84187e5b30a21c2cc4419c7dd`; PostgreSQL restore is through its bundled `pg_restore`.  No package or UI library will be added.
- A private local extractor reads the Noorix PostgreSQL custom dump into an ephemeral container; it emits a hash-pinned supplier payload and report.  A private Odoo ORM writer consumes that payload in QA.
- This is the shortest safe route: it retains relational source integrity and avoids a manual Excel import that cannot provide source provenance, idempotency, or cross-company reconciliation.
- The local QA service is separate from the existing procurement QA, because that database has an unrelated source baseline and add-on set.
