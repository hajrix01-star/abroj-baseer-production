# PAU2 — نشر إصدارات وكيل الطباعة وتسجيلها في أودو

## عقد الإصدار وبوابات البناء

| البوابة | نطاق المراجعة |
|---|---|
| G0 | ملف Windows العام في GitHub، وسجل الإصدار ورابطه وبصمته في مركز الوكيل. القبول في QA قبل أي قرار للأصلية. لا أثر على الطلبات أو المحاسبة. |
| G1 | افتراض إصدار واحد في كل دورة نشر وعشرات أجهزة الطباعة. أودو يكتب بيانات وصفية صغيرة في معاملة نشر واحدة، والتحميل من GitHub. |
| G2 | نشر أودو المحمي يستورد بيانات الإصدار المثبتة في Git. رقم النسخة فريد وإعادة التسجيل آمنة. تُحفظ إصدارات الربط القديمة ما دام ملف ربط الجهاز الجديد يعتمد عليها. |
| G3 | إعادة استخدام نموذج الإصدار وبيانات XML وآلية نشر QA وفحوص Odoo القائمة. لا تبعيات إضافية ولا بيانات اعتماد جديدة. |

## خطوات النشر

1. ابنِ الوكيل من commit مراجع. استخدم رقم إصدار جديدًا عند تغير الملف.
2. انشر الملف `Baseer.PrintAgent.exe` في GitHub Releases تحت الوسم `baseer-print-agent-<version>`. احتفظ بالإصدار السابق للاسترجاع.
3. تحقق من رقم النسخة واسم الملف وبصمة SHA-256 للملف المنشور. سجّل الرقم والبصمة في [بيانات سجل الإصدارات](../../custom_addons/baseer_pos_print_bridge/data/print_agent_github_release.xml) وارفع رقم إصدار إضافة `baseer_pos_print_bridge`. يُشتق رابط التنزيل من رقم النسخة.
4. مرّر تغيير التسجيل عبر Pull Request، ثم رقِّ الإضافة بسياسة QA معتمدة عبر `deploy-reviewed-qa-release.yml`. تسجّل الترقية الإصدار وتقاعد سجلات GitHub الأقدم تلقائيًا. احتفظ بسجل الربط الذي يحتوي ملف الإعداد حتى يجتاز بديله تجربة ربط جهاز جديد.
5. تحقق من خادم QA نفسه، ثم افتح مركز الوكيل وتحقق من النسخة المعتمدة والرابط والبصمة. اختبر زر تنزيل الوكيل وإمكانية الربط. نجاح GitHub Actions وحده يثبت انتهاء مهمة GitHub، وتبقى معاينة المركز والتحقق من الخادم جزءًا من القبول.
6. لإجازة التثبيت التلقائي على Windows يلزم اختبار نسختين متتاليتين على جهاز QA مع مهمة طباعة جارية، وانقطاع التنزيل، وفشل بدء النسخة الجديدة، والتحقق من الاسترجاع. يحتاج الوكيل 1.5.16 إلى تثبيت أولي لنسخة تدعم الآلية بعد اجتيازها هذه الفحوص.

### تكرار تجربة الرجوع

1. ابنِ ثلاث نسخ تجريبية مع `dotnet publish -c Release -p:QaProfile=true -p:Version=<version>`، واحفظ كل نسخة في مجلد منفصل. يعمل هذا البناء فقط مع ملف الربط المعزول لـQA ولا ينشئ مهمة Windows.
2. بعد التأكد من خمول عامل QA السابق، اعرض النسخة الوسطى عبر `services/baseer-print-agent/qa/Set-UpdateOffer.ps1`. ابدأ مشرف النسخة الأولى بحساب الطباعة المحدود، مع `BASEER_QA_REJECT_TRIAL_VERSION` مضبوطًا على النسخة الثالثة.
3. بعد ظهور النسخة الوسطى في أودو، اعرض الثالثة بالطريقة نفسها. تحقق من رفضها وعودة الوسطى، ثم أرسل مهمة واحدة وتحقق من قبول Windows وخروج ورقة واحدة.
4. لاختبار مسار الشبكة، شغّل بناء QA مع `BASEER_QA_NETWORK_PILOT=1` وذاكرة تنزيل فارغة. انشر ملفات `Baseer.PrintAgent.QA.exe` كإصدارات GitHub تجريبية تحت `baseer-print-agent-qa-<version>`. في قاعدة QA، عيّن معرّف الوكيل المعزول في `baseer_print_bridge.update_v2_agent_id` ورقم النسخة وبصمتها بصيغة `<version>:<sha256>` في `baseer_print_bridge.qa_update_offer`.
5. تحقّق في سجل Windows من تنزيل كل مرشح من GitHub ومطابقة بصمته. اعرض مرشح النجاح أولًا ثم مرشح الفشل. بعد التحقق من الرجوع والطباعة، اضبط عرض QA على `disabled` ومعرّف الوكيل على `0`.
