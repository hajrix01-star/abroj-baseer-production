# سجل الحوكمة الحي — مسار نشر بصير للإنتاج

## عقد البناء — G0

**الهدف.** إتاحة نشر إنتاجي يدوي من GitHub من دون أن يحتاج المالك إلى
طرفية Hostinger أو كلمة مرور في كل إصدار، مع نسخة استرجاعية حقيقية قبل أي
تحديث لموديولات أودو.

**المستخدمون.** مالك المستودع هو من يبدأ النشر من GitHub. حساب النشر الآلي
محدود ولا يملك كلمة مرور أو صلاحية عامة إلى الجذر؛ يستطيع فقط رفع الحزمة
المؤقتة وطلب غلاف نشر مضبوط المعاملات.

**النطاق في هذه الشريحة.**

- GitHub Actions يدوي، من رأس الفرع `main` فقط وبعبارة تأكيد صريحة؛ الشريحة
  الأولى تقبل فقط SHA `5e73e6b` والموديول `baseer_native_spend` حرفياً.
- حساب `baseer_deploy` على VPS، مفتاح SSH مستقل، وغلاف جذر محدود وثابت المسار
  `/usr/local/sbin/baseer-production-deploy`.
- حزمة مصدرية قابلة للإثبات، قفل تزامن، نسخة PostgreSQL + filestore، مقارنة
  لقطة بيانات تشغيلية، تبديل `current` ذري، فحص صحة، واسترجاع DB/filestore
  والرمز عند الفشل.
- أول إطلاق عبر المسار: الموديول الآمن `baseer_native_spend` فقط عند SHA
  `5e73e6b`؛ لا يشمل الملفات غير الملتزمة الموجودة محلياً.

**خارج النطاق.** خريطة الحسابات التحليلية الموحدة، إلزام التوزيع التحليلي،
ترحيل الفواتير القديمة، موديولات الدفعات/الداش بورد غير الملتزمة، أو تغيير
أي قاعدة محاسبية.

**معايير القبول.**

1. زر التشغيل في GitHub يقبل `main` فقط ولا يعمل من push أو PR.
2. يفشل الغلاف قبل إيقاف أودو عند SHA أو بنية الحزمة أو سعتها غير الصحيحة.
3. قبل المسار الذي قد يغيّر DB يوقف أودو، ثم توجد نسخة استرجاع PostgreSQL
   وfilestore قابلة للفحص ولقطة قبل/بعد لبيانات الحركة المحمية من نفس لحظة
   السكون.
4. أي فشل بعد تبديل الإصدار يعيد symlink السابق، وعند بدء تحديث الموديول
   يعيد أيضاً قاعدة البيانات وfilestore ثم يثبت صحة الإصدار السابق؛ فشل
   الاسترجاع أو الصحة يعلن `ROLLBACK_FAILED` ولا يُعلن نجاحاً زائفاً.
5. تنقل الحزمة من صندوق الرفع القابل للكتابة لحساب النشر إلى حجر root-only،
   ثم تنسخ إلى inode جديد يملكه root قبل فحص hash أو المحتوى أو الاستخراج.
6. بعد النجاح يكون `/web/login` سليماً، والموديولات المطلوبة مثبتة، وسجل
   تشغيل منقح متاح في مجلد النسخة الاحتياطية.

### خريطة دورة ERP والرقابة

هذه الشريحة لا تنشئ أو تعدل مستندات مبيعات أو مشتريات أو دفعات أو قيود.
النقطة الوحيدة التي قد تمس قاعدة البيانات هي تثبيت/تحديث موديول أودو؛ لذلك
يوقف الغلاف أودو قبلها، ثم يقارن لقطة مستندات الحركة المحمية، ويستعيد الزوج
الموثق إذا تعذر القبول. لا تعتبر الإضافة التحليلية الجديدة ترحيلاً تاريخياً.

### الافتراضات المقيدة

- الإصدار الحي الحالي هو `f54d83b` ويطابق أساس المصدر الموثق في الإيصال.
- خدمة PostgreSQL وvolume الفلستر مرتبطان بأسماء Compose الحالية.
- حساب GitHub الحالي يملك صلاحية إدارة المستودع؛ مفتاح SSH الخاص سيبقى في
  GitHub Environment secret فقط ولا يوثق هنا ولا يرسل عبر المحادثة.

## معمارية التشغيل والعقود — G2

```text
مالك GitHub
  -> Run workflow (main + DEPLOY)
  -> GitHub hosted runner يبني git archive من SHA ثابت
  -> SSH key مخصص
  -> baseer_deploy:/deploy-inbox
  -> sudo محدود إلى baseer-production-deploy
  -> lock + validate + backup + atomic release + Odoo module action
  -> health / snapshot
  -> success أو restore كامل إلى الإصدار السابق
```

**مصدر الحقيقة.** SHA الذي يخرجه `git rev-parse HEAD` من checkout لـ`main`؛
الغلاف يقارن SHA-256 للأرشيف ويقبل المسار الصريح فقط. ملفات `.env` و
`config/odoo.conf` لا تدخل الأرشيف وتنسخ من الإصدار الحي إلى الإصدار الجديد.

**العقد.** الغلاف يقبل فقط:

```text
/srv/abroj-baseer-production/deploy-inbox/baseer-<40-hex>.tar.gz
<40-hex SHA> <GitHub run id> <64-hex archive SHA>
```

ويرفض الرموز/المسارات أو archive entries خارج `source/` أو symlinks/hardlinks.
يقتصر `sudo` على الغلاف الثابت ولا يأخذ قائمة موديولات من المستخدم؛ الغلاف
يثبت/يحدث `baseer_native_spend` فقط ويرفض كل SHA غير المعتمد للشريحة الأولى.
يُضبط known_hosts بمفتاح ED25519 المفحوص من VPS، ويمنع حساب النشر كلمة المرور
والـTTY والـforwarding، ولا يملك docker group أو sudo آخر.

**التزامن ومنع التكرار.** lock على مستوى الخادم؛ اسم الإصدار يحمل SHA وrun id؛
وإعادة تشغيل نفس SHA تنتج إصداراً مستقلاً مع نسخة احتياطية جديدة بدلاً من
الكتابة فوق الإصدار الحالي.

**الفشل والرجوع.** قبل التبديل كل شيء قابل للفشل بلا أثر. بعد السكون تؤخذ
اللقطة والزوج الاسترجاعي، ثم بعد التبديل يعيد trap symlink السابق؛ وإذا بدأت
عملية أودو يعيد dump وfilestore المأخوذين في السكون.
لا يبتلع فشل الاسترجاع أو فحص الصحة؛ يسجل `ROLLBACK_FAILED` ويخرج بفشل واضح.
لا يحذف نسخاً قديمة تلقائياً؛ التنظيف سياسة منفصلة بعد مراجعة السعة.

## التقنية والاعتمادات — G3

| القرار | البدائل | قرار المسار المباشر |
|---|---|---|
| تنفيذ النشر | طرفية Hostinger يدوية أو runner ذاتي | GitHub-hosted Actions عبر SSH؛ لا يحتاج runner مقيم أو جلسة متصفح، ويتطلب إعداداً واحداً للمفتاح والحساب المقيد. |
| حزمة المصدر | clone من VPS بمفتاح GitHub أو رفع ملفات يدوياً | `git archive` من SHA checked-out؛ لا يحتاج Git credential على الخادم ولا يضم `.env`. |
| حماية الوصول | root SSH key لعمليات Actions | مستخدم نشر منفصل + sudo لغلاف واحد ثابت؛ لا كلمة مرور ولا docker group، وknown_hosts صريح. |
| النسخ والاسترجاع | symlink فقط | PostgreSQL + filestore + symlink؛ يلزم لاستعادة أثر تثبيت موديول أودو. |
| مكتبات جديدة | أي action طرف ثالث للنشر | لا توجد؛ فقط `actions/checkout` الرسمي المثبت على SHA. |

**سؤال المسار المباشر.** نعم: هذا أقصر مسار يزيل اعتماد المالك على طرفية
الجوال من دون جعل VPS عاماً أو تخزين GitHub credential عليه، ويحافظ على نمط
الإصدار الذري والنسخ الموجود بالفعل.
