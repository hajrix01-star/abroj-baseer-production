## G0 contract / architecture impact
Reference POS-GD1; ARCHITECTURAL financial delta. Source official/main ca92e7eb4; isolated branch codex/pos-global-discount-qa-20261119. Authorized: implement and deploy to QA only; no LIVE deployment, production fiscal sends, or historical data migration. Native pos.order/account.move/account.tax and Saudi EDI remain authoritative. Do not install the reviewed third-party ZIP.

User flow: unpaid sale draft -> synchronize -> server-authorized percent/fixed discount -> canonical order -> native payment/invoice -> native Saudi EDI. Fixed amount means gross reduction in SAR; percent applies to eligible positive sale lines. Remove discount before changing the discounted basket. Refund: select original sold lines -> server allocates reversal of original discount -> native credit note; full/partial/repeated refunds must never refund more than net originally paid. Audit user/time/intent and persist source-line linkage. No discounts on refunds, protected source/replacement lines, tips, combos or formula/fixed taxes in this first candidate; reject unsupported tax cases explicitly rather than claim support. Ordinary 15%, zero/exempt and price-included/excluded percentage taxes must work. Do not change protected item prices or tobacco rules.

Acceptance: 10% of115 ->103.50 (100+15 ->90+13.50); fixed20 of115 ->95; mixed tax groups and cent rounding; replacing/removing discount; stale/malicious payloads and direct CRUD; authorized company/POS and closed/paid guards; idempotent retry; tax/accounting receipt/XML parity; full, partial and successive refund allocation including last-cent residual; same-company original invoice credit-note link. Real ZATCA sandbox validation required before any LIVE approval; if credentials/SDK unavailable report that as an unpassed gate, not compliance.

## G2 direct architecture decision (pending independent gate review)
New owned addon baseer_pos_global_discount, reuse Odoo19 account.tax._prepare_global_discount_lines (supports percent/fixed GROSS), _export_base_line_extra_tax_data and native invoice conversion. Server RPC on synchronized unpaid draft, company/access/session check and row lock; append negative native discount lines with explicit source-line linkage, immutable snapshots and idempotency UUID/revision. Group/allocate by source and tax to preserve partial refund lineage; refunds reverse original allocated amounts cumulatively, last refund consumes residual. Backend enforces integrity on sync/direct mutation and payment; frontend displays canonical data and performs no financial computation. Online required for apply/remove/refund preparation. No silent stale-basket recompute at payment. Refuse unsupported tax/protected combinations. Do not enable native auto-reapply JS for this owned configuration. Arabic/English dialog uses native OWL Dialog/control buttons, touch48px, RTL/LTR and Western digits. UI never changes fiscal totals/QR. EDI export must be inspected/tested against actual QA runtime before selection is final.

Alternative rejected: supplied ZIP (missing dependencies, client-only limits, incorrect fixed tax handling); independent tax calculator (duplicated authority); global precision changes to native discount field (system-wide side effects).

Binding design clarifications:
1. Call the native helper once over the full eligible basket and preserve source AND tax identity during grouping. Do not independently round a fixed discount per line or call the fixed helper once per line with the full amount. Carry exported extra_tax_data into POS lines and invoice lines unchanged through native conversion; assert actual gross/tax totals after persistence.
2. Treat unsupported protected/source/replacement/combination and formula/fixed-tax baskets as an explicit rejection in this candidate, with a clear translated message. Do not silently call a partial discount a whole-invoice discount. Whether ordinary tip lines are excluded must be explicit in the UI. This limitation is a QA acceptance limitation, not proof of support for tobacco/protected cases.
3. Metadata, source links, allocated money, UUID/revision, snapshot and command status are server-owned. A context flag supplied over RPC is not an authorization bypass. Direct create/write/unlink, x2many command variants, ordinary sync and payment must preserve the same integrity. No cashier sudo. Company/POS/session/cashier membership checks precede idempotent-result lookup, including reused command UUIDs.
4. Serialize all refund reservation/finalization and discount mutation against the source order in a deterministic lock order shared with existing protected/kitchen flows. Count already completed refunds AND conflicting draft reservations or validate remaining allowance atomically at finalization; otherwise two partial drafts can both claim the last cent. A refunded item retains the original price/tax identity and same-company invoice/credit-note lineage. Refunds consume source-specific allocated base and tax cumulatively; final refund takes the remaining base AND tax cents, never only the gross residual. Block direct refunding of standalone discount lines and mixed sales/refund baskets in the first candidate.
5. Financial input is a finite, bounded Decimal parsed from the raw string; reject booleans, NaN/Infinity, invalid syntax, excess decimals, percent outside0–100 and fixed amount above eligible gross. The native Odoo tax engine's float representation is an explicit interoperability boundary, not a second custom money engine. Persist and compare results with native currency precision; no frontend amount allocation.
6. Scope the native-pos_discount auto-reapply suppression only to the new managed configuration; avoid changing other POS behavior. A lost response must block further edits/payment until canonical reconciliation proves command outcome. Removing/replacing discount cannot erase audit history. Basket lock covers product, qty, prices, per-line discount, taxes, fiscal position, pricelist, company/config, source UUIDs, addition/deletion/merge and refund links; do not allow indirect owner changes.
7. G1's20-device/200-line values are declared design assumptions, not observed owner use or capacity certification. A single bounded safe latency measurement suffices initially; shared-QA load is not authorized. No additional infrastructure/dependency is justified.
8. G5/G8 must prove native posted accounting/receipt/XML totals and credit-note links using actual installed localization plus offline SDK rules and sandbox path when available. Missing credential/SDK or unsupported export is an unpassed fiscal gate and bars LIVE readiness; no changing QR generation or bypassing signed XML/reporting guards to make a test pass.

The implementation may now begin within these boundaries. Any change in the accepted unsupported-tax scope, lock model, fiscal representation or refund allocation reopens G2. G4–G8 remain NOT STARTED.
