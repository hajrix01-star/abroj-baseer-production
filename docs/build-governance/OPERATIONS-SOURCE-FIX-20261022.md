1. رفض `_pos_amounts` وقراءة قيد الجلسة كل طلب بلا بنود، حتى الطلب الأصلي الصفري تمامًا. الآن لا يُستبعد إلا طلب `source=pos` بعملة الشركة، بلا أي إجمالي/ضريبة/دفع/مرتجع، ولا فاتورة أو مردود أو دفعة حتى الصفرية. تثبت روابط الدفع والعكس بمقارنة SQL-ID مع ORM وفق حقوق القارئ؛ لا يصبح السطر المحجوب صفريًا. يسجل الاستبعاد كمعلومة، ولا يولد حدثًا ماليًا.
2. يجمع التقرير كاش إجمالي بنود POS، بينما Odoo19 يوزع فروق التقريب العام عند حساب الإجمالي الأصلي. أعيد إنتاج فرق سنت على نسخة البيانات. يثبت الإصلاح كاش كل بند وفق `total_excluded_currency/total_included_currency` في مسار الضرائب الأصلي، ثم يقرأ تخصيص net/tax النهائي ويثبت مطابقته للرأس والضريبة بعملة الشركة. لا يُستخدم تقريب `raw_total_included` بوصفه بديل الكاش، ولا تُقبل فروق تعويض بين بندين. تبقى المطابقة الدقيقة للإجمالي؛ لا توسيع لمسار cash rounding أو summary أو العملات الأجنبية.
3. بعد الإصلاحين يصل الشهر إلى طلب بيع **غير صفري بلا أي بنود فعلية في SQL** مع دفعة وجلسة مغلقة وقيد مرحل. هذا نقص بيانات حقيقي، لا يجوز إخفاؤه أو اختراع بنوده من الدفع. أكدت قراءة إنتاجية SQL محكومة بـREAD ONLY وROLLBACK بقاء الحالة؛ المصدر المنشور وبصمته لم يتغيرا. معرّف الطلب والتفاصيل في الدليل الخاص فقط. السبب التاريخي لفقد البنود غير مثبت.
