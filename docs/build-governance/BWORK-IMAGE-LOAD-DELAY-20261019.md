# BWork — تأخير فتح الصور (BIL-20261019)

## النطاق والخريطة المعاد استخدامها

الأساس المنشور41bd5bf6 (0.1.24/build25)، فرع مستقل
`codex/bwork-image-load-delay-20261019`. إعادة استخدام خريطة BCM ومسار الأرشيف
والوسائط؛ لا مسح نظام أو اعتماديات أو خادم جديد. إصلاح CONTROLLED محدود
بـruntime.ts وMediaTile واختباراتهما. لا تغيير مصادر الرسائل أو صلاحياتها أو
المسارات/العقود أو حدود الملفات أو واجهة العرض. طلب المالك التشخيص والإصلاح،
لا بناءAPK أو نشرQA/Live في هذه الجولة.

## السبب المثبت وحدود الاستنتاج

- `localMediaLease` كان يحجز `serialMedia` أثناء انتظار HTTP للجسم كاملًا؛
  نفس الطابور يملك قراءة الكاش وstageFile والتنظيف. مصغر واحد بطيء يمنع حتى
  قراءة ملف محلي صحيح. اختبار فعلي للمحول مع شبكة معلقة فشل قبل الإصلاح:
  بقيت قراءة الكاش والتهيئة محجوبتين حتى تحرير الاستجابة.
- `MediaTile.resolve(true)` أثناء تحميل مصغر كان يسجل الرغبة فقط وينتظر
  نجاح المصغر، وفشله لا يطلب الأصل. اختبارا المكون أثبتا الفشل قبل الإصلاح.
- النمطان موجودان بالفعل في المصدر3497dc5d السابق لـ0.1.23 و0.1.24؛ ليس
  دليلًا على انتكاسة جديدة سبّبها إصلاح إرسال المرفقات. لا نملك تسجيل الهاتف
  أو آخر حالة ناجحة لننسب كل التأخير المبلغ عنه إلى هذين السببين وحدهما.
- غياب الملف المحلي يتطلب تنزيلًا فعليًا؛ لا يمكن ضمان فتح فوري مع شبكة
  بطيئة. أصل محذوف من الخادم أو رفض صلاحية يبقى خطأً، لا صورة مختلقة.

## القرار المحدود قبل التحقق

تظل عمليات الملفات والكاش والسعة وLRU/pins متسلسلة. انتظار الشبكة والتحقق
من الملف الجزئي خارج قفل التعديلات؛ التثبيت والفحص الأخير والتنظيف عند فشل
التثبيت داخله. مساران فقط: مصغر تلقائي واحد وأصل متعمد واحد، فلا طوفان
تنزيلات ولا انتظار الأصل خلف المصغر. حجز سعة/عدد للملفات الجارية وإعادة
فحص قبل التثبيت، وإزالة الحجز في النجاح والفشل. تتشارك الطلبات المطابقة
نفس الجسم بمفتاح الجيل/مسار الحساب والشركة والغرفة والعضوية والنسخة والبصمة؛
كل مستهلك يحصل على lease مستقل وجسر pin يمنع إخلاء الملف بينهما.

الضغط يبدّل serial القبول للمصغر ويبدأ أصلًا واحدًا فورًا؛ المصغر المتأخر
يحرر lease ولا يبدّل العارض. تبقى حواجز الخلفية والتدوير والحساب والعضوية
والصلاحية وSHA256 وفحص MIME/الأبعاد والحدود والأوفلاين وcachedOnly كما هي.

### خريطة فرق التسليم

`MediaTile → localMediaLease → [قفل كاش قصير] → [مصغر1 | أصل1] → [قفل تثبيت قصير] → lease مستقل`

الحقيقة دون تغيير. الأجزاء غير المتغيرة (ERP/الأرقام/ترحيل البيانات/النشر)
خارج الفحص. قرار المصدر المحلي GO وفق المراجعة أعلاه؛ أي APK جديد يحتاج
فحص الحزمة والترقية والرحلة الأصلية قبل النشر، ولا يعاد استعمال APK0.1.24
المبني قبل هذا الإصلاح على أنه يحتويه.

## B07 — دليل الصور الجديدة: اكتشاف معاينة الرسالة بعد الإقرار

أرسل المالك صورتين لاستكمال التشخيص والإصلاح: صف معلق باسم ملف وساعة، ثم
صف مرسل بعلامة صح ومكان صورة فارغ. هذا لا يثبت فشل HTTP أو مدة الانتظار.
صف الطابور يعرض اسم المرفق فقط في التنفيذ القائم؛ لا نستنتج فقد بايتاته.

ثبت مسار ثالث في المكتبة المثبتة FlashList2.3.2: ViewabilityHelper يقارن
الفهارس المرئية لا هوية الصف. صف معلق يتحول إلى صف صورة مُقرّ بنفس الفهرس
لا يصدر بالضرورة حدث ظهور جديد، فيما TimelineScreen يخزن معرفات الرسائل
المصورة فقط. لذلك تظل previewVisible=false ولا يبدأ المصغر. اختبار المكوّن
مع ViewabilityHelper الحقيقي أعاد الفشل قبل أي تغيير للتطبيق.

الأثر المحدود الإضافي: TimelineScreen/اختباره فقط. إعادة حساب الظهور عبر
APIالقائمة القائمة بعد commit/إطار العرض، عند تغير هوية صفوف الوسائط أو
النطاق/سلطة العرض، لا عند كل poll متطابق. لا جعل كل الصفوف مرئية، ولا تغيير
عتبات150ms/10% للمعاينة أو600ms/75% لإيصالات القراءة. الإطار يلغي عند الحجب
أو تبديل النطاق؛ لا طلب وسائط أثناءالخلفية أو تلاعب بإيصال/طابور/مصدرالخادم.
لا إضافة معاينة للملف المرحلي أو تعديل تسوية ACK في هذا الفرق.
