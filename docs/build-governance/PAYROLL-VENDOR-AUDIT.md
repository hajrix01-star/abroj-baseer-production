# Payroll vendor financial audit — 2026-09-08

**Decision: QA evaluation only; NO-GO for production financial use as shipped.** Installation availability does not establish accounting correctness. Existing vendor forms, salary rules and calculation engine remain potentially reusable, but the four-module combination needs accounting and lifecycle corrections before real payroll or loans.

Scope: official source commit `c70e3f54b50442f46faed15f2643aed278b3fb37`, quarantined under `.local-backups/payroll-p1/source`: `hr_payroll_community`, `hr_payroll_account_community`, `ohrms_loan`, `ohrms_loan_accounting`. No application code or settings were changed by this audit. After parent installed the modules in QA, a bounded native Odoo shell characterization ran against `baseer_reports_qa_20260907`; every fixture was rolled back.

## Runtime evidence

Reproducible script and evidence: `payroll_p1_vendor_checks.py`, `payroll_p1_vendor_checks.json`, `payroll_p1_vendor_checks.log` beside this document. This is defect characterization, **not seven passing acceptance tests**.

- The first unmodified payslip approval raises `AttributeError: 'hr.payslip' object has no attribute 'net_wage'`, in `ohrms_loan_accounting/models/hr_payslip.py:53`. The source references this attribute but none of these four modules defines it.
- To inspect downstream behavior, the test alone temporarily supplies a class attribute `net_wage=1000`. This is explicitly recorded in JSON, is not a production fix, and is removed before exit. With that shim, the native fixed salary rule and accounting engine post a balanced SAR 1,000 journal entry. A repeated approval posts **another SAR 1,000** and replaces the payslip's `move_id`; both entries remain posted.
- The posted payslip's end date can subsequently be changed while its journal entry remains posted.
- Payslip cancellation then deletes the latest journal entry while leaving the first duplicate posted and no longer linked from the payslip.
- A synthetic loan submits successfully. The vendor tries to send mail immediately; both `mail.template.send_mail` and `mail.mail.send` were intercepted before any actions. Two mail calls were suppressed, no messages were sent.
- A loan with a paid installment remains flagged paid after its loan is cancelled. This bounded test sets the paid flag directly; it does not claim end-to-end salary recovery was validated.

The script uses a synthetic QA employee, version/contract, salary category/rule, structure, accounts and journal. It commits no employees, salary slips, loans, messages or ledger entries. Database sequences may consume values during rollback, which is native PostgreSQL behavior.

## Payment availability and native reuse

These modules supply salary calculation, payslip records and general journal entries. No `account.payment` or `account.payment.register` integration exists in their source. The payslip `paid` field is only a Boolean labelled “Made Payment Order?”. Therefore **Done is not proof of salary disbursement or bank reconciliation**.

Loan disbursement and standalone collection post directly against the selected cash/bank journal's default account; they do not create a native payment or bank statement transaction. Configuring a receivable account may additionally require partner/maturity information; the disbursement code supplies neither. This account-type case has not been runtime-tested here.

Native Odoo 19 provides the building blocks: `odoo/addons/account/models/account_move.py` `_reverse_moves` around line 5501, `action_register_payment` around 6105, and `button_cancel` around 6390. Native `button_cancel` resets a posted move to draft if permitted, removes reconciliations and cancels it; it is not an auditable reversal. The vendor then explicitly unlinks the move. Native payment/reversal APIs should be reused under their account, partner, date, currency and reconciliation requirements.

## Smallest defensible implementation path

1. Keep the vendor payroll structure, calculation and forms. Add one separate Baseer extension, without editing vendor files, for approval idempotence, finalized-source guards, company checks and safe reversal policy. For the first bounded release, allow payroll accrual only and use clearly labelled native payment actions; do not represent the Boolean paid flag as settlement evidence.
2. Treat automated loan recovery as a separate gate. The missing attribute and disconnected accounting hook show that merely selecting accounts is insufficient. Either keep the loan accounting automation unavailable initially, or complete loan disbursement/recovery/reversal and installment ownership as a tested unit.
3. A narrow salary-only guard layer is **small-to-medium**, likely a few hundred lines plus integration/concurrency/security tests. Full safe salary + loan + repayment/cancellation support is **medium**, several model/security extensions and materially more tests; describing it as a trivial configuration or a ten-line fix would be misleading. These are source-based scope estimates, not a delivery commitment.
4. Acceptance must prove one financial result on repeat/concurrent approval, independent company access including child RPCs, immutable posted source, correct salary payable/payment reconciliation, installment principal/interest reconciliation, and reversal restoring exactly the original balances. Re-run with notifications suppressed and all fixtures rolled back before a production decision.

No claim is made here about Saudi payroll/GOSI/WPS statutory completeness; these vendor modules and this bounded technical audit do not establish it.
