## G0 — user journey and accounting controls

User authorized the agreed native Odoo editable table. Batch header: single company, entry date, automatic batch number. Each row: invoice date (also payment date), existing supplier, supplier invoice reference, purchases/expense type, category, optional description, gross total, configured purchase tax or explicitly no tax, computed net/tax, configured outgoing payment method or credit. Bill link after approval, printable batch summary. Regular detailed bills remain native and unchanged. Summary entries do not receive stock.

Draft batches have no financial effect. The explicit Save and approve button validates all rows, creates/posts native vendor bills, registers/reconciles native payments for paid rows, and verifies residual zero and actual paid status. Credit rows remain payable. One RPC/transaction/savepoint for the whole batch: any error rolls back every generated document. No partial successes, force-paid flags, manual ledger entries or commits. Native fiscal locks, accounts, taxes and permissions apply. A paid method that cannot immediately settle the bill must fail with a clear configuration error; do not silently change financial configuration. Payment date equals invoice date; prevent silent native accounting date shifts across locked periods.

Approved batch inputs and document links are immutable through ORM/RPC, including child writes/unlink/reparenting. Correction of financial documents remains native reversal/credit workflow; links and current bill state remain visible. Normal save preserves draft input; only the clearly labeled approval action creates final invoices.

## G1 — bounded capacity assumptions

Three independent Saudi SAR companies; assume 3 concurrent operators, 100 batches/month/company with average10 and maximum50 invoices per batch. Paginated native list, indexed company/state/date and batch foreign keys, no all-history fetch. Target a10-row approval under15 seconds on local QA; measure1/10/50 rows and same/different-batch concurrent retries.50 is a hard synchronous ceiling, not an unbounded queue promise. Reuse PostgreSQL transaction recovery and local backup discipline. Record measured limits; no production capacity claim. No cron/queue/external integration/new dependency.

## G2 — data ownership and contracts

Small addon baseer_purchase_batch: persistent batch and line models plus a company-scoped category mapping to a native service product. Mapping selects an existing product in the same category and permitted company, with native product/category expense account. Managers configure mappings; operators select their category. No hidden product/account creation and no sudo accounting writes. The product on generated bill lines gives the existing cash report its category without modifying the report handler. Support one category and one simple configured percentage purchase tax per invoice in PB1; multi-category, grouped/fixed/mixed tax and inventory bills use the regular flow.

Raw gross amount is finite, positive SAR, maximum2decimal places, validated with Decimal before ORM persistence. All custom money aggregation/validation uses Decimal in Python, never JS. Native Odoo tax/bill/payment engine owns final accounting values; derived unit-price precision needed for exact gross roundtrip crosses the native float ORM boundary only. Do not rewrite Odoo monetary storage/calculations. Final gross and displayed preview must reconcile to native computed bill net/tax to the cent before posting; reject unsupported configurations. Persisted user amount remains2decimals. Western0–9 digits and Arabic/English UI.

Company record rules on every custom model plus native accounting ACL, check_company and explicit allowed company checks. Group account invoice operators may draft/approve within their native rights; accounting managers configure category mappings. No external state supplied by the client may set approved state, bill/payment links, sequence or approval audit. Revalidate all sources and tax/journal/product companies at approval.

Concurrency: lock and invalidate batch before checking state; child writes/reparent/delete use the same batch lock. Repeated approve returns existing result. Serialize batch approvals per company before supplier-reference duplicate checks. Reject duplicate supplier references per commercial supplier/company within a batch or against existing noncancelled vendor bills. This serializes custom-batch entry, not concurrent regular Odoo bill entry; native duplicate detection remains the regular-flow authority. Do not claim a universal cross-module uniqueness constraint. Lock/reference indexes and bounded queries reviewed before release.
