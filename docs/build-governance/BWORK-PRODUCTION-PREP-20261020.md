# BPR-20261020 — مرشح إنتاج BWork مباشر دون Tailscale

## عقد البناء والحدود

فوّض المالك تجهيز نسخة الإنتاج والـAPK وإكمال الفحوص المطلوبة، **دون نشر أو تغيير Live قبل عرض النتيجة واعتمادها**. الإذن تحضير مصدر وحزمة محلية واختبار معزول فقط؛ لا push/merge/release/workflow/deploy أو ترقية غلاف/إعداد خادم/حذف/أدوار أو إيقافTailscale. قراءة الهدف غير المدمرة ضمن الجرد، ولا كتابة بيانات تشغيلية لإثبات الجاهزية.

المصدر الأساس `9bd6cc5c50a2796b74ee25a29fbc17aa3be09b27`، وشريحة المنتج المقبولة `735b4b9a`؛ فرع مستقل `codex/bwork-production-prep-20261020`. مرجع المعمارية BCR/BRT/BMS/BCS وسجل `output/bwork-live-readiness-20261020/readiness-0.1.32.md` معاد استخدامه. لا إعادة اكتشاف أو إعادة بناء الخريطة أو الوظائف المالية.

النطاق ARCHITECTURAL محصور بهوية الإنتاج وتوقيعه ووجهته وحراس التجهيز وبروفة/حزمة النشر غير المنفذة. الهدف: تطبيق مستقل `com.baseer.bwork`، إصدار مقترح1.0.0/build1، يتصل مباشرة بـ`https://baseer.abroj.sa` وقاعدة `baseer_prod`؛ QA0.1.32/build33 وهويتها وتخزينها وشهادتها باقية دون تغيير. مفتاح الإنتاج لم يُعتمد بعد؛ طلب المالك البحث عن القديم قبل القرار. لا إنشاء أو استيراد أو إعادة استعمال مفتاح تطبيق آخر تلقائيًا ولا fallback إلى Debug.

## الخريطة والملكية وG1/G2

المسار: إعداد إنتاج صريح → Expo/bundle + native بنفس origin/package/database → HTTPS العام المحروس → خدمات أودو الأصلية. لا نقل كاش/رسائل/طوابير QA إلى الإنتاج، ولا POST fallback أو إلغاء مصادقة أو فتح قاعدة البيانات للإنترنت. تحفظ الحسابات والدقة والشركات والـAPIv2 والخدمات الحالية كما قُبلت؛ لا تغيير محاسبي أو schema أو اعتماد جديد.

تعاد أدلة640نجاحًا للعميل والـ213ثابتًا و39ORM/HTTP و18مطابقةQA؛ عند استقرار الفرق ينفذ check:bwork الإلزامي مرة واحدة مع الحالات الجديدة، ولا تعاد nativeSQL/migration/load غير المتغيرة بلا سبب. حجم العينة المثبت5شركاتQA و1460صفًا مخولًا؛ لا شهادة لحمل الإنتاج أو رقم تزامن جديد. حدود الصفوف والمهل والسعة والخلفية كما هي. سبب الاختبار الجديد هو فصل origin/package/signing وتجهيز الإنتاج لا نمو بيانات أو منطق مالي جديد.

العزل: لا تشغيل مرشح الإنتاج متصلًا بالأصلية لأوامر كتابة قبل اعتماد المالك. تثبيت محاكي مرشح جديد مشروط بعزل الشبكة قبل install/launch؛ لا استعارة حاويةQA أو نسخ حساباتها. البروفتان fresh/upgrade واستعادةDB+filestore المعتمدتان تعاد أدلتهما للشيفرة غير المتغيرة؛ أي تشغيل جديد على بيانات حقيقية/نسخة منها يحتاج حدودًا معزولة واضحة ومراجعة قبل التنفيذ، ولا نسخ أسرار أو إرسال بيانات المالك لخدمة جديدة.

## معايير القبول

1. production يرفض QA/Tailnet/loopback/private/wrong realm، origin العام المحدد وDBالأصلية مثبتان بالـbundle/native والـmanifest. QA لا يتغير، والـnative staging لا يقبلorigin مخالفًا لملفه.
2. مفتاح إنتاج موثوق وموافَق عليه، وعدم fallback إلى Debug؛ لا أسرار بالمصدر أو السجل أو APK، وبصمة الشهادة العامة فقط في دليل المرشح. إنشاء مفتاح جديد إن اختير يكون بتفويض مستقل وحفظ ونسخة أمان مناسبة.
3. إصلاح FCM staging المحدود يمنع فقد profile/package عند التحقق؛ لا تفعيل مزود أو تغيير أسرار خادم. configured FCM delivery يبقى غير مقبول حتى إعداد واختبار مفوضين؛ تعطيل التشغيل ليس ادعاء دعم فعلي.
4. لا عبارة«نسخة تجريبية» في الإنتاج؛ نفس الشعار/المكونات/الأحجام وAR/EN، وإصدار أصلي منفصل. لا إعادة تصميم واجهة أو حركة جديدة.
5. APK عادي source-frozen/release/nondebug، same declared permissions بلا توسعة، exact package/origin/db/version/signer/no fixtures، مع proof/bundle-map/native+asset provenance.
6. حزمة تجهيز خادم محلية تشمل source closure والنسخ وحراس الغلاف والسياسة المقترحة والـbackup/rollback، دون تنفيذ أو إرسالها. تصنيف Live لم ينفذ بعد؛ غياب الوحدات ليس fresh GO. لا نسخ سياسة QA ذاتdashboard فقط.
7. القبول الفعلي بلاTailscale يتطلب هاتفًا علىWi-Fi خارجي وبيانات الجوال، معHTTPS/DNS/session/المحادثات والوسائط والأهداف/التقارير؛ لا تعادل صفحةLogin عامة أو mock أو emulator مع DNSمحول هذا القبول. Live لا يحتوي BWork بعد؛ ما لا يمكن إغلاقه دون تغييرLive يُعرض كمانع ولا يتجاوز إذن المالك.
