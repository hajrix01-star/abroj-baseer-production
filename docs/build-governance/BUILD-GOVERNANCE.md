# سجل الحوكمة الحي — مسار نشر بصير للإنتاج

## عقد البناء — G0

**الهدف.** إتاحة نشر إنتاجي يدوي من GitHub من دون أن يحتاج المالك إلى
طرفية Hostinger أو كلمة مرور في كل إصدار، مع نسخة استرجاعية حقيقية قبل أي
تحديث لموديولات أودو.

**المستخدمون.** مالك المستودع هو من يبدأ النشر من GitHub. حساب النشر الآلي
محدود ولا يملك كلمة مرور أو صلاحية عامة إلى الجذر؛ يستطيع فقط رفع الحزمة
المؤقتة وطلب غلاف نشر مضبوط المعاملات.

**النطاق في هذه الشريحة.**

- GitHub Actions يدوي، من رأس الفرع `main` فقط وبعبارة تأكيد صريحة؛ الشريحة
  الأولى تقبل فقط SHA `5e73e6b` والموديول `baseer_native_spend` حرفياً.
- حساب `baseer_deploy` على VPS، مفتاح SSH مستقل، وغلاف جذر محدود وثابت المسار
  `/usr/local/sbin/baseer-production-deploy`.
- حزمة مصدرية قابلة للإثبات، قفل تزامن، نسخة PostgreSQL + filestore، مقارنة
  لقطة بيانات تشغيلية، تبديل `current` ذري، فحص صحة، واسترجاع DB/filestore
  والرمز عند الفشل.
- أول إطلاق عبر المسار: الموديول الآمن `baseer_native_spend` فقط عند SHA
  `5e73e6b`؛ لا يشمل الملفات غير الملتزمة الموجودة محلياً.

**خارج النطاق.** خريطة الحسابات التحليلية الموحدة، إلزام التوزيع التحليلي،
ترحيل الفواتير القديمة، موديولات الدفعات/الداش بورد غير الملتزمة، أو تغيير
أي قاعدة محاسبية.

**معايير القبول.**

1. زر التشغيل في GitHub يقبل `main` فقط ولا يعمل من push أو PR.
2. يفشل الغلاف قبل إيقاف أودو عند SHA أو بنية الحزمة أو سعتها غير الصحيحة.
3. قبل المسار الذي قد يغيّر DB يوقف أودو، ثم توجد نسخة استرجاع PostgreSQL
   وfilestore قابلة للفحص ولقطة قبل/بعد لبيانات الحركة المحمية من نفس لحظة
   السكون.
4. أي فشل بعد تبديل الإصدار يعيد symlink السابق، وعند بدء تحديث الموديول
   يعيد أيضاً قاعدة البيانات وfilestore ثم يثبت صحة الإصدار السابق؛ فشل
   الاسترجاع أو الصحة يعلن `ROLLBACK_FAILED` ولا يُعلن نجاحاً زائفاً.
5. تنقل الحزمة من صندوق الرفع القابل للكتابة لحساب النشر إلى حجر root-only،
   ثم تنسخ إلى inode جديد يملكه root قبل فحص hash أو المحتوى أو الاستخراج.
6. بعد النجاح يكون `/web/login` سليماً، والموديولات المطلوبة مثبتة، وسجل
   تشغيل منقح متاح في مجلد النسخة الاحتياطية.

### خريطة دورة ERP والرقابة

هذه الشريحة لا تنشئ أو تعدل مستندات مبيعات أو مشتريات أو دفعات أو قيود.
النقطة الوحيدة التي قد تمس قاعدة البيانات هي تثبيت/تحديث موديول أودو؛ لذلك
يوقف الغلاف أودو قبلها، ثم يقارن لقطة مستندات الحركة المحمية، ويستعيد الزوج
الموثق إذا تعذر القبول. لا تعتبر الإضافة التحليلية الجديدة ترحيلاً تاريخياً.

### الافتراضات المقيدة

- الإصدار الحي الحالي هو `f54d83b` ويطابق أساس المصدر الموثق في الإيصال.
- خدمة PostgreSQL وvolume الفلستر مرتبطان بأسماء Compose الحالية.
- حساب GitHub الحالي يملك صلاحية إدارة المستودع؛ مفتاح SSH الخاص سيبقى في
  GitHub Environment secret فقط ولا يوثق هنا ولا يرسل عبر المحادثة.

## معمارية التشغيل والعقود — G2

```text
مالك GitHub
  -> Run workflow (main + DEPLOY)
  -> GitHub hosted runner يبني git archive من SHA ثابت
  -> SSH key مخصص
  -> baseer_deploy:/deploy-inbox
  -> sudo محدود إلى baseer-production-deploy
  -> lock + validate + backup + atomic release + Odoo module action
  -> health / snapshot
  -> success أو restore كامل إلى الإصدار السابق
```

**مصدر الحقيقة.** SHA الذي يخرجه `git rev-parse HEAD` من checkout لـ`main`؛
الغلاف يقارن SHA-256 للأرشيف ويقبل المسار الصريح فقط. ملفات `.env` و
`config/odoo.conf` لا تدخل الأرشيف وتنسخ من الإصدار الحي إلى الإصدار الجديد.

**العقد.** الغلاف يقبل فقط:

```text
/srv/abroj-baseer-production/deploy-inbox/baseer-<40-hex>.tar.gz
<40-hex SHA> <GitHub run id> <64-hex archive SHA>
```

ويرفض الرموز/المسارات أو archive entries خارج `source/` أو symlinks/hardlinks.
يقتصر `sudo` على الغلاف الثابت ولا يأخذ قائمة موديولات من المستخدم؛ الغلاف
يثبت/يحدث `baseer_native_spend` فقط ويرفض كل SHA غير المعتمد للشريحة الأولى.
يُضبط known_hosts بمفتاح ED25519 المفحوص من VPS، ويمنع حساب النشر كلمة المرور
والـTTY والـforwarding، ولا يملك docker group أو sudo آخر.

**التزامن ومنع التكرار.** lock على مستوى الخادم؛ اسم الإصدار يحمل SHA وrun id؛
وإعادة تشغيل نفس SHA تنتج إصداراً مستقلاً مع نسخة احتياطية جديدة بدلاً من
الكتابة فوق الإصدار الحالي.

**الفشل والرجوع.** قبل التبديل كل شيء قابل للفشل بلا أثر. بعد السكون تؤخذ
اللقطة والزوج الاسترجاعي، ثم بعد التبديل يعيد trap symlink السابق؛ وإذا بدأت
عملية أودو يعيد dump وfilestore المأخوذين في السكون.
لا يبتلع فشل الاسترجاع أو فحص الصحة؛ يسجل `ROLLBACK_FAILED` ويخرج بفشل واضح.
لا يحذف نسخاً قديمة تلقائياً؛ التنظيف سياسة منفصلة بعد مراجعة السعة.

## الشريحة التالية S2 — خريطة الإنفاق الأصلية

**الهدف.** تحويل تصنيف الموردين والمشتريات إلى خريطة أودو التحليلية الأصلية
القابلة للتدقيق، بحيث يحصل سطر فاتورة المورد على توزيع تحليلي صحيح قبل
ترحيله، ويستمد داشبورد المشتريات قراءته منه لاحقاً.

**مصدر الحقيقة.** خطة `تصنيف الإنفاق` وحساباتها التحليلية ونماذج التوزيع
التحليلي الأصلية في أودو. علامات تصنيف المورد هي مفتاح المطابقة عند غياب
الصنف؛ لا تصبح فئة مورد مخصصة ثانية ولا مصدر حقيقة موازٍ.

**حدود الشريحة.**

- تبنى شجرة مرجعية مشتركة من تصنيفات نوركس المعتمدة، ثم تنشأ لكل شركة
  الحسابات/النماذج الخاصة بها أو المشتركة بحسب عقد أودو.
- أولوية التوزيع هي: الصنف، ثم فئة الصنف، ثم المورد، ثم علامة تصنيف المورد.
  إذا أعطت العلامات المتعددة نتائج متضاربة، فلا يوجد اختيار صامت: يختار
  المستخدم التصنيف أو ينشأ نموذج أكثر تحديداً.
- لا يفعل الإلزام لشركة إلا بعد أن تملك شجرتها ونماذجها المعتمدة. عند التفعيل
  ترفض الفاتورة أو الإدخال الجماعي الترحيل من دون توزيع إنفاق كامل `100%`.
- الفواتير القديمة لا تعدل ضمن التهيئة؛ تبدأ بمعاينة ومصالحة ثم ترحيل منفصل
  قابل للمراجعة والعكس، للأسطر ذات المطابقة غير الملتبسة فقط.

**دليل البداية.** الجرد الحي أظهر خطة `تصنيف الإنفاق` وخمسة حسابات أوراق
حالياً وخمسة نماذج توزيع مرتبطة بموردين في الشركة النشطة؛ هذه تهيئة جزئية ولا
تمثل الخريطة الموحدة أو ترحيل الفواتير التاريخية.

### عقد S2 المقترح — G2

1. **الكتالوج.** شجرة نوركس هي كتالوج مُرقّم بإصدار، يتكون من خطط أبناء
   لحسابات الفئات الأم وحسابات تحليلية للأوراق. الحساب المشترك يحمل
   `company_id=False` ويخدم كل الشركات؛ الاختلاف الحقيقي فقط ينشئ override
   خاصاً بالشركة، ولا تنسخ الشجرة خمس مرات.
2. **المطابقة.** ينشأ نموذج توزيع أودو قياسي واحد لكل قاعدة معتمدة. داخل
   المستوى نفسه: الخاص بالشركة قبل المشترك؛ ولا يقبل التنفيذ نماذج مكررة أو
   متساوية تعطي أوراق إنفاق مختلفة. الترتيب بين المستويات ثابت: الصنف، فئة
   الصنف، المورد، علامة المورد. تعدد العلامات مقبول فقط إذا انتهت كلها إلى
   الورقة نفسها.
3. **المعاينة والجاهزية.** يسجل النظام run غير قابل للكتابة بعد اعتماده،
   ولقطة المورد/العلامة/الشركة/القاعدة/الورقة المقترحة والنتيجة
   (`resolved` أو `ambiguous` أو `unmapped` أو `conflict`). لا تصبح الشركة
   جاهزة إلا إذا كانت حساباتها فعالة، وجميع علامات مورديها لها نتيجة واحدة،
   والموردون بلا علامات لديهم قاعدة مورد صريحة، وتمر رحلة الفاتورة والإدخال
   الجماعي في QA.
4. **التفعيل.** لا يفعّل الإلزام إلا بعد وجود قالب مشترك مكتمل من حسابات
   تحليلية مشتركة ونماذج توزيع Odoo مرتبطة بالعلامات. بعد تهيئة هذا القالب
   وفحصه، ترث الشركة الجديدة حارس الترحيل عند إنشائها؛ لا تنسخ نماذج أو
   حسابات لكل شركة ولا تبقى الشركة الجديدة اختيارية بالخطأ. المورد بلا علامة
   أو متعدد الوجهات يبقى مسودة قابلة للحفظ، ويرفض الترحيل حتى يكتمل تصنيفه.
5. **التاريخ.** لا تكتب أي فاتورة مرحلة في S2. شريحة التاريخ اللاحقة تلتقط
   hash لكل سطر ومصدر القاعدة والمبلغ والحساب المقترح، وتقبل النتائج الواضحة
   وحدها ضمن run idempotent وسجل تراجع مثبت في QA؛ لا تمس القيود أو المبالغ.

**معايير قبول كود المعاينة.** يعرّف المفتاح الطبيعي للقاعدة صراحةً كـ
`(catalog version, company scope, selector kind, selector id)` ويرفض تكراره ولو اتفقت الورقة؛
المعاينة تنشئ سياق سطر للصنف/فئته/المورد/العلامة وكذلك سطر بلا صنف؛ وتبطل
الجاهزية إن اختلفت لقطة المورد أو علاماته أو الصنف أو فئته أو القاعدة أو
الحساب بعد run. اعتماد run أو تغيير الجاهزية محصور في مدير المحاسبة وسجله
ثابت. المورد الجديد بلا علامة لا يحصل على اختيار افتراضي.

**حالات تتطلب نتيجة معاينة لا تخميناً:** `فحم` (له سياقان في كتالوج نوركس)،
`تأمين طبي`، `مقدمو الخدمات`، `رسوم تطبيقات`، `فواتير نقدية صغيرة` والعلامات
الأم العامة. تعالج بورقة محددة أو قاعدة مورد/صنف أدق بعد ظهورها في المعاينة.

**G0–G4 (قيد المراجعة قبل التنفيذ).** طلب المالك مواءمة لوحة فواتير الموردين والمصروفات والتقويم الحراري بصرياً مع لوحات أودو الأصلية: مساحة محتوى متمركزة ومحددة العرض، خلفية صفحة بيضاء، بطاقات KPI فاتحة هادئة بنص داكن بدلاً من البطاقات المشبعة، ومسافات/زوايا متسقة. لا تتغير أي RPC أو مصدر بيانات أو حساب مالي أو صلاحية أو منطق الرسم أو تفاعل التقويم. يظل أودو وخلفية الموديولات مصدر الأرقام، وتبقى الأرقام الغربية وRTL/LTR كما هي.

## ATX1 — توحيد خريطة الحسابات التحليلية

## PBTP1 — ربط ترحيل الإدخال الجماعي بعلامة المورد

### الملخص التنفيذي

**الحالة: مرشح مُنفذ ومختبر محلياً، غير منشور للإنتاج.** لا تغيير حي في
الفواتير أو القيود أو الموردين ضمن هذه الشريحة حتى تاريخ هذا السجل. لا يجوز
تسميتها «جاهزة للنشر» قبل إكمال ملفات ترحيل العلامات المعتمدة لكل
شركة/علامة مستخدمة، ثم بروفة إصدار واسترجاع مستقلة.

### قبل التغيير

1. كان الإدخال الجماعي يطلب حقل **فئة** يختاره المستخدم على سطر الفاتورة.
   هذا الحقل يحدد المنتج الخدمي وحساب المصروف/تكلفة المبيعات المستخدمين عند
   إنشاء فاتورة المورد.
2. للمورد علامات تصنيف (`res.partner.category`) وتصل بالفعل إلى التحليل
   الأصلي في أودو عبر نماذج التوزيع التحليلي؛ وهذا البعد التقاريري لا يختار
   وحده منتج فاتورة أو حساب أستاذ عام.
3. توجد فئات منتجات/ملفات ترحيل خدمية في بصير (`baseer.purchase.category.map`)
   تربط فئة المنتج بمنتج خدمي وحساب صالح، لكن اختيارها الافتراضي على المورد
   كان حقلاً مخصصاً منفصلاً، ما خلق مصدر حقيقة ثانياً إلى جانب علامة المورد.
4. في الإنتاج وقت الجرد: توجد 26 خريطة فئة نشطة في كل شركة من الشركات
   المفحوصة، بينما حقل الافتراض القديم معبأ لسبعة موردين فقط. لذلك لا يمكن
   افتراض أن جميع الموردين مغطون به.

### السبب والقرار المعماري

**سبب المشكلة.** التحليلي في أودو يجيب عن سؤال: «إلى أي بُعد تقريري ينسب
السطر؟». أما فاتورة المورد فتحتاج أيضاً جواباً محاسبياً تنفيذياً: «أي منتج
خدمي وأي حساب مصروف/تكلفة تستخدم عند الترحيل؟». علامة المورد وحدها ليست في
أودو القياسي علاقة ترحيل مباشرة إلى المنتج والحساب.

**القرار.** تكون علامة المورد المصدر التشغيلي الواحد للاختيار، وتربط مرة
واحدة بملف ترحيل محكوم لكل شركة. الملف يعيد استخدام خريطة الفئة القائمة التي
تحتوي المنتج والحساب، بدلاً من نسخ الحسابات أو إنشاء مصدر ثالث. يبقى التحليل
الأصلي في أودو هو مصدر لوحة التحليل؛ ولا يجري تعديل قيود أو فواتير تاريخية.

```text
علامة المورد
  ├─ نموذج توزيع تحليلي قياسي في أودو → التقرير/اللوحة
  └─ ملف ترحيل علامة المورد (شركة + علامة، فريد)
         → خريطة فئة شراء قائمة
              → منتج خدمي + حساب مصروف/تكلفة صالح
                   → فاتورة المورد الجديدة عند الاعتماد
```

**ما هو خارج النطاق.** لا تغيير صامت لفاتورة مرحلة، ولا نقل تاريخي، ولا
تخمين حساب للأصول أو الإيجار أو الوقود أو الصيانة أو أي علامة لا توجد لها
سياسة حسابية معتمدة. هذه سياسات مالية وليست قراراً برمجياً.

## PBTP1-R1 — تصحيح التوصية بعد مراجعة إمكانات أودو الأصلية

**الحالة بتاريخ 2026-09-16: توصية PBTP1 السابقة مستبدلة بهذه المراجعة؛
الكود السابق محفوظ للدليل وغير معتمد للنشر.** طلب المالك إعادة التقييم بأقل
تخصيص والاستفادة من الربط التحليلي الموجود. هذا القسم إضافة تصحيحية للسجل؛
لا يلغي تاريخ ما نُفذ ولا يدعي تنفيذ البديل أو نشره.

### الدليل الذي غيّر القرار

- قراءة مباشرة من الإنتاج: 52 نموذجاً في `account.analytic.distribution.model`؛
  جميعها مرتبطة بـ`partner_category_id` ومشتركة (`company_id` فارغ)، ولا يوجد
  بينها شرط مورد أو منتج أو فئة منتج. هذه أعداد إعداد، وليست إثباتاً بأن كل
  مورد مغطى أو أن جميع فواتيره القديمة مصنفة.
- الإصداران الحيان المقروءان: `baseer_native_spend 19.0.1.3.0` و
  `baseer_purchase_batch 19.0.1.2.4`.
- مصدر أودو 19 في الحاوية الحية يؤكد أن `_compute_account_id` في
  `account.move.line` يستعمل حساب المنتج عند وجوده، وعند غيابه يستدعي
  `_get_most_frequent_account_for_partner`؛ ثم توجد بدائل منها حساب اليومية.
  لذلك إنشاء منتج خدمي وخريطة علامة ليس شرطاً أصلياً لإنشاء كل فاتورة مورد.
- فحص المصدر المحلي المطابق لهذا المسار أظهر أن اقتراح الحساب يعتمد على
  الاستعمال خلال سنتين وفي نطاق الشركة ونوع المستند. لا يشترط الاستعلام
  `posted` صراحةً، ويختار الأكثر تكراراً؛ فلا يجوز وصفه بأنه قرار محاسبي
  ثابت أو مضمون للمورد الجديد أو متعدد الأنشطة أو للأصول.
- `_compute_analytic_distribution` الأصلي يستعمل نموذج أودو مع المورد،
  علاماته، الشركة، المنتج/فئته إن وجدا، وبادئة الحساب. لا يشترط منتجاً لكي
  تنطبق قاعدة العلامة.
- مصدر دفعات بصير الحالي هو الذي يفرض `category_map_id` ثم يمرر منتجاً
  وحساباً صريحين عند إنشاء الفاتورة. هذه حاجة المسار المخصص الحالي وليست
  دليلاً على أن أودو يحتاج خريطة ترحيل إضافية.
- سجل المعمارية الرئيسي يحتوي بالفعل NBT-1: تجربة محلية سابقة لسطور
  الدفعات ذات حساب مصروف وتوزيع أصليين، دون منتجات مصطنعة. هي دليل تصميم
  سابق يستفاد منه، وليست النسخة الحية ولا ضمان توافق مع آخر إصدار.

### التوصية المصححة وأقل نطاق تغيير

1. إعادة استعمال نماذج التوزيع الأصلية الموجودة. لا إنشاء ربط تحليلي ثانٍ،
   ولا حسابات تحليلية مكررة ولا نسخ القواعد المشتركة لكل شركة.
2. عدم اعتماد جدول `baseer.purchase.tag.posting.map` الجديد كشرط للإطلاق.
   لا حاجة إلى إدخال مصفوفة علامة/منتج/حساب كاملة فقط للحصول على التحليل.
3. تكييف إنشاء الفاتورة في الإدخال الجماعي مع سطر أودو الأصلي بلا منتج
   للحالات التي لا تحتوي أصنافاً؛ الحساب المحاسبي ما زال مطلوباً ومستقلاً
   عن الحساب التحليلي. يستخدم اقتراح أودو مع إظهار الحساب للمراجعة عند
   الحاجة، وتصحيح الحالات غير المناسبة قبل الاعتماد. لا يستبدل ذلك مراجعة
   حسابات الفواتير التاريخية التي قد يعتمد عليها الاقتراح.
4. اختبار اختيار مورد مهيأ ثم إنشاء فاتورة مسودة في بيئة معزولة: وصول
   التوزيع الصحيح تلقائياً، صلاحية الحساب، المبلغ والضريبة، الشركة، وتغيير
   المورد. تضمين مورد جديد ومورد ذي تاريخ متعدد الحسابات. لا يكفي عدّ
   نماذج التوزيع لإثبات نجاح الرحلة.
5. إبقاء الروابط القديمة اللازمة للتاريخ، والحماية القائمة من نقص التحليل
   والتعارض وعزل الشركات. التخلص من أي تخصيص قديم منفصل يحتاج فحص أثره؛
   وجود آلية أودو الأصلية لا يعني أن نسخة بصير الحالية بلا امتدادات.

**النتيجة المتوقعة بعد تنفيذ البديل واختباره:** اختيار المورد يستفيد من
التحليل الأصلي الموجود ومن اقتراح الحساب الأصلي، دون خريطة مخصصة جديدة؛

وارتباطها بالإدخال الجماعي. الفرع النظيف `codex/native-batch-without-category`

### NBC1 — القرار الثابت وحدود التنظيف

أودو عادية بلا منتج أو حساب مفروض أو توزيع بديل. يعالج أودو الحساب والتوزيع،

الدفعة واعتمادها، خانة الفئة في القائمة والنموذج والجوال والطباعة، اختيار
الفئة الافتراضية في المورد وقائمة خرائط الإدخال. رفض إرسال فئة جديدة عبر

ولا يشغّلها هذا التغيير، ولا يشمل الطلب إعادة هندسة خدمات الموظفين.

## HRN1 — خدمات الموظفين على المسار الأصلي لأودو

### G0 — عقد البناء وخريطة الدورة — معتمد للتصميم

**الهدف:** إزالة اعتماد `baseer.hr.service` على
`baseer.purchase.category.map` عند احتساب واعتماد فواتير الخدمات، مع إبقاء
دقة حساب المصروف بحسب نوع خدمة الموظف والتوزيع التحليلي بحسب المورد.

**المسار المباشر المختار:**

`خدمة الموظف + نوع الخدمة → منتج أودو الخدمي المزروع لنوع الخدمة →
account.move.new (حساب/يومية أودو) + account.analytic.distribution.model
للمورد → فاتورة مورد مرحلة`.

المنتج ليس «خريطة شراء»: هو سجل Odoo أصلي يملك حساب مصروف الخدمة. المورد
وعلاماته يحددان التوزيع التحليلي عبر نموذج أودو الموجود. لا يُمرر حساب أو
توزيع يدوي في الإنشاء، بل يُعاين حساب أودو ويتحقق منه قبل الكتابة.

**سبب عدم اختيار فاتورة بلا منتج:** مقدم واحد مثل الجوازات قد يقدم إقامة
وتأشيرة. اقتراح حساب أودو من تاريخ المورد وحده لا يميز هاتين الخدمتين؛
المنتج الأصلي هو أقصر مصدر دقيق لحساب المصروف بحسب نوع الخدمة، ويبقى
التحليل مستقلاً عن الحساب.

**نطاق التغيير:** الحساب، الحسابات التحليلية، شاشة/حقل الخريطة الداخلي،
seed الجديد، اختبارات خدمات الموظفين، والترجمة/التوثيق. خارج النطاق: حذف
فواتير أو قيود مرحلة، إعادة توزيع تاريخي، تغيير إعدادات التحليل الحية،
وسياسة ضرائب أو رواتب أو خصومات. تبقى خرائط الفئات المسجلة تاريخياً حتى
تُنقل حماية تصحيح الفواتير القديمة في عملية مستقلة.

**الدورة والرقابة:** HR ينشئ مسودة؛ مدير HR ذو صلاحية فواتير مورد يعتمدها؛
الخلفية تتحقق من الموظف/الشركة/المورد/الضريبة/المنتج والحساب، وتنشئ فاتورة
واحدة ثم ترحلها داخل savepoint؛ تصبح الخدمة والفاتورة غير قابلتين للتعديل
إلا بعكس/تصحيح Odoo الأصلي. الدفع يبقى Odoo الأصلي. فشل الحساب أو التحليل
أو الفترة المقفلة يرجع العملية بلا فاتورة جزئية. لا تتغير الفواتير السابقة.

**معايير القبول:** الخدمة الجديدة لا تقرأ أو تكتب خريطة فئة؛ المنتج المحدد
يتوافق مع نوعها ويقود حساب مصروف أودو صالحاً؛ تغيير المورد يعيد التوزيع
التحليلي عبر النماذج الأصلية؛ فشل الإعداد واضح وذري؛ خدمة/فاتورة تاريخية
تبقى قابلة للعرض؛ لا يدخل حساب مالي أو توزيع من العميل؛ العربية/الإنجليزية
والجوال لا يظهران حقلاً ميتاً.
