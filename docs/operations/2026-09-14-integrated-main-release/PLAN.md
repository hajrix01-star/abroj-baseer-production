# خطة الإصدار الموحّد: تحديث الموديولات + ترحيل نوركس إلى الأصل

## النتيجة النهائية

تشغيل `baseer_dev` بمرشح كود واحد مثبت ومراجع، مع بيانات نوركس المطابقة للمصدر. لا تُنسخ قاعدة QA أو filestore QA أو معرفات QA إلى الأصل مطلقاً.

## القرار التقني

المسار الأقصر والأقل مخاطرة هو: **كود مرشح موحّد → rehearsal جديدة من لقطة الأصل → replay مصدر-only → مطابقة مستقلة → ترقية زوج rehearsal DB/filestore المتطابق**. إن تغيرت بصمة الأصل قبل القطع، تعاد rehearsal من لقطة الأصل الجديدة؛ لا يرحّل clone قديم.

## ضوابط لا يمكن تجاوزها

- الأرقام `Decimal` من المصدر ثم HALF_UP إلى منزلتين عند كتابة Odoo.
- الضريبة من `source_tax_raw` فقط؛ المبلغ شامل VAT عند وجودها.
- كل شركة/شهر عملية ذرية؛ لا تشغيل متوازٍ لنفس الموجة.
- أي مرجع صفر/متعدد، قيد غير متزن، فرق مبلغ/عدد، أو فشل ترقية موديول يوقف الموجة فقط ويعيد rehearsal/المعاملة؛ الأصل لا يتغير.
- لا stock moves أو quants من البيانات التاريخية، ولا نسخ لطلبات/منتجات/فواتير QA الاختبارية.
- قبل وبعد القطع تؤخذ لقطة متماسكة: DB + filestore + candidate code. لا restore جزئي ولا uninstall مالي كوسيلة رجوع.

## بوابات الفريق

تفتح G0–G3 لترقية الموديول لأنها تغير مخطط البيانات والمرشح، ثم G5 لترقية rehearsal، G6 لقياسها، G7 للموجات، وG8 لمراجعة تسليم Alpha Delivery. تظل بوابات replay السابقة دليلاً لبيانات نوركس، لكنها لا تغني عن مراجعة مرشح الكود الجديد.

## ما يراه المستخدم بعد النهاية

- شاشة طلبات مشتريات سريعة محدثة، إضافة منتج شراء سريع، المفضلة والأكثر استخداماً.
- شركات وموردون موحدون وتصنيفات صحيحة.
- تاريخ المبيعات والمشتريات والرواتب والسلف ظاهر داخل أودو وقابل للتدقيق.
- تقرير مطابقة نهائي يمكن الرجوع إليه قبل فتح النسخة الأصلية.
