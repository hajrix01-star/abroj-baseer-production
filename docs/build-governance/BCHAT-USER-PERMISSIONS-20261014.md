## G0 — عقد البناء المعاد فتحه

- طلب المالك أن تُدار صلاحيات كل قسم حالي ومستقبلي من صفحة المستخدم في أودو، لا بتعديل أسماء الأدوار في الكود أو إخفاء الأزرار فقط. حسم صراحةً فصل «إنشاء وإرسال الطلب» عن «تأكيد الاستلام»، مع عرض الطلبات خيارًا مستقلًا.
- الخيارات الحالية المقترحة في قسم BChat واحد: عرض المحادثات، إرسال الرسائل، استخدام الوسائط (صور/صوت/ملفات)، إنشاء المجموعات، إدارة المجموعات المخوّل بها، عرض المهام، إنشاء/تحديث المهام المخوّل بها، عرض الطلبات، إنشاء/إرسال الطلب، تأكيد الاستلام، وإدارة غرف BChat العامة. لا تعني صلاحية القسم تجاوز عضوية الغرفة أو صلاحية الشركة أو ملكية المهمة؛ إدارة المجموعة المعينة تتطلب أيضًا دور مشرف داخلها.
- الأدوار المؤهلة لكتابة طلب/استلام تبقى `owner` و`cashier` و`pos_cashier` فقط، لكن منح كل إجراء مستقل في خانة المستخدم؛ مندوب المشتريات يقرأ رسالة الغرفة بعضويته ولا يرث قسم الطلبات. لا تتغير الأسعار/المخزون/المحاسبة أو سياسة ترحيل مستندات أودو بهذا التنظيم.
- نجاح القبول: خانات واضحة AR/EN في صفحة المستخدم؛ سحب كل خانة يمنع API المعني قبل `sudo` ويخفي/يعطل القسم أو الزر في Android بلا فشل دخول؛ بقاء كل وصول قائم للمستخدمين الحاليين حتى يغيّره المسؤول؛ عدم تسرب snapshot أو cache محلي بعد سحب صلاحية؛ بقاء إذن الشركة/العضوية شرطًا إضافيًا. لا نشر QA/Live في مرحلة التصميم والبناء المحلي.

## G1 — حجم الاستخدام والاستمرارية

- قاعدة BChat المحلية: 8 شركات و7 طلبات BChat (3 قابلة للاستلام)، ولا يوجد قياس لحجم استخدام أوسع. إضافة حقول صلاحية صغيرة إلى المستخدم ورد قدرة صغير لا تبرر cache أو خدمة مستقلة أو اختبار حمل شامل. احفظ فحص الصلاحية منخفض الكلفة في مسار الجلسة، واختبر تبديل الحق أثناء تشغيل التطبيق دون إعادة تسجيل دخول.
- أخطر تزامن هنا سحب الصلاحية مع طلب جارٍ أو محادثات محفوظة بلا إنترنت؛ الخلفية تحسم الطلب عند التنفيذ، والعميل يمسح/يحجب عرض البيانات المحلية الخاصة بالقسم المسحوب بعد أول مزامنة موثقة. لا تعد بإبطال فوري أثناء انقطاع الجهاز عن الشبكة؛ يجب توثيق هذا الحد الأمني بوضوح.

## G2 — حدود الملكية والعقود (مقترح للمراجعة المستقلة)

- يملك `baseer_bchat` خيارات المحادثة/الوسائط/المجموعات/المهام العامة على `res.users`، وتضيف `baseer_bchat_procurement` خيارات عرض/إنشاء/استلام الطلب إلى المجموعة نفسها في نموذج المستخدم. كل خيار محفوظ لكل مستخدم ويدرجه المسؤول فقط؛ backend يقرأه بعد تحقق الجلسة ولا يثق بعلم من Android. كل موديول BChat مستقبلي يضيف خيارًا وشرط API واختبار عقد في الموضعين نفسيهما، لا سجلًا ديناميكيًا أو `sudo` عامًا.
- الخيارات الحالية المعتمدة على `res.groups` تُنقل تدريجيًا دون فقد صلاحية: إظهار القيمة الحالية للمستخدم ثم seed صريح آمن لخانات الطلبات/إدارة الغرف من المجموعات القائمة. عند تغيير الدور لا تمحو إعادة تعيين `group_ids` الخيارات المحفوظة؛ يبقى الدور المؤهل شرطًا إضافيًا لعمليات ERP. لا تمنح خيارات كتابة جديدة تلقائيًا لمن لم يكن مخولًا قبل الترحيل.
- لا تُغيَّر بنية `bootstrap` القديمة بكسر المستهلك: قدرة إصدار جديد/عقد إضافي يتضمن الأعلام الفردية؛ Android الجديد يتعامل مع true/false، والقديم يبقى متوافقًا للحقوق غير المسحوبة. عند السحب يرفض الخادم كل مسار كتابة/قراءة مناسب ويرشح change snapshot والصفحات، لا يكتفي بإخفاء تبويب. خصوصية الغرف والشركات والمهام أصلية ولا تستبدلها خانة عامة.
- الطلبات: `view` يحرس قائمة/تفاصيل/خيارات العرض، `create` يحرس الكتالوج/quote/إنشاء/إعادة إرسال المسموح، `receive` يحرس قائمة/تفاصيل/تأكيد/مشاركة نتيجة الاستلام. إنشاء أو استلام يتطلبان أيضًا تفعيل العرض؛ ترفض صفحة المستخدم تركيبًا متناقضًا بدل منح عرض خفي. يمكن منح الإنشاء دون الاستلام أو العكس. تبقى عمليات stock والـUUID في أودو وحده.

### مصفوفة الحراسة الملزمة قبل أي `sudo`

| خيار المستخدم | قراءة/API | كتابة/API | المزامنة والذاكرة | شرط إضافي |
| --- | --- | --- | --- | --- |
| عرض المحادثات | `GET /rooms`, `/rooms/{id}/messages`, معلومات المجموعة/الصورة/المرفق | إيصال القراءة/التسليم بعد القراءة | أحداث room/message/receipt وsnapshot الغرف؛ امسح تاريخ الغرف والوسائط المحفوظة عند رصد السحب | الشركة وعضوية الغرفة/حقبة الانضمام |
| إرسال الرسائل | لا يمنح قراءة وحده | `POST /rooms/{id}/messages`, وإرسال طلب إلى غرفة أو مشاركة ملخص استلام | outbox المعلّق لا يُعاد إرساله بعد السحب؛ يبقى قابلًا لمراجعة/حذف محلي | يتطلب عرض المحادثات وعضوية الغرفة |
| الوسائط | `GET /media/...` مع عرض المحادثة | upload؛ الإلغاء للرفع المرحلي مسموح حتى بعد السحب لتجنب أصل يتيم | امسح media cache المحفوظة عند السحب، وامنع إعادة إرسال الوسائط | عرض المحادثات؛ company/room/media-owner |
| إنشاء مجموعة | قائمة مرشحي الأعضاء المناسبة | `POST /rooms` | لا أحداث كتابة خاصة | عرض المحادثات وشركة مشتركة مرخصة |
| إدارة مجموعة | معلومات المجموعة والأعضاء | تغيير الاسم/الوصف/الصورة/الأعضاء عبر group API | لا يمنح تاريخ رسائل غير عضوية | عرض المحادثات و`is_group_admin` الحالي؛ الإدارة العامة القديمة منفصلة |
| عرض المهام | options/list/detail | لا شيء | أحداث task/task_revoked وsnapshot المهام؛ إزالة cache عند السحب إن وجدت | شركة/غرفة/تعيين المهمة الحالي |
| إنشاء/تحديث المهام | لا يمنح قراءة وحده | create/transition بالقيود الأصلية | لا يحق replay بعد السحب | عرض المهام وcreator/assignee والعضوية |
| عرض الطلبات | `GET /orders?scope=all`, detail, unscoped `/orders/options` | لا شيء | أحداث order وsnapshot الطلبات؛ محو cache المحفوظة عند السحب | شركات المستخدم، BChat source فقط |
| إنشاء الطلب | catalog/quote/options الخاصة بشركة، صورة الصنف، تفصيل إعادة الإرسال | `POST /orders` | UUID يبقى معلقًا فقط للمراجعة ولا يُعاد بعد سحب الحق | عرض الطلبات + دور ERP مؤهل؛ مع `room_id` يلزم إرسال الرسائل |
| تأكيد الاستلام | receipts list/detail | confirm/share | UUID الاستلام يُمنع replay بعد السحب؛ لا تُعاد حركة المخزون | عرض الطلبات + دور ERP مؤهل؛ share يحتاج إرسال الرسائل |
| إدارة غرف BChat العامة | إعدادات الربط فقط | binding/room/membership/storage administrative services | لا يفتح محتوى غرفة دون عضوية | admin الأصلي + `group_bchat_manager`، مستقل عن group admin |

`_v2_lock_room` حد مشترك، فلا توضع فيه حراسة `chat_view` عمياء تكسر إنشاء الطلب والمهام؛ كل مدخل service عام يحرس القدرة الخاصة به قبل الولوج. `GET /changes` يرد تلميح سحب الحق/تنظيفه حتى عندما تُحجب أحداث القسم، ولا يرد payload غرفة أو مهمة أو طلب مسحوب. snapshot القسم المسحوب يرجع 403 من دون بيانات، مع استثناء تلميح تطهير آمن. لا يجوز لـAndroid تفسير 403 لصلاحية قسم على أنه انتهاء جلسة عامة.

### مصدر الحقيقة والترحيل والتوافق

- المصدر الجديد حقول Boolean محفوظة على `res.users` لكل خيار. حقول core تُفعّل افتراضيًا للمستخدم الداخلي كما كان الوصول قبل التغيير؛ لا تفعّل للمستخدم الخارجي. خيار الإدارة العامة يحتفظ بقيد admin والمجموعة الأصلية. عند ترقية procurement يُنفّذ post-migration idempotent مرة واحدة: المستخدم الداخلي بدور owner يصبح `view=true` فقط حتى لو حمل مجموعة operator القديمة؛ صاحب دور cashier/pos_cashier ومجموعة operator القديمة يصبح `view/create/receive=true`؛ الآخرون false. لا تُستنتج الكتابة من الدور وحده. المستخدمون الجدد بعد الترقية يبدأون بخيارات الطلب false، ويضبطها المسؤول صراحة. إعادة ضبط `group_ids` عند تبديل الدور لا تمحو الخيارات المحفوظة، لكن دور ERP غير المؤهل يمنع تنفيذ الإنشاء/الاستلام حتى لو بقيت خاناته true؛ يظهر هذا في الواجهة بوضوح.
- `bchat_can_order` القديم يبقى حقل توافق مشتقًا/مخفيًا دورة واحدة ولا يكون مصدر تفويض. الاختبار يقارن مصفوفة حقوق المستخدمين قبل/بعد الترقية في قاعدة معزولة ثم يثبت سحب `view` أو `create` أو `receive` كلًا على حدة، بما فيه مستخدم owner viewer ومندوب مشتريات بلا قسم.
- لا تغيّر `capabilities` داخل bootstrap v2 القديم؛ `verifyV2` في APK المنشور يرفض اختلافها. أضف `permissions` على المستوى الأعلى مع `version=1` و`revision` عددي متزايد؛ APK الجديد يقرأها بعد التحقق ويطهّر cache عند السحب. نوع حدث `kind=permissions` جديد، وAPK القديم يرفض الأنواع المجهولة: لا يرسله الخادم إلا إذا أعلن العميل `permissions_version=1` في GET `/changes`، وبدون ذلك يتقدم المؤشر ويحجب الحدث. APK الجديد يعيد جلب bootstrap عند هذا hint وعند resume. APK القديم يتجاهل الحقل الإضافي ويُرفض خادميًا في المسارات المسحوبة، وقد يظهر له زر يفشل إلى أن يُحدَّث. أثناء انقطاع الشبكة لا يمكن معرفة سحب جديد؛ لا يُعد هذا إبطالًا فوريًا للجهاز دون اتصال.
- يتطلب الرجوع إلى خادم أقدم بعد تثبيت APK v50 إرجاع APK متوافق أيضًا أو إبقاء عقد `/changes?permissions_version=1` في الخادم؛ لا تُجرى إعادة خادم منفردة بينما عميل v50 يعمل، لأن المزامنة الحية ستفشل.
- يضيف موديول procurement إلى `permissions` أعلى bootstrap المفاتيح `order_view/order_create/order_receive` إن كان مثبتًا، كي يظهر تبويب الطلبات بلا انتظار استعلام خيارات الشركة؛ غيابها يعني false. `/orders/options` غير المحدد بالشركة يرد `can_view/can_create/can_receive` مستقلة أيضًا للخيارات المتاحة. القيمة القديمة `access=operator` فقط إذا اجتمع الحقان الكتابيان، و`viewer` عند العرض دون اجتماعهما حتى لا يفعّل APK القديم زرًا لا يملكه؛ APK الجديد يستخدم الأعلام الثلاثة ولا يعتمد `access`. `options?company_id` يحتاج create لأنه يحمل المستودعات والكتالوج. قائمة الاستلام تحتاج receive؛ قائمة كل الطلبات تحتاج view. إذن الشركة/العضوية/الدور يُفحص في الخدمة قبل `sudo` لكل مسار.
- امتدادات BChat المثبّتة جزء من حدود الصلاحية أيضًا: inbox الإشعارات وتفاصيل رسالة الغرفة وحالات الفواتير في OCA DMS لا يجوز لها إعادة محتوى أو اسم مرفق بعد سحب `chat_view`/`media`، ولا إرجاع وجهة مهمة بعد سحب `task_view`. استثناء المندوب المعيّن لطلبه ليس صلاحية «قسم الطلبات»: وجهة `representative_order` وتفاصيلها تشترط `chat_view` ثم تحقق هوية المندوب وشركته في الامتداد الأصلي، وتظل قائمة الطلبات محجوبة بلا `order_view`. حارس الإشعارات مستقل عن تركيب مستندات BChat؛ حارس الفواتير يُفعّل فقط بوجودهما، مع إبقاء فحص العضوية والشركة الأصلي في `super`.
- يمتد inherited view الأساسي من `baseer_bchat` داخل صفحة المستخدم؛ procurement يضيف حقوله في مجموعة BChat الموجودة باعتماد manifest معلن، لا ينشئ مجموعة ثانية. اختبر combined view في قاعدة مثبت بها الموديولان، بالعربية والإنجليزية، وعلى عرض ضيق. لا يضيف هذا إذن أودو عامًا لـ`ir.attachment` أو `stock`.

## G3 — أقصر تنفيذ قابل للصيانة

- أعد استخدام Android Java وموديولات Odoo الحالية؛ لا مكتبة جديدة. صفحة المستخدم BChat هي سطح الإدارة الواحد، مع حقول مملوكة للموديول المختص ومجموعة عرض واحدة. لا تبنِ محرك صلاحيات عام أو خدمة منفصلة من أجل ثلاثة أقسام.
- نفّذ على شريحة واحدة ثم وسّع: حقّا الطلب المستقلان واختبارات مالك/مدير/كاشير/مندوب وشركتين؛ ثم المحادثات/المجموعات والمهام/الوسائط مع فحص API وAndroid وoffline؛ ثم ترقية قاعدة اختبار معزولة وحفظ الصلاحيات السابقة. APK موحد للهاتف والمحاكي بعد نجاح العقود. الخادم المحلي فقط بعد مراجعة تسليم مستقلة ونسخة احتياطية؛ QA/Live يحتاجان مسار نشرهما المعتمد وقرارًا منفصلًا.

## G5–G8 — دليل القبول المطلوب قبل تحديث أي خادم

1. فحص ترقية قاعدة معزولة: مصفوفة قبل/بعد لكل مستخدم ذي دور owner أو cashier أو pos_cashier أو مندوب/موظف عادي؛ عدم منح write جديد، وبقاء owner viewer. تغيير preset الدور بعد الترقية لا يمحو الخانات المحفوظة، لكن يمنع الدور غير المؤهل الإجراء.
2. فحص `view` فقط و`create` فقط مع view و`receive` فقط مع view و`create+receive` في شركتين؛ رفض كل endpoint غير مأذون قبل `sudo`، بما في ذلك image/catalog/quote/order replay/receipt replay/share/options/snapshot/events.
3. فحص حجب محتوى room/task/order من change feed وsnapshot بعد سحب الحق؛ وصول hint تطهير بلا محتوى، وعدم ظهور بيانات شركة أو غرفة غير مخولة. اختبار قرار 403 الخاص بقسم واحد دون إسقاط جلسة Android كاملة.
4. فحص محاكي/جوال على APK من المصدر نفسه: تبديل الخانات أثناء الجلسة ثم resume يحدّث التبويبات ويمسح تاريخ/وسائط cache الممنوعة، ويبقي تاريخ المحادثة المسموح offline. يراجع مسؤول التسليم حد عدم إمكان سحب حق من جهاز منقطع كليًا.
5. فحص APK قديم مقابل الرد الإضافي: لا يفشل `verifyV2` ولا يكتسب حق create أو receive بعد سحبه؛ اختبار RTL/LTR وعرض مستخدم أودو ضيق ومجموعة BChat واحدة.
6. لا يُعاد فحص حمل نظام الطلبات الكامل دون فرق في query plan أو حجم الاستخدام؛ قياس هذه الإضافة يركز على زمن bootstrap/options وحقول صلاحية صغيرة في قاعدة معزولة. منع الاختبارات على QA/Live إلا بتفويض منفصل.
