## الواجهة والطباعة والسعة

راجعت بصريًا قائمة الرواتب ونافذة التصحيح النهائية على الكمبيوتر ولقطة الجوال 390×844. الحقول والسبب وإقرار المراجعة والإجراء واضحة، وأُغلقت ملاحظة تعريب الحقول الخمسة. صور القبول هي `ui-payroll-correction-final.png` و`ui-payroll-mobile-final.png`؛ الصور السابقة سجل اكتشاف فقط. [UI-REVIEW.md](UI-REVIEW.md) يربطها بالأرشيف النهائي.

راجعت خمس عينات PDF مستقلة: كشف راتب مصحح عربي وإنجليزي، وبيان سداد معلق عربي، وبيان دفع مختلط إنجليزي، ومخالصة EOS عربية. القيم والحالة والتوقيع مقروءة دون قص ظاهر؛ الأصل 2950 والتعديل 25.55 والصافي 2975.55 واضح، والمعلق 3100 منفصل عن المدفوع صفر. مالك الرواتب راجع 22 صفحة في 12 ملفًا وفق `payroll-runtime/payroll-pdf-manifest.json`. هذه مراجعة عينات محددة وليست اختبارًا لكل تقرير أو جهاز.

السعة المثبتة محليًا: 50 موظفًا، توليد 1.099 ثانية وترحيل 6.236 ثانية مع 50 قيدًا متوازنًا؛ ودفعة 50 فاتورة في نحو 5.007 ثانية. تحقق هدف الجولة، ولا يمثل ذلك ضمانًا لكل حمل أو لحجم شركات غير محدود. مرجع النمو والاحتفاظ وهدف الاستعادة المحلي هو عقد G1 في [FA2-REMEDIATION.md](../../build-governance/FA2-REMEDIATION.md).

## التشغيل والحفظ وحدود الحكم

طابقت بصمات نسخ QA وقاعدة الأصلية ومرفقاتهما وأرشيف المحرك قراءةً من الملفات. [clones.json](clones.json) و[main-restore-result.json](main-restore-result.json) يوثقان الاستعادة إلى قواعد معزولة؛ استعادة نسخة الأصلية نحو 100 ثانية، وتجهيز نسخ QA نحو 231 ثانية إجمالًا. `core-filestore-result.json` يثبت 792 محتوى مرفق مميزًا بلا ملف مفقود أو checksum مخالف. هذه أزمنة محلية وليست SLA؛ RPO هو snapshot المحفوظ.

[main-projection-result.json](main-projection-result.json) يحفظ الأعمدة والمعرفات القديمة مع فصل إضافات schema والتهيئة. كانت جداول حسابات الأصلية فارغة، لذا حفظها لا يثبت وحده ترقية تاريخ مالي غير فارغ. فروق master على نسخة الأصلية اقتصرت على `write_date/write_uid` كما يوثق [main-metadata-diff.json](main-metadata-diff.json). الأصلية الحية مطابقة لبصمتها السابقة ولم تُنقل.

لم تبق QA الحية ثابتة بالكامل أثناء العمل: أضيفت أربعة مسيرات وتغيرت بصمات بعض سجلات master، مع ثبات جداول الحسابات المقاسة. هذا موثق في [live-preservation-before-qa-update.json](live-preservation-before-qa-update.json) ولا أنسب سببه لأحد. لذلك يتطلب تطبيق QA نسخة جديدة متماسكة بعد إيقاف الكتابة. راجعت `update-qa.py`: يقارن كل أعمدة الأعمال القديمة ومعرفاتها وعدد السجلات المالية، ويفصل فقط `write_date/write_uid` في سجل metadata مستقل؛ لا يستثني مبلغًا أو حسابًا أو تاريخ ترحيل أو شريكًا أو حالة أو رابطًا ماليًا. عند فشل الترقية أو الحفظ يبقى التشغيل متوقفًا للمعالجة.

[دليل النقل والرجوع](TRANSFER-RUNBOOK.md) يحدد المصدر والمحرك غير المتغيرين ونسخة جديدة للأصلية قبل نافذة نقل مصرح بها، واستعادة قاعدة البيانات والمرفقات والمصدر والإعدادات السابقة كمجموعة واحدة. لا تنقل fixtures أو نسخة QA فوق الأصلية، ولا تجري استعادة جزئية لجداول أو حذف إضافات بدل الرجوع الكامل.

حدود القبول: SAR ودقة منزلتين، والسياسات والسيناريوهات الموثقة، و50 موظفًا و50 فاتورة وطلبان متزامنان. سياسة EOS الجديدة ميلادية بتأكيد مراجع وليست شهادة قانونية لكل عقد؛ المستندات التاريخية لا يعاد حسابها تلقائيًا. التصحيح لا يرسل حوالة ولا يثبت استردادًا نقديًا فعليًا. WPS/GOSI والعملات الأجنبية وكل تقارير المورد والوظائف غير المتأثرة ليست ضمن شهادة القبول هذه.

**الموانع المفتوحة ضمن النطاق: لا توجد.** نتائج تطبيق QA والتنظيف اللاحق تضاف كأدلة تشغيل، ولا يحول هذا القرار جاهزية المصدر إلى ادعاء نقل الأصلية فعليًا.

## ملحق قبول التشغيل المستقل — تطبيق QA الفعلي

**الحكم: GO لتشغيل QA بعد الترقية المنفذة.** راجعت أدلة التنفيذ والتحقق اللاحق قراءةً، دون تعديل التطبيق أو تشغيل اختبارات قاعدة بيانات جديدة. بقي المصدر عند commit `4f5d0ff133f4b32fd8ca01b957490b20dba38326` والأرشيف `c8843337ffabea086892c1defe995032ea7f7c17be7592b60c0abf12df71d3e5`، كما يثبت [candidate-deployment.json](candidate-deployment.json). هذا الملحق لا يغير استقلال مراجعة شريحة SECURITY التي اعتمدها root، ولا يصرح بنقل MAIN.

نجحت الترقية، ثم أوقف حارس الحفظ إعادة الفتح عند اختلاف أربع قيم أصلية من `account_move.is_manually_modified`. كان التوقف صحيحًا؛ لم تُتجاهل الفروق تلقائيًا. راجعت [التحقيق](qa-upgrade-projection-investigation.json) و[نتيجة التنفيذ](qa-update-result.json) ومنطق `finish-qa.py`: يثبت أولًا تطابق بصمة الصورة السابقة في نسخة security مع baseline QA الجديد مباشرة قبل الترقية، ثم يقارن كل عمود أعمال أصلي على المعرفات الأصلية وعدد صفوف كل جدول `account_*`. يسمح فقط بالصفوف والانتقال الآتيين، ويتحقق من النوع والحالة وملكية مصدر POS المعتمد:

| معرف القيد | مصدر POS | النوع والحالة | الفرق الأصلي المقبول |
|---|---|---|---|
| 646 | 82 — approved | entry / posted | is_manually_modified: false → true |
| 647 | 82 — approved | entry / posted | is_manually_modified: false → true |
| 805 | 288 — approved | entry / posted | is_manually_modified: false → true |
| 811 | 289 — approved | entry / posted | is_manually_modified: false → true |

تحققت من دلالة الحقل في مصدر المحرك التنفيذي المثبت، لا من نسخة Odoo المحلية المفترضة: `account/models/account_move.py:3964–3965` يضع العلم عند كتابة ORM غير فارغة ما لم يرد سياق التخطي. ترحيل `baseer_pos_summary/migrations/19.0.1.4.0/post-migrate.py:7–11` يكتب رابط ملكية المصدر عبر هذا المسار. الاستخدام القرائي الذي عُثر عليه في إضافات المحرك المثبتة، `account_move.py:5911–5930`، يضبط اقتراح الترحيل التلقائي للمستندات الشرائية المستوردة؛ القيود الأربعة من نوع `entry` فلا تنطبق عليها هذه الأهلية. لم يظهر استخدام مالي مخصص لهذا العلم في الإضافات المحلية.

أقبل هذا الفرق الإداري المحدد وحده: **لم تتغير بقية أعمدة الأعمال الأصلية أو المبالغ أو تواريخ الترحيل أو الحالات أو الروابط المالية، ولم تنشأ معاملات محاسبية جديدة.** تغيرات `write_date/write_uid` موثقة منفصلة في `account_move` و`hr_payslip`. لا يعني القبول تطابق جميع بتات الصفوف الأصلية، ولا يجيز استثناء هذا الحقل عالميًا أو على الفواتير. إرشاد [دليل النقل](TRANSFER-RUNBOOK.md) صحيح: أي اختلاف لاحق يحتاج baseline جديدًا وتصنيفًا مستقلًا قبل إعادة الفتح، ولا تعاد استخدام معرفات QA أو `finish-qa.py` على MAIN.

بعد إعادة فتح QA، راجعت [qa-post-verify.json](qa-post-verify.json) و`verify-qa.py`: نجح 20/20 تحققًا قرائيًا مع rollback، وإصدارات الإضافات الثلاث المتغيرة صحيحة، ولا عمليات إضافات معلقة، ونماذج عربية صالحة وتسميات التصحيح الأربع صحيحة، ومعالج تقرير المساهمات موجود، والقيود المرحلة متوازنة. أعادت صفحة الدخول HTTP 200، وبقيت MAIN مطابقة لخط أساسها. هذه فحوص تشغيل لاحقة محددة، وليست إعادة لجميع اختبارات التصحيح أو شهادة لكل وظائف النظام.

[clone-cleanup.json](clone-cleanup.json) يثبت حذف النسخ الاختبارية الخمس ومرفقاتها وإيقاف خدمة المراجعة، مع الاحتفاظ بأرشيفات المصدر والنسخ الاحتياطية. **لا موانع تشغيل مفتوحة لـQA ضمن النطاق المقبول؛ MAIN لم تُنقل.**
