# ABROJ-PROJECT-STUDY-TREE — دراسة المشروع الهرمية

## عقد البناء

**الهدف:** تحويل «دراسة المشروع» في `abroj_project_costing` من قائمة بنود مسطحة إلى شجرة نطاق عمل: مكان/حزمة رئيسية (مثل المطبخ) ← أقسام فرعية (سباكة، كهرباء) ← بنود مسعرة. يحتفظ كل بند مسعر بنوع عمل مستقل للتقرير العابر للمواقع.

**قرار تجربة الواجهة:** تنفّذ التجربة أولاً داخل تبويب «دراسة المشروع» الحالي وعلى QA، وتستبدل قائمة هذا التبويب بالواجهة الجديدة؛ لا تنشئ نسخة بيانات أو موديولًا تشغيليًا ثانيًا. الرجوع يعيد إصدار الواجهة السابقة من الفرع/نسخة QA، من دون مساس ببيانات المشروع أو الدفعات أو السندات.

**المستخدمون:** مدير ومستخدمو تكاليف المشاريع في الشركة المختارة فقط.

**ضمن النطاق:**

- إنشاء أقسام رئيسية وفرعية قابلة للطي وفتحها في دراسة المشروع.
- ربط بند الدراسة الأب/الابن والتحقق من عدم الدورات أو عبور المشروع/الشركة.
- حساب التقديري والفعلي والانحراف في الخلفية: الورقة مصدر التكلفة، والأصل يجمع الأبناء.
- اختيار موقع رئيسي ثم بند فرعي متوافق في التكلفة الفعلية، مع بقاء الرابط الدقيق إلى بند الدراسة.
- تقرير تجميعي حسب نوع العمل (مثل «كهرباء») عبر كل أماكن المشروع.
- استيراد/تصدير يحفظان مسار الشجرة، مع استمرار قبول ملف الاستيراد الحالي المسطح.
- ترحيل آمن: البنود الحالية تبقى أوراقاً جذرية؛ لا يغيّر الترحيل مبلغاً أو فاتورة أو دفعة.
- تبدأ كل دراسة مشروع جديدة بلا أب أو قالب أو أقسام مهيأة مسبقاً؛ ينشئ المستخدم الأب داخل المشروع نفسه.

**خارج النطاق:** القيود المحاسبية، دفعات العميل، الاتفاقية، المخزون، شراء الموردين، أو تعديل موديولات أودو الأصلية.

**معايير القبول:**

1. يمكن للمستخدم إنشاء «المطبخ» ثم «سباكة» ثم بنود مسعرة تحته، وطيّ/فتح القسم في شاشة الدراسة.
2. لا تقبل الخلفية ربطاً دائرياً، ولا ابناً من مشروع أو شركة أخرى.
3. مجموع كل عقدة يعرض مجموع أوراقها فقط ولا يضاعف إجمالي الدراسة.
4. التكلفة الفعلية تختار الأب ثم الابن التابع له؛ لا يمكنها الربط بقسم له أبناء أو ببند تابع لموقع آخر.
5. تقرير نوع العمل يجمع أوراق «الكهرباء» من المطبخ والصالة مرة واحدة فقط.
6. ترقية قاعدة قائمة تحافظ على كل بنود الدراسة والتكاليف الفعلية وقيمها وروابطها.
7. العربية/RTL والجوال وسطح المكتب واضحان، والأرقام المعروضة تستخدم 0–9.

**الافتراضات:** عمق الشجرة غير مقيد عملياً، لكنه يختبر بثلاث طبقات. «الفئة» الحالية ستصبح «نوع العمل» للأوراق فقط. لا تُخمن مواضع البنود التاريخية؛ تبقى عند الجذر إلى أن ينقلها المستخدم. لا يتم زرع أب أو قالب أو استيراد تلقائي عند إنشاء مشروع.

## خريطة ERP والرقابة

هذه الدراسة والتكلفة الفعلية سجلات تشغيلية داخل الموديول، ولا تنشئ قيداً محاسبياً أو دفعة أو حركة مخزون. مصدر مبلغ التكلفة الفعلية هو `abroj.cost.actual.line.amount`، ومصدر التقدير هو حقول الورقة في `abroj.cost.plan.line`. الحساب والتجميع والتحقق في ORM فقط؛ المتصفح لا يملك أرقاماً أو قرار ربط. سندات الصرف والمرفقات تبقى مرتبطة بسجل التكلفة الفعلية نفسه. لا توجد سياسة ضريبة أو عملة أو إقفال جديدة في هذا التغيير.

## G2 — المعمارية والبيانات

```text
abroj.cost.project
  └─ abroj.cost.plan.line (_parent_store + parent_id / child_ids)
       ├─ قسم: يجمع الأبناء فقط
       └─ ورقة: تسعير + نوع عمل + تكلفة فعلية مرتبطة

abroj.cost.actual.line
  └─ plan_line_id (ورقة فقط) → parent_plan_line_id (عرض/تحقق مشتق)
```

- يحتفظ `abroj.cost.plan.line` بملكية الشجرة؛ لا نموذج مكرر أو خدمة خارجية. يعلن `_parent_store=True` و`_parent_name='parent_id'`، و`parent_id` يستخدم `ondelete='restrict'` و`parent_path` مفهرساً.
- تُعرّف العقدة `section` أو `item`. القسم بلا مبلغ مباشر ولا مادة ولا نوع عمل ولا تكلفة فعلية؛ الورقة وحدها تحمل كمية وسعراً وفئة. لا يقبل البند الورقي أبناءً، ولا يقبل القسم التسعير أو الفعلي.
- يتحقق ORM في `create` و`write`: الأب في المشروع والشركة نفسيهما، ليس الذات أو أحد نسلها؛ لا يتحول بند له تكلفة فعلية إلى قسم، ولا يضاف ابن إلى ورقة أو إلى ورقة مرتبطة بتكلفة فعلية.
- تتجمع حقول القسم من أوراقه في الخلفية. كل مجموع أو مقارنة نقدية يمر عبر `currency_id.round` وبنفس اصطلاح حقول العملة الحالي؛ لا يعتمد على مجموع `float` خام. إجمالي المشروع يجمع الأوراق فقط لتفادي الاحتساب المزدوج؛ تختبر ورقة واحدة أنها تظهر مرة في أصلها وفي مجموع المشروع.
- يبقى `plan_line_id` هو العقد المعتمد للتكلفة الفعلية ولا يقبل إلا ورقة. حقل «نطاق/أب الدراسة» في الشاشة قيمة اختيار مؤقتة للفلترة فقط، ولا يُخزن كمرجع ثانٍ: يختار المستخدم الأب ثم الورقة التابعة له؛ وعند الحفظ يستنتج النظام الجذر من الورقة. تبقى التكلفة غير المخططة مساراً مستقلاً بلا بند.
- الاستيراد/التصدير يستخدمان عقداً ثابتاً: `path` و`node_kind` إضافة إلى الأعمدة الحالية. المسار يعرّف الأقسام بالترتيب، والملف المسطح القديم بلا `path` ينشئ أوراقاً جذرية كما كان. لا يقبل الاستيراد مساراً مكرراً متضارباً أو ورقة بلا نوع عمل.
- تحديث schema يضيف قيماً افتراضية محافظة: كل بند تاريخي `item` جذري؛ لا يحرك بيانات تاريخية ولا يغير مبلغاً أو رابط تكلفة فعلية.

## G3 — التقنية والمكتبات

المسار المباشر: Odoo ORM وواجهات وقوالب الموديول الحالية، بلا حزمة أو خدمة أو تعديل Core. استُبعدت حزمة بناء مقاولات خارجية لأنها تملك نماذج مشروع/ميزانية/دفعات متداخلة. استُبعدت `web_hierarchy` الأصلية لأنها تعرض مخططاً تنظيمياً أفقياً لا جدول كميات متداخل، ولا تحقق تجربة الإدخال المطلوبة. أي مكوّن طيّ خاص يبقى محلياً في الموديول، ويعاد استخدام مكونات أودو القياسية للأزرار والحقول والحوار.

## G4 — عقد الواجهة

- مسار عرض محلي باسم `abroj_project_costing.study_tree`: حقل OWL داخل تبويب الدراسة يقرأ بنود المشروع الحالية ويعرضها كصفوف متداخلة قابلة للفتح والطي؛ لا تعتمد الشاشة على قائمة One2many المسطحة.
- رأس دراسة واحد: «إضافة بند رئيسي» و«إضافة بند فرعي»؛ الأخيرة معطلة حتى يختار المستخدم أباً. لا يوجد زر إعداد أو قالب أو استيراد أب عند إنشاء المشروع.
- صف القسم: سهم فتح/طي، اسم، ومجاميع التقديري/الفعلي/الانحراف، وإجراء إضافة تابع.
- صف الورقة: مسافة مستوى، نوع العمل، كمية، تقديري/فعلي/انحراف، وإجراء تعديل.
- لا حركة ضرورية: الفتح والطي فوريان لأنه إجراء متكرر. تدعم الصفوف لوحة المفاتيح واللمس ولا تعتمد على hover.
- تستخدم الشجرة حوار نموذج أودو القياسي للإضافة/التعديل. حالة الفتح والطي محلية للمتصفح ولا تغيّر بيانات الدراسة. تدعم الصفوف لوحة المفاتيح واللمس ولا تعتمد على hover.
- يستخدم النمط المحلي للموديول وألوان/حدود أودو، مع RTL/LTR والجوال؛ لا مكتبة UI جديدة. يختبر العرض العربي الضيق، وإدخال/طي 500 بند بثلاث طبقات.
