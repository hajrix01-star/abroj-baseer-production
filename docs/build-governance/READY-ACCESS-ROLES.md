## Independent security / ERP gate review — roles_security_map, 2026-09-10

Decision: **G0, G1, G2 and G3 APPROVED for implementation of the draft-only contract below.** This is design approval, not a release GO; no executable candidate or role journey has yet been verified. The earlier cashier posting bridge is superseded and must not be implemented.

- **G0:** The separation is explicit: cashier owns and edits draft batches; accountant approves through the existing atomic native vendor-bill/payment pipeline. Approved batches stay immutable. Own approved batch summaries remain visible without opening general accounting records. No existing users are reassigned automatically.
- **G1 bounded assumptions:** Plan for 100 configured role users, 3 companies, up to 10 concurrently active input users, 10,000 batches/year with the existing 50-row ceiling, and native paginated list reads. Role assignment is administrative and infrequent; do not promise production capacity from these assumptions. Isolated QA targets: common paginated list/search under 2 seconds and a single preset assignment under 5 seconds; record measured environment/results. Preserve current daily backups and release restore process; a 24-hour backup interval is an operational schedule, not a guarantee against all data loss. Do not run load on MAIN. No retention deletion is introduced.
- **G2 implementation decisions:** Owner gets an explicit audited XML-ID inventory of installed administrative groups (including Settings, accounting and EH manager, HR/payroll, attendance/leave/expense, purchase/sales/POS/stock/product, project, maintenance, dashboards and website designer where installed). Resolve optional known references idempotently. Do **not** select all groups, copy mutable current-admin membership, or infer administrative privilege from greatest numeric sequence. Exclude portal/public and incompatible user types; preserve native company/ledger rules. Adding a new unknown application requires extending/reviewing the inventory, not a claim of automatic unlimited future access.
- **G2 accountant baseline:** `account.group_account_manager`, `purchase.group_purchase_manager`, `sales_team.group_sale_salesman_all_leads`, and `point_of_sale.group_pos_user` plus required native internal dependencies. POS manager is excluded because it implies `stock.group_stock_user`; unrelated EH-suite administrator privileges are not implied merely for invoice access. Necessary shared product/contact/tax/journal and operational POS stock access is part of permitted workflows, not a standalone extra application. Sales grants CRM lead rights natively: enforce a conditional global deny for limited-role `crm.lead`, not only a hidden CRM menu. Check and close accidental internal-user project/task and employee-directory business reads where they are unrelated to permitted workflows; retain specifically justified POS employee lookups if required. The final implementation must enumerate the supported/denied models and prove allowed workflows still work.
- **G2 cashier:** Internal + POS user; never invoice group. Own-batch and own-line conditional global rules intersect company rules. Existing create/write/unlink draft guards stay authoritative. Explicit public `action_approve` denial precedes the already-approved shortcut. Native bill/payment actions remain denied. Narrow printable/display references may use a fixed-shape helper only after caller batch read, owner and company checks; no arbitrary-model, arbitrary-field or context-flag elevation. Do not elevate draft CRUD or approval.
- **G2 role assignment:** Restrict role and membership/company administration to an existing authorized administrator. Apply presets atomically and clear unrelated inherited grants on downgrade. Prevent later membership edits from silently defeating a constrained preset; test direct user/group RPC paths. Existing unassigned users remain unchanged. Denying a limited role must not restrict the owner through an accidental inherited cashier/accountant marker.
- **G3:** Native Odoo 19 groups, ACLs, global record rules, views and current batch model are the direct path. No new financial models, approval bridge, dependencies, formulas or UI framework are warranted.
