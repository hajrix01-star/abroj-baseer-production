# طلبات المشتريات والعهدة — عقد البناء والسجل الحي

الحالة: PRC-UI1 مرشح QA معتمد؛ G0–G6 مغلقة بـGO لبيئة QA. لا يوجد اعتماد نشر للإنتاج.

المرجع المعماري: **BASEER-ODOO-PRC-v1**، تصنيف **ARCHITECTURAL** (مخزون ومال وصلاحيات وتكامل). المالك: قائد البناء؛ البديل: المراجع المستقل. يتكامل مع `stock` و`account` و`baseer_purchase_batch` من دون تعديل Odoo core أو POS.

## عقد البناء (G0)

### الهدف

إضافة Odoo مستقلة باسم مقترح `baseer_procurement_requests` تقدم كاشير مشتريات سريعاً للمواد الخام، من الطلب التشغيلي بلا مورد وإرسال واتساب اليدوي، إلى الاستلام، إدخال الكاشير للسعر الفعلي، استلام المخزون، إدخال فاتورة المورد الإجمالية، وتسوية عهدة مندوب المشتريات. لا تعدل POS أو Odoo core.

### المستخدمون والرحلات

| الدور | الرحلة المصرح بها |
| --- | --- |
| مدير المطعم | ينشئ طلب المواد الخام، يرسله يدوياً في واتساب، ويؤكد الكمية المستلمة كاملة أو جزئية. لا يرى أو يعتمد القيود أو الضريبة. |
| مندوب المشتريات | يستلم رسالة واتساب وكشف عهدته فقط؛ لا يعدل السعر أو يعتمد مالياً. |
| كاشير المشتريات | يثبت الصنف والحجم والكمية والسعر الفعليين بعد الاستلام؛ لا يعتمد فاتورة مورد أو تسوية عهدة. |
| المحاسب | يدخل فاتورة المورد الإجمالية، يربطها بالطلب، ويراجع التسوية. |
| مدير المحاسبة | يعتمد الفروقات والعكس والتصحيحات. |

### دورة المستندات والرقابة المحاسبية

```text
مسودة طلب (لا أثر)
  → مرسل واتساب يدوياً (لا أثر)
  → عهدة صادرة إلى المندوب (دفعة/قيد أصلي واحد)
  → استلام المدير: كامل أو جزئي (لا أثر مالي)
  → شراء فعلي/تسعير الكاشير (استلام مخزون + سجل سعر)
  → فاتورة مورد مرتبطة (لا دفعة مورّد ثانية)
  → تسوية من حساب عهدة المندوب أو نقد مرتجع
  → مقفل أو فرق مفتوح
```

العهدة ليست قرض رواتب. بعد الترحيل لا يعدل مبلغ أو كمية أو سعر بصمت: التصحيح يتم عبر مرتجع مخزون/عكس فاتورة/حركة عهدة عكسية مع مرجع وسبب. الفاتورة المرتبطة بعهدة تنشئ دَين المورد ثم تسويه من حساب عهدة المندوب؛ يمنع مسار `baseer_purchase_batch` الحالي من تسجيل دفعة بنك/صندوق ثانية على ذلك السطر.

### النطاق

- كتالوج مواد خام فقط، بحث وتصنيف وسلة شبيهة بواجهة POS، عربية/إنجليزية، RTL/LTR، هاتف وسطح مكتب.
- وحدات شراء وتغليف: كيلو/نصف كيلو/كرتون/كيس/حبة، مع تحويل صحيح إلى وحدة مخزون المنتج.
- آخر سعر فعلي لكل شركة + مادة + عرض شراء/وحدة؛ ليس `standard_price` ولا سعر المسودة.
- طلب، واتساب يدوي، استلام جزئي، شراء فعلي، استلام مخزون، سجل سعر، كشف عهدة شهري، ربط فواتير الإدخال الجماعي.
- تقارير كميات وأسعار ونواقص وعهدة؛ والإيقاف الآمن read-only بدلاً من إلغاء تثبيت مباشر.

### خارج النطاق الأول

- تعديل POS أو نسخه أو تشغيل جلسات المبيعات.
- إرسال واتساب آلي أو ادعاء وصول الرسالة.
- عمل بلا اتصال.
- تحويل الإضافة إلى بديل شامل للمشتريات أو نظام رواتب/سلف.
- حذف أو تعديل قيود أودو الأصلية مباشرة.

### معيار القبول

1. طلب بلا مورد لا ينشئ مخزوناً أو فاتورة أو قيداً.
2. الشراء الفعلي مرة واحدة فقط ينشئ استلام مخزون واحداً ويحدّث آخر السعر للمادة والحجم الصحيحين.
3. فاتورة 1,900 مرتبطة بعهدة 2,200 لا تسجل دفعة مورّد ثانية؛ كشف العهدة يوضح 300 ثم يصل صفراً بعد مرتجع 300.
4. الاستلام الجزئي، العكس، النقر المكرر، اختلاف الشركة، والضريبة/الفترة المقفلة تفشل بأمان أو تمر بمستند التصحيح الصحيح.
5. المحاسب لا يعيد إدخال الأصناف؛ يربط الفاتورة برقم الطلب، ويعتمد التخصيص فقط عندما يطابق الإجمالي أو يثبت فرقاً.
6. واجهة الكاشير مستقلة عن POS، قابلة للاستخدام بالعربية على هاتف وسطح مكتب، وكل الحسابات المعتمدة في الخلفية.

## ملف السعة والاستمرارية (G1)

افتراض قابل للقياس قبل توفر أرقام تشغيلية: 20–100 فرعاً، 5–20 طلباً يومياً للفرع، 10–50 سطراً للطلب، وثلاثة مستخدمين متزامنين للفرع. هدف اعتماد شراء فعلي من 10 أسطر أقل من 15 ثانية في QA محلي. صفحات القوائم والتقارير مفهرسة بالشركة/الحالة/التاريخ/المندوب؛ الكتالوج يحمل مواد الشركة النشطة فقط ويستخدم بحثاً خادمياً عند آلاف المواد. اعتماد الشراء، تمويل العهدة، والتسوية ذرية ومقفلة ومقاومة لإعادة الطلب. لا queue أو cache أو خدمة جديدة في الإصدار الأول.

## المعمارية والملكية (G2)

| المالك | مصدر الحقيقة |
| --- | --- |
| الطلب التشغيلي/سلاله/العروض/سجل آخر السعر/حالة واتساب | الإضافة الجديدة |
| الكميات المخزنية والاستلام والمرتجع | `stock.picking` و`stock.move` الأصليان |
| فاتورة المورد والضريبة والمصالحة | `account.move` والمسار المحاسبي الأصلي |
| تمويل العهدة والنقد المرتجع | `account.payment` أو مستند حسابي أصلي مراجع؛ سجل الإضافة رابط/عرض وليس دفتر أستاذ بديل |
| تفاصيل الفاتورة الإجمالية الحالية | `baseer_purchase_batch`، مع امتداد مضبوط للربط والتخصيص لا إعادة بناء |

نماذج جديدة مقترحة: `baseer.procurement.request`, `baseer.procurement.request.line`, `baseer.procurement.purchase.option`, `baseer.procurement.price.history`, `baseer.procurement.custody.event`, و`baseer.procurement.bill.allocation`. تخصيص الفواتير many-to-many، لأن طلباً قد يحمل فواتير عدة؛ لا يحتسب مبلغ الفاتورة أو العهدة مرتين.

**قرار المالك PRC-D5:** الإصدار الأول مخزون **كمي فقط** مع آخر سعر فعلي؛ لا يستخدم تقييم مخزون محاسبي حي ولا يحدّث `standard_price`. تبقى فاتورة الإدخال الجماعي الإجمالية مصروفاً أصلياً كما هي، ويمنع التقرير ادعاء قيمة مخزون محاسبية. ما زال الربط والتخصيص ضرورياً لمنع عدّ المشتريات أو العهدة مرتين.

## التقنية والمكتبات (G3)

المسار المباشر: addon واحد modular في `custom_addons`, يعتمد قدرات Odoo الحالية (`web`, `stock`, `account`, `purchase`, وامتداد `baseer_purchase_batch` عند الحاجة). واجهة OWL/Client Action عبر `web.assets_backend` تستعمل خدمات ORM/RPC/dialog/notification الأصلية. لا تستورد `pos_store` أو `ProductScreen` أو `OrderWidget` ولا تفتح `/pos/ui`، لأنها مرتبطة بجلسات مبيعات POS. لا اعتماد npm أو Python جديد مقترح.

## قراءة QA ومراجعة البوابات

قراءة قاعدة `baseer_dev` في 2026-09-11 (read-only) أثبتت وجود مستودعات وسندات استلام ودفاتر مشتريات أصلية للشركات، لكنها أثبتت أيضاً أن فئة `Food` لا تملك إعداد تكلفة أو تقييم أو حسابات مخزون، ولا توجد مواد خام stockable مهيأة لها. لا تنشئ الإضافة منتجات أو فئات أو حسابات خفية. تعرض الإضافة حارس إعداد واضحاً، ولا تسمح بتأكيد شراء فعلي قبل اختيار مواد خام وموقع استلام ووحدات متوافقة. إعداد التقييم والحسابات ليس شرطاً لمسار الكميات فقط، لكنه شرط مستقبلي لأي قيمة مخزون محاسبية.

مراجعة المراقب العام المستقلة PRC-R1 ثم PRC-R2:

| البوابة | القرار | سبب القرار |
| --- | --- | --- |
| G0 | قبول مشروط | الرحلات والنطاق صحيحان؛ ثُبتت سياسة مخزون كمي ومالك اعتماد السعر النهائي، ويبقى تثبيت مسار العهدة الأصلي. |
| G1 | غير معتمدة | افتراضات السعة موثقة لكن لا توجد بيانات catalog/latency QA أو قياس بعد. |
| G2 | غير معتمدة | لا يلزم تقييم حي الآن؛ يلزم ربط stock→bill→custody، تخصيص الفاتورة، ومسار حساب العهدة الأصلي قبل ترحيل مالي. |
| G3 | قبول مشروط للهيكل غير المالي | OWL مستقل ولا POS core صحيحان؛ جسر الإدخال الجماعي اختياري ولا يعتمد عليه مسار الإضافة الأساسي. |

### إعادة المراجعة PRC-R2 بعد PRC-D5 وPRC-D6

| البوابة | القرار التنفيذي | الحد الفاصل |
| --- | --- | --- |
| G0 | GO مشروط للمسار التشغيلي | طلب/واتساب يدوي/استلام مدير/كمية وسعر فعليان/سجل سعر/استلام مخزون كمي؛ لا تمويل أو تسوية عهدة. |
| G1 | GO مشروط | يقاس تحميل الكتالوج وطلبات 10 و50 سطراً والتزامن في QA قبل المعاينة. |
| G2 | GO مشروط للمخزون الكمي، NO-GO للمال | لا تأكيد إذا كان تقييم المنتج `real_time` أو إذا أنشأ الاستلام أثراً محاسبياً؛ العهدة وجسر batch لا يعتمدان قبل تصميم المستند الأصلي. |
| G3 | GO محدود | addon وOWL وأمن واستيراد QA فقط، بلا POS/core/npm وبلا اعتماد مالي للجسر. |

لا ينفذ جسر `baseer_purchase_batch` المالي قبل تثبيت: تحويل العهدة (مدين ذمة عهدة الموظف/دائن صندوق أو بنك)، فاتورة المورد (مدين مصروف/دائن مورد)، تسوية موثقة (مدين المورد/دائن ذمة العهدة) ونقد مرتجع (مدين صندوق أو بنك/دائن ذمة العهدة)، مع حساب ومجلة وشريك/موظف وتواريخ إقفال وعكس. عندها فقط يمنع خادمياً السطر المرتبط من الدفع المباشر (`is_credit=True` و`payment_method_line_id=False`) ويقفل التخصيصات بالصفوف والمبالغ.

### قرار مسار الإصدار الأول

اختار المالك في 2026-09-11 المسار الثاني: **مخزون كمي فقط مع آخر سعر**. تدخل الكميات وسجل آخر السعر، وتبقى فاتورة الإدخال الجماعي الإجمالية كما هي. لا تدعي الإضافة قيمة مخزون محاسبية لحظية. أي انتقال لاحق إلى تقييم حي هو قرار معماري جديد يحتاج عقداً وترحيل بيانات ومراجعة مستقلة.

لا يكفي اختيار طريقة دفع من واجهة الإدخال الجماعي: أي فاتورة مرتبطة بعهدة يجب أن يمنع خادمياً `payment_method_line_id` ومسار `account.payment.register` الحالي، ثم تسوّى بمستند أصلي من حساب العهدة. الفاتورة الواحدة قد تخص عدة طلبات؛ لا يعتمد تخصيصها إلا إذا ساوى مجموع تخصيصاتها الإجمالي المعتمد أو كانت هناك تسوية فرق موقعة.

### عقد تنفيذ العهدة PRC-D7 (QA)

المسار المنفذ في QA هو: (1) تمويل العهدة: مدين حساب ذمة عهدة المشتريات/دائن حساب الصندوق أو البنك المختار؛ (2) اعتماد فاتورة الإدخال الجماعي المرتبطة بالعهدة: فاتورة مورد آجل فقط، بلا `account.payment.register`؛ (3) إنشاء قيد تسوية أصلي: مدين ذمة المورد/دائن ذمة عهدة المشتريات ثم المصالحة مع الفاتورة؛ (4) النقد المرتجع: مدين الصندوق أو البنك/دائن ذمة العهدة. كل تمويل أو مرتجع يحتفظ بقيده الأصلي، وتبقى الفاتورة وسجل التسوية غير قابلين للتعديل. يُشترط حساب ذمم قابل للمصالحة ومجلة عامة للعهدة، ومجلة صندوق/بنك لكل حركة؛ ولا يُنشئ الإعداد الافتراضي حسابات أو مجلات خفية.

هذا الإصدار يدعم فاتورة إجمالية مقابل طلب مكتمل واحد فقط، وبنفس الإجمالي الفعلي للطلب. التخصيص الجزئي أو فاتورة مشتركة بين عدة طلبات مؤجلان صراحة إلى امتداد `allocation` مستقل، ولا يمرران كمبالغ غير مثبتة.

## سجل القرارات

| المعرف | القرار | السبب |
| --- | --- | --- |
| PRC-D1 | كاشير مشتريات مستقل بأسلوب POS، لا POS نفسه | يمنع خلط جلسات ومبيعات ومدفوعات العملاء بالمشتريات. |
| PRC-D2 | الطلب يبدأ بلا مورد ولا `purchase.order` | المورد لا يكون معروفاً عند تكوين قائمة واتساب. |
| PRC-D3 | الفاتورة ترتبط بالطلب ولا يعاد إدخال الأصناف | يحفظ تجربة المحاسب ويربط العهدة والمخزون دون تكرار. |
| PRC-D4 | لا استخدام مباشر لمسار الدفع في الإدخال الجماعي للعهدة | يمنع دفع المورد مرتين بعد دفع المندوب من العهدة. |
| PRC-D5 | الإصدار الأول مخزون كمي فقط مع آخر سعر فعلي | قرار المالك؛ يحافظ على فاتورة المحاسب الإجمالية ولا ينتج قيمة مخزون محاسبية. |
| PRC-D6 | استيراد كتالوج المواد إلى QA فقط | استيراد مواد ووحدات/تغليف وآخر سعر من بصير القديم؛ لا فواتير أو قيود أو تاريخ عهدة. |
| PRC-D7 | عهدة محاسبية أصلية في QA | تمويل/تسوية/مرتجع عبر `account.move` الأصلي؛ ربط batch يجعل الفاتورة آجلًا ويمنع الدفع المباشر. |
| PRC-D8 | مطابقة تجربة Odoo POS بالنمط لا بالاعتماد الداخلي | تعاد هندسة شاشة الطلب كـProduct Screen/Order Display محلية داخل `web.assets_backend`: كتالوج وصور وتصنيفات وبحث خادمي وسلة، مع شاشة سلة مستقلة على الجوال. لا يستورد الموديول `pos_store` أو مكونات `/pos/ui` ولا يغيّر جلسات أو بيانات المبيعات. |

## عقد إعادة بناء واجهة POS-like (PRC-UI1، G0–G4)

**G0 — النطاق ومعيار القبول:** التغيير محصور في نسخة QA `baseer_procurement_qa_20260911` وموديول `baseer_procurement_requests`. شاشة «طلب جديد» يجب أن تشبه رحلة Odoo POS فعليًا: إضافة المادة بلمسة، زيادة الكمية عند التكرار، بحث وتصنيف وصورة/بديل صورة، سلة واضحة، إجمالي خادمي، اختيار المستودع والمندوب وواتساب، وحفظ لا يقبل النقر المكرر. النسخة الأصلية وPOS core والسياسات المالية خارج النطاق.


## PRC-UI2 — مسار الكاشير الموحد (QA فقط)

### عقد البناء وقرار المالك

المالك اعتمد في 2026-09-11 أن **كاشير المشتريات** هو صاحب تأكيد الاستلام المادي والكميات والأسعار؛ مرحلة المدير لا تظهر في واجهة الكاشير الجديدة. لا يغيّر فتح الطلب حالته، ولا ينشئ نسخة أو طلباً جديداً: يحمل الطلب الأصلي بمعرّفه ويطبق الإجراء المحكوم فقط.

### G0 — النطاق والقبول (معتمدة)

- تبويبان داخل شاشة الكاشير: «طلب جديد» و«الطلبات السابقة».
- الطلبات السابقة مرقمة ومفلترة بالشركة والصلاحية والحالة: مسودة، مرسل للمندوب، بانتظار تأكيد الكاشير، مكتمل.
- المسودة تُعدل وتُرسل؛ المرسل يُفتح لتأكيد الكاشير؛ المكتمل قراءة فقط. لا تعرض المعرفات التقنية أو الحقول الإدارية في الجوال.
- خارج النطاق: العهدة، تعديل POS أو Odoo core، وتعديل المخزون أو آخر السعر عند مجرد فتح الطلب.

### G1 — السعة (معتمدة)

يعاد استخدام حد الكتالوج 48 وخلفية مرقمة؛ قائمة الطلبات السابقة لا تتجاوز 50 طلباً في الصفحة ويدعم الاستعلام فهرس الشركة/الحالة/التاريخ القائم. الهدف أقل من ثانية لصفحة الطلبات في QA الحالية، ولا cache أو مكتبة أو خدمة جديدة.

### G2 — العقد والضوابط (معتمدة)

واجهة الطلبات تستدعي RPC قراءة محدوداً؛ الخادم يعيد الإجراء المسموح من الحالة والصلاحية. تأكيد الكاشير يقفل صف الطلب، يتحقق من الكميات بدقة Decimal، وينشئ الاستلام الكمي وسجل آخر السعر مرة واحدة فقط. الطلب المكتمل لا يعدل إلا بمسار تصحيح معتمد. يظل `stock.picking` الأصلي مصدر حقيقة المخزون.

### G3/G4 — التقنية والتجربة (معتمدة)

**G1 — السعة والاستمرارية:** الوضع الحالي 255 خيارًا؛ التصميم المستهدف يدعم عدة آلاف من الخيارات بلا تحميلها كلها. البحث والتصنيف والترقيم خادمية بصفحات لا تتجاوز 48 عنصرًا، مع هدف أقل من ثانية لاستجابة الصفحة في QA المعتادة. لا cache أو queue أو مكتبة جديدة. العمليات المنشئة تبقى ذرية ومقاومة للنقر المكرر، والرجوع هو إعادة نشر مصدر `19.0.3.0.0` على QA.

**G2 — البيانات والعقود والأرقام:** `baseer.procurement.purchase.option` يبقى مصدر المادة/العرض/آخر السعر، و`product.category` مصدر التصنيف، وصورة المنتج من مسار `/web/image` الأصلي. RPC الكتالوج يفرض الشركة والصلاحية والنشاط والحد والترقيم. RPC تسعير السلة يعيد الكمية والسعر وإجمالي السطر والإجمالي كنصوص غربية بمنزلتين؛ لا تكون نتيجة JavaScript مصدر حقيقة. `create_from_catalog` يعيد التحقق من الخيارات والكميات ويأخذ السعر من الخادم كما هو قائم. لا تغيير في حركة المخزون أو العهدة أو الفواتير.

**G3 — التقنية والمكتبات:** OWL/Odoo 19 الحالي هو المسار الأقصر والأقل مخاطرة. لا حزمة Python أو npm أو مكتبة UI جديدة. نستخدم Bootstrap/Font Awesome وخدمات ORM/action/notification المضمنة فقط، ونستعير بنية التفاعل من POS دون نسخ مكوناته الخاصة أو ربط تحديثاتنا بعقودها الداخلية.

**G4 — نظام التجربة:** مصدر النص إنجليزي قابل للترجمة، وترجمة عربية كاملة مع RTL/LTR من لغة أودو لا `dir` ثابت. سطح المكتب: سلة ثابتة بجانب كتالوج قابل للتمرير. الجوال: تبديـل صريح بين «المواد» و«السلة» وشريط إجراء سفلي، بلا سلة تغطي المواد أو تمرير أفقي. أهداف اللمس 44px على الأقل، بطاقات المواد أزرار بلوحة مفاتيح وARIA، حالات تحميل/فارغ/خطأ، أرقام 0–9، وحركة ضغط قصيرة فقط مع `prefers-reduced-motion`.

مراجعة الاختصاصيين قبل التنفيذ: مسؤول مطابقة POS أكد أن الاعتماد على Client Action المستقل صحيح وأن النواقص الجوهرية هي التصنيف والصورة وسلوك السلة والجوال. مسؤول الخلفية أكد الحاجة إلى بحث خادمي مجزأ وتسعير خادمي. حارس البوابات اعتبر صلاحية QA قائمة ولا يطلب إذنًا إضافيًا داخلها؛ يوقف فقط الإنتاج أو تغيير قرار مالي أو حذف واسع.

### إغلاق شروط المراجعة المستقلة PRC-UI1-R1

- **منع التكرار (G0):** تنشئ الواجهة UUID ثابتًا للسلة وترسله إلى `create_from_catalog`. تحفظ الخلفية مفتاح `(company, requester, client_token)` وبصمة canonical للمستودع والمندوب والواتساب وخيارات/كميات السلة. إعادة الطلب بالمفتاح والبصمة نفسيهما تعيد رقم الطلب الموجود؛ اصطدام المفتاح ببيانات مختلفة يُرفض. يتغير المفتاح فقط بعد نجاح الإنشاء أو بدء سلة جديدة.
- **قياس G1:** اختبار آلي معزول ينشئ 1,200 خيارًا موزعة على 12 تصنيفًا ويثبت أن `catalog_page` لا يعيد أكثر من 48 وأن الصفحة التالية بلا تكرار. ويشغّل اتصالين/معاملتين متزامنتين على `create_from_catalog` بالـUUID والبصمة نفسيهما ويثبت إنشاء طلب واحد وإرجاع الرقم نفسه للاتصالين. قياس QA يسجل p95 لعدد 30 استدعاءً لكل من list/search/quote عند بيانات QA الحالية، و10 قراءات بحث متزامنة؛ هدف p95 أقل من 1 ثانية ولا أخطاء. لا تنشأ طلبات قياس تشغيلية إضافية خارج اختبار المعاملات المعزول. تفحص خطة استعلام list/search للتأكد من استخدام قيود الشركة/النشاط/التصنيف/الترتيب؛ لا يضاف فهرس نصي قبل دليل بطء. الرجوع: استعادة مصدر `19.0.3.0.0` على QA، ترقية الموديول، حذف مرفقات bundle المولدة الخاصة بـ`web.assets_web` عند الحاجة، إعادة تشغيل QA وحده، ثم تحقق HTTP/الأصول؛ بيانات الطلب الجديدة لا تحذف.
- **عقد DTO والأخطاء (G2):** `catalog_page` يعيد `{items, offset, next_offset, has_more}`؛ كل item يحمل معرف العرض/المنتج/التصنيف، الاسم والوحدة والتغليف ومسار صورة Odoo. `quote_catalog_cart` يعيد لكل سطر `amount` كسلسلة عشرية canonical و`text` غربيًا بمنزلتين، مع `{currency_symbol, currency_position}` وإجمالي مماثل. التقريب `ROUND_HALF_UP` في الخلفية إلى `0.01`. تُرفض الخيارات المكررة أو المفقودة أو غير النشطة أو التابعة لشركة أخرى، والكميات غير المنتهية/غير الموجبة/الأكثر من منزلتين. الصفحة ليست حد صلاحية: يجوز للسلة الاحتفاظ بخيار صالح ظهر في صفحة سابقة. الصورة لا تمنح صلاحية؛ RPC لا يعيد إلا منتج خيار اجتاز ACL والشركة، وفشل الصورة أو غيابها يظهر بديل الحرف المحلي.
- **أدلة G4:** قبول بصري وتفاعلي عند `1440×900` و`390×844` و`360×800` بالعربية والإنجليزية. يفحص Tab ثم Enter/Space لإضافة المادة، Escape لإرجاع شاشة الجوال للمواد، أسماء/حالات ARIA، عدم overflow أفقي، أهداف لمس 44px، وحالات loading/error/empty. يفحص وجود `prefers-reduced-motion` وعدم اعتماد hover على اللمس. تمر سلامة XML، وتجميع SCSS الكامل من Odoo بلا fallback، وتحميل ترجمة `ar_001.po` بعد ترقية QA. تحفظ لقطات desktop/mobile لكل لغة، مع دليل مستقل أن السلة لا تغطي الكتالوج.

## PRC-CUSTODY2 — صندوق العهدة وربط دفعات إدخال المشتريات (QA فقط)

**الحالة:** مرشح QA `19.0.6.0.0` مكتمل الاختبارات والتحقق الحي؛ G0–G6 **GO** لبيئة QA فقط. الإنتاج وPOS والمبيعات خارج النطاق ولم تُلمس.

### عقد البناء (G0)

الهدف: إعادة استخدام محرك العهدة القائم في `baseer_procurement_requests` لتقديم **صندوق عهدة واحد** للمشتريات. لا يبنى دفتر أستاذ أو دورة دفع موازية، ولا تتغير المبيعات أو POS أو الإنتاج.

**لغة التشغيل:** حساب واحد في شجرة الحسابات باسم «عهد المشتريات» (أصل متداول قابل للتسوية)، وصندوق واجهة واحد باسم «صندوق العهدة». المندوب تفصيل تشغيلي على الطلب/الحركة والتقرير، وليس مورداً أو حساباً أو صندوقاً مستقلاً. البنك وصندوق النقد القائمان هما المصدر أو وجهة استلام المرتجع.

```text
الكاشير: طلب بلا مورد → إرسال للمندوب → استلام فعلي للكميات والأسعار (لا أثر مالي)
المحاسب: دفعة إدخال مشتريات → اختيار طلب مستلم واحد في الهيدر
        → تمويل: حساب/يومية مصدر → صندوق العهدة
        → فواتير الموردين الحقيقية
        → اعتماد ذري: مجموع الفواتير = قيمة الطلب الفعلية، ثم تسوية من العهدة
نهاية الشهر: استلام للبنك أو صندوق نقد، أو ترحيل تقريرِي موثق للرصيد
```

| الحدث | القيد الأصلي ومصدر الحقيقة |
| --- | --- |
| تمويل العهدة | مدين عهد المشتريات / دائن الحساب أو اليومية المصدر — `account.move` |
| فاتورة المورد | مدين حساب الفاتورة الأصلي / دائن ذمم المورد — `account.move` و`baseer_purchase_batch` |
| تسوية من العهدة | مدين ذمم المورد / دائن عهد المشتريات مع مصالحة أصلية |
| استلام المتبقي | مدين البنك أو صندوق النقد / دائن عهد المشتريات |
| ترحيل الشهر | لا قيد؛ رصيد افتتاحي تقريرياً من الحركات المرحلة |

التزامات الرقابة: الحسابات والمبالغ والمطابقة في الخلفية بدقة عملة الشركة؛ بعد الترحيل لا تعديل صامت بل عكس موثق؛ المحاسب فقط يمول/يسوي/يرحل؛ الكاشير لا يملك أثراً مالياً؛ لا يعاد ربط الطلب بأكثر من دفعة معتمدة؛ لا تمر فاتورة العهدة بدفع مباشر ثانٍ. **التمويل حدث مستقل** يثبت حوالة أو تسليمًا وقع فعلاً، ويبقى مرحلاً إذا فشلت لاحقاً دفعة المورد؛ الذرية والتراجع الكامل يخصان فاتورة المورد وتسوياتها داخل اعتماد الدفعة فقط.

معايير القبول: تمويل SAR 2,000 لا يسجل مصروفاً؛ طلب مستلم بقيمة SAR 1,800 لا يعتمد إلا إذا ساوت فواتيره SAR 1,800 ولو كان التمويل SAR 2,000؛ SAR 200 يبقى رصيداً أو يستلم أو يرحل؛ منع النقر/الاعتماد المكرر؛ تقرير شهري قابل لفتح الطلب والفاتورة والقيد؛ طريقة «صندوق النقد» في الإدخال الجماعي تبقى دفعاً أصلياً مباشراً؛ QA فقط.

### ملف السعة والاستمرارية (G1 — مسودة)

افتراض قابل للقياس: حتى 20 مستخدماً متزامناً، 30 طلباً مستلماً يومياً للشركة، 1–20 فاتورة لكل طلب (حتى 600 فاتورة/يوم أو نحو 219,000 فاتورة/سنة للشركة عند الذروة)، واحتفاظ سبع سنوات. الرحلات الحرجة: القائمة، نموذج الصندوق الشهري، اعتماد دفعة 20 سطراً، التقرير الشهري. الهدف في QA: قائمة/تقرير مفلتر أقل من ثانيتين واعتماد أقل من 10 ثوانٍ دون زمن المستخدم. لا يملك هذا التغيير نظام نسخ جديداً: قبل ترقية QA يثبت مسار استعادة QA الموجود كافتراض RPO 24 ساعة وRTO أربع ساعات، ولا يطبق ذلك على الإنتاج. ترقيم وتصفية خادمية، قفل صف وذرية ومنع تكرار؛ لا cache أو queue أو خدمة أو مكتبة جديدة.

### المعمارية والبيانات (G2 — مسودة)

- `account.move` و`account.move.line` هما المصدر المالي؛ `baseer.procurement.custody` رابط/دفتر تشغيلي لا دفتر أستاذ بديل.
- يستمر رابط المصدر غير القابل للتعديل `baseer_procurement_custody_id` لعزل المصالحة. صندوق واحد/حساب واحد في العرض لكل شركة؛ لا حساب أو يومية لكل مندوب. لكل حركة جديدة جهة اتصال `res.partner` موسومة «مندوب شراء» كشريك محاسبي وتفصيل للتقرير، مع إبقاء `employee_id` للسجلات التاريخية فقط؛ لا ترفع هذه الجهة `supplier_rank` ولا تظهر كمورد.
- يوجد سجل صندوق واحد فريد لكل شركة، ويكون مصدر التمويل/المرتجع يومية Odoo نشطة من نوع بنك أو نقد فقط، ويُستخدم حسابها الافتراضي. الهدف حساب الشركة المهيأ القابل للتسوية؛ لا يقبل حساب GL حر أو إعداداً مخفياً.
- يضاف `procurement_request_id` حقيقي قابل للفراغ على رأس `baseer.purchase.batch`، وقيد unique قاعدة بيانات مع فهرس. عند الاختيار تقفل الخلفية الطلب والدفعة؛ لا يحرر الحجز إلا بإلغاء/حذف مسودة غير مرحلة، ولا يحرر بعد الاعتماد. ترفض أسطر/تخصيصات الطلب القديمة في مسار الهيدر.
- التمويل حدث مستقل idempotent مربوط بالطلب+المندوب+مرجع التحويل، مع قفل الحدث/الصندوق/الطلب قبل القيد. اعتماد الدفعة فقط يعمل ضمن معاملة واحدة: قفل الطلب والدفعة والصندوق → تحقق الحالة والمبلغ والفترة والصلاحية والرصيد → فواتير المورد → تسويات ومصالحات، أو تراجع كامل للفواتير والتسويات دون مساس بتمويل سابق.
- يضاف سجل إقفال شهري غير قابل للتعديل لكل شركة/شهر/مندوب يحفظ الافتتاحي/الداخل/الخرج/المستلم/المرحّل والمستخدم. الترحيل لا يكتب قيداً؛ والمرتجع قيد مستقل. يحدد مسار عكس صريح قبل تعديل مصدر فترة مقفلة.
- فهارس: `batch(request_id)`، وحدث العهدة `(company, representative, state, event_date)`، والتسوية `(company, representative, state)`، وطلب `(company, state, actual_confirmed_at)`؛ التصفية شهرية خادمية وسجل منقح لزمن الاعتماد وفشل التحقق دون مراجع مالية حساسة.

### التقنية والتجربة (G3/G4 — مسودة)

المسار المباشر: توسعة addon `baseer_procurement_requests` وواجهات Odoo و`baseer_purchase_batch` الحالية؛ لا Odoo core/POS ولا npm/Python أو مكتبة جديدة. يعاد تبسيط النموذج إلى: تاريخ، مبلغ، **من الحساب**، **إلى الحساب = صندوق العهدة**. تظهر بطاقات شهرية: داخل الصندوق، خرج للمشتريات، مستلم من المندوب، رصيد الإقفال. يختار الطلب في هيدر الدفعة. تستخدم الحوارات والحقول والجداول الأصلية، مع عربية/إنجليزية وRTL/LTR والجوال/سطح المكتب وأرقام غربية `0-9`.

## PRC-REMEDIATION1 — معالجة موانع العهدة والطلبات السابقة (QA فقط)

**الحالة:** G0–G8 مقفلة بـGO لبيئة QA فقط بعد إعادة التحقق المستقلة. الإنتاج لم يُلمس وغير مفوض.

**التصنيف المعماري:** ARCHITECTURAL بسبب schema والقيود والتزامن المالي، مع شريحة واجهة CONTROLLED.  
**التفويض:** المالك طلب التنفيذ باستخدام فريق ألفا بتاريخ 2026-09-11. الإنتاج خارج النطاق صراحة.

### عقد الإصلاح (G0)

الهدف هو إغلاق موانع التسليم المثبتة من دون تغيير السياسة المحاسبية أو بناء دفتر موازٍ أو إضافة مكتبات:

1. تثبيت `baseer_procurement_requests` بنجاح على قاعدة فارغة، مع ترحيل schema قابل للإعادة.
2. إتاحة كل الطلبات السابقة للكاشير ببحث خادمي وترقيم صفحات، لا أول 50 فقط.
3. منع نشر تسوية في شهر أغلق بالتزامن، بترتيب أقفال ثابت وإعادة تحقق داخل القفل.
4. ضمان شريك المندوب في عكس التسويات التاريخية، وحماية دورة قيود العهدة الأصلية من الإلغاء/المسودة غير المنضبط.
5. استبدال قراءات كل التاريخ باستعلامات مقيدة/مجمعة وفهارس تخدم رحلة الاعتماد والرصيد.
6. منع تقسيم أحجام الصنف بين صفحات الكتالوج، ومعالجة نتائج البحث القديمة عند الشبكة البطيئة.
7. إكمال تعريب الحالات الظاهرة في شاشة الكاشير، مع بقاء أسماء البيانات الرئيسية كما أدخلها مالكها.
8. جعل QA تعود بعد إعادة تشغيل Docker وتملك healthcheck، ثم تجميد مرشح جديد مطابق للمصدر الجاري.

**المستخدمون:** مستخدم المشتريات، الكاشير، مدير المشتريات، المحاسب، مدير المحاسبة، ومالك QA.  
**خارج النطاق:** الإنتاج، POS والمبيعات، Odoo core، تغيير شجرة الحسابات أو السياسة الضريبية، استيراد بيانات، ومكتبات جديدة.

**معايير القبول:**

- fresh install ثم upgrade ينجحان على قاعدتين مؤقتتين، واختبارات الإضافة المحددة صفر فشل/خطأ.
- 120 طلباً تجريبياً يمكن البحث فيها وتصفحها كاملة، وفتح طلب مستلم يعيد السجل نفسه إلى السلة.

- نتائج الكتالوج تعرض كل خيارات المنتج معاً؛ والبحث السريع لا يعرض نتيجة استعلام أقدم.

### ملف السعة والاستمرارية (G1)

تُعاد افتراضات C2: 20 مستخدماً متزامناً، 30 طلباً مستلماً/يوم/شركة، حتى 20 فاتورة/طلب و219,000 فاتورة/سنة/شركة، احتفاظ 7 سنوات. يضاف سيناريو 120 طلباً حديثاً لاختبار الوصول الوظيفي، وعينة كبيرة معزولة لاختبار الاستعلامات من دون حمل على QA المشتركة. الهدف: صفحة/بحث أقل من ثانية في QA، واعتماد 20 فاتورة أقل من 10 ثوانٍ. RPO/RTO لا يتغيران؛ healthcheck/restart يعالجان توافر الحاوية لا النسخ الاحتياطي.

لا cache أو queue أو خدمة جديدة. القراءة مفلترة ومصفحة من PostgreSQL، والتجميع المالي في الخلفية. الاختبارات الكتابية والحمل على قواعد مؤقتة فقط.

### المعمارية والبيانات والتزامن (G2)

- يبقى `account.move` مصدر الحقيقة المالية، و`stock.picking` مصدر حركة المخزون، وسجلات العهدة روابط تشغيلية قابلة للتدقيق.
- fresh install يعتمد حقول وفهارس ORM التصريحية و`post_init_hook` بعد إنشاء الجداول عند الحاجة لإعادة بناء العرض؛ migration إصدارية منفصلة تعالج ترقية القواعد الموجودة فقط. يبقى `monthly.report.init()` خاصاً ببناء SQL view ولا ينفذ DDL لجداول النماذج العادية.
- ترتيب الأقفال الجزئي الموحد: الدفعة إن وجدت → العهدة → الطلبات مرتبة بالمعرف → صف المصدر (event/settlement/close) → إعادة قراءة حالة الإقفال داخل قفل العهدة وقبل `account.move`. التمويل بلا دفعة يبدأ العهدة → الطلب → الحدث؛ العكس يبدأ العهدة → التسوية؛ الإقفال يبدأ العهدة → سجل الإقفال. لا مسار يعكس هذا الترتيب.
- العكس يستخدم `representative = settlement.representative_partner_id or custody._representative_partner()` في التحقق وسطر القيد معاً.
- قيود العهدة الموسومة لا تقبل `button_draft`/إلغاء/حذف غير منضبط؛ التصحيح عبر إجراءات العكس الحالية مع سبب وسجل.
- تحقق تأكيد الكاشير يقيد الشركة المسموحة قبل `FOR UPDATE`.
- حساب الرصيد وتحقق التخصيص يستخدمان `read_group`/SQL SUM مقيداً وفهارس مركبة، دون materializing لكل السجل.
- RPC الطلبات السابقة يحافظ على التوافق ويقبل `offset`, `limit`, `search_term`, `state` بقيم محدودة، ويعيد `items`, `has_more`, `next_offset` ورمز/موضع العملة؛ يقرأ `limit + 1` بلا `search_count`، والفرز ثابت `(request_date desc, id desc)`. يشمل البحث الرقم والمستودع والمندوب والمادة والخيار/الحجم والتغليف والوحدة، ويظل مقيداً بالشركة النشطة وACL.
- pagination للكتالوج يكون على المنتجات، ثم يعيد الخادم جميع الخيارات التابعة للمنتجات المختارة في استجابة واحدة؛ يجمعها عميل OWL في بطاقة منتج واحدة، كي لا تنقسم variants أو يتكرر المنتج. مطابقة حجم أو وحدة واحدة تعيد المنتج مع جميع خياراته النشطة المصرح بها.
- يحتفظ OWL بتسلسل مستقل للكتالوج وللطلبات السابقة؛ كل بحث جديد يبطل أثر الطلب الأقدم حتى إذا عاد لاحقاً، بينما يمنع فقط تكرار `Load more` لنفس الجيل. الدمج يزيل التكرار بالمعرف.
- لا تغير عقود Decimal أو قواعد المنازل العشرية أو الذرية ومنع التكرار الحالية.

## PRC-PRODUCT-SOURCE1 — المنتج مصدر الكتالوج والاستلام التشغيلي الاختياري (QA فقط)

**الحالة:** منفذ ومسوّى ومقبول على QA المعزولة؛ فريق ألفا للتسليم: GO لـQA فقط وNO-GO للأصلية.  
**التاريخ والتفويض:** 2026-09-12؛ المالك فوّض التنفيذ في نسخة ترحيل نوركس التجريبية، وجعل منتجات أودو مصدر طلبات المشتريات، وتعطيل تتبع المخزون للمواد المرحّلة مع بقاء الاستلام التشغيلي وسجل السعر وتحديث التكلفة.  
**التصنيف:** ARCHITECTURAL؛ يتغير مصدر كتالوج تشغيلي، ومسار الاستلام، وتكلفة مرتبطة بالشركة، وسياسة بيانات المنتجات المرحّلة.

### عقد البناء G0

- المصدر التشغيلي للمواد هو `product.product` النشط والمملوك للشركة الحالية تحديداً، بشرط `purchase_ok=True` وأن يكون بضاعة لا خدمة. لا تظهر المنتجات المشتركة لأن المالك اعتمد أن أصناف كل شركة مستقلة. خيار الشراء `baseer.procurement.purchase.option` يبقى تفصيلاً داخلياً للوحدة/التغليف وآخر السعر، ويُنشأ الخيار الافتراضي تلقائياً بوحدة المنتج عند غيابه.
- المنتج غير المخزني يمر بكامل دورة الطلب: الطلب، استلام المدير، تأكيد الكاشير، الكمية والسعر الفعليان، الحالة `purchased`، المستخدم والوقت، وسجل سعر غير قابل للتعديل؛ لكنه لا ينشئ `stock.picking` ولا يزيد الرصيد.
- المنتج المخزني مستقبلاً يحتفظ بالمسار الحالي: استلام Odoo أصلي كمي فقط، مع رفض التقييم الآلي أو أي قيد محاسبي غير متوقع.
- عند تأكيد الكاشير فقط، يحول الخادم سعر وحدة الشراء إلى وحدة المنتج عبر مجموعة UoM المتوافقة، يقربه إلى منزلتين، ثم يكتب `product.product.standard_price` في سياق شركة الطلب. لا تحديث أثناء السلة أو استلام المدير.
- سجل السعر يحفظ وحدة الشراء، وحدة المنتج، التكلفة السابقة، التكلفة الجديدة/المحوّلة، وهل أُنشئ استلام مخزني. يبقى `option.last_price` سعر وحدة الشراء، لا تكلفة وحدة المنتج.
- مواد نوركس المرحّلة والمخصصة للشراء فقط تُحدّث في QA إلى `type='consu'` و`is_storable=False`. لا تتحول إلى خدمات، ولا تتغير منتجات البيع فقط، ولا الأصل `baseer_dev`.

**خارج النطاق:** مخزون افتتاحي، استهلاك/تصنيع، AVCO، تقييم آلي، قيد محاسبي، أمر شراء أو فاتورة مورد جديدة، تغيير أسعار البيع، تخمين معاملات تغليف، أو نشر الإنتاج.

**معايير القبول:**

1. كل منتج شراء مؤهل في الشركة يظهر في الكتالوج ولو لم يوجد خيار شراء مسبق؛ ولا يظهر منتج شركة أخرى أو خدمة أو منتج بيع فقط.
2. الخيار الافتراضي يُنشأ/يعاد استخدامه بلا تكرار تحت التزامن، وتظل خيارات التغليف الموجودة متوافقة.
3. تأكيد مادة غير مخزنية ينشئ سجلاً تشغيلياً وسجل سعر واحداً، يحدّث تكلفة الشركة بعد تحويل الوحدة، ولا ينشئ picking أو كمية أو قيداً.
4. تأكيد مادة مخزنية ينشئ picking واحداً فقط ويحدّث سجل السعر والتكلفة؛ إعادة التأكيد لا تضاعف أي أثر.
5. اختلاف وحدة غير قابلة للتحويل، خدمة، شركة أخرى، سعر/كمية غير صالحين، أو أثر محاسبي غير متوقع يفشل ذرياً بلا تحديث تكلفة أو تاريخ أو حالة.
6. تحديث QA يعطل التتبع للعدد المطابق تماماً من منتجات نوركس الشرائية المربوطة، مع payload وبصمة ونسخة استعادة وفحص أن الأصل لم يتغير.

### G1 — السعة والاستمرارية

تبقى افتراضات PRC الحالية: حتى آلاف المنتجات، 48 منتجاً في صفحة الكتالوج، و50 سطراً للطلب. البحث والترقيم خادميان، ولا تُحمّل كل المنتجات إلى الواجهة. إنشاء الخيار الافتراضي محصور بمنتجات الصفحة وتحت قفل منتجات مرتب؛ تأكيد الطلب تحت قفل الطلب الحالي وبمعاملة واحدة. هدف QA يبقى دون ثانيتين لصفحة الكتالوج ودون 15 ثانية لتأكيد 10 أسطر. الاستعادة: لقطة قاعدة+filestore قبل ترقية الإضافة وقبل تحديث سياسة المنتجات، ثم restore smoke على clone معزول.

### G3/G4 — التقنية والتجربة

المسار المباشر هو تعديل مالك السلوك الحالي فقط: `baseer_procurement_requests` وامتداد QA `baseer_noorix_migration`. لا مكتبة ولا Odoo core ولا POS ولا خدمة جديدة. عقد RPC وشكل بطاقات الكتالوج يبقيان متوافقين؛ لا إعادة تصميم واجهة، وتظل العربية/الإنجليزية والجوال/سطح المكتب كما في PRC-UI1. تتغير نصوص الاستلام من «مخزني دائماً» إلى «تشغيلي، ومخزني عند تفعيل التتبع» حيث يلزم.

## PRC-CATALOG-QUICK1 — الإنشاء السريع والمفضلة والأكثر طلبًا (QA فقط)

**الحالة:** مرشح `PRC-CATALOG-QUICK1-v9` مطبق ومقبول على QA المعزولة فقط؛ لا نشر على الأصلية.  
**التاريخ والتفويض:** 2026-09-13؛ طلب المالك زرًا بسيطًا لإضافة منتج غير متتبع للمخزون مع سعره، وإظهار المفضلة والأكثر طلبًا أعلى كتالوج كاشير المشتريات.  
**التصنيف:** CONTROLLED/ARCHITECTURAL؛ يضيف كتابة مضبوطة إلى سيد المنتجات وترتيبًا شخصيًا داخل كتالوج متعدد الشركات.

### G0 — عقد المنتج والتجربة

- زر «إضافة منتج» والنجوم والمنطقة السريعة تظهر في شاشة طلب المشتريات الجديد **لعضو مجموعة كاشير المشتريات فقط**. النافذة تطلب **اسم المنتج** و**سعر الشراء**؛ وتستخدم الفئة المحددة حاليًا إن وُجدت، وإلا XMLID الصريح `product.product_category_goods`. لا تضيف حقولًا أو خطوات غير لازمة. الفئة كيان عالمي: يجب أن توجد وتكون مقروءة، وتُقرأ خصائصها بـ`with_company` ويجب أن تكون `property_cost_method='standard'`؛ وإلا يرفض الإنشاء برسالة ولا يعدل الفئة.
- المنتج الجديد يُنشأ داخل الشركة النشطة تحديدًا، `purchase_ok=True` و`sale_ok=False`، بضاعة غير مخزنية `type='consu', is_storable=False`، بوحدة «وحدة»، وتكون التكلفة/آخر سعر الابتدائيان مساويين للسعر المدخل. السعر بعملة الشركة وهو سعر وحدة الشراء بعد الخصم وقبل الضريبة القابلة للاسترداد، وفق عقد PS1.
- يمنع الاسم الفارغ والسعر غير الموجب أو الأكثر من منزلتين، ويمنع التطابق الاسمي داخل الشركة بعد Unicode NFKC وtrim ودمج المسافات وcasefold، ويشمل البحث المنتجات المؤرشفة. يقفل الخادم `(company_id, normalized_name)` بقفل PostgreSQL advisory ثم يعيد البحث داخل القفل قبل الإنشاء. ضمان المنع يخص RPC السريع؛ المنتج المطابق المؤهل والنشط يعاد للواجهة دون تعديل سعره، والمطابق المؤرشف أو غير المؤهل يُرفض بوضوح ولا يُعدّل.
- النجمة مفضلة **للمستخدم داخل الشركة** وليست علامة عامة على المنتج. تظهر على كل بطاقة وتُحفظ بحالة مرغوبة صريحة idempotent (`set_favorite(product_id, desired_state)`) دون فتح البطاقة. سجل المفضلة يبقى خاملًا إذا أُرشف المنتج أو فقد قابلية الشراء، ولا يظهر حتى يعود مؤهلًا.
- أعلى الكتالوج منطقة سريعة واحدة محدودة بـ12 بطاقة: المفضلة أولًا بترتيب أحدث تفضيل ثم الاسم ثم ID، وإن ملأت 12 فلا يضاف غيرها؛ ثم المنتجات الأكثر شراءً فعليًا بالعدد تنازليًا ثم آخر شراء تنازليًا ثم ID، مع إزالة التكرار داخل هذه المنطقة فقط. «الأكثر طلبًا» يُقاس بعدد سجلات الشراء المؤكدة في `baseer.procurement.price.history` وليس بالمسودات أو السلال المتروكة. تختفي المنطقة أثناء البحث أو اختيار فئة حتى لا توحي بأنها نتائج للمرشح؛ الشبكة العادية وحدها تتبع البحث والفئة.
- البطاقة السريعة تضيف المنتج إلى السلة بنفس عقد الخيار/الحجم الحالي. البحث والفئة والصفحات العادية تبقى كما هي.

**خارج النطاق:** صور المنتج، باركود، مورد، ضرائب، مخزون افتتاحي، تحويل المنتج إلى مخزني، تعديل منتجات أودو الأصلية، أو نشر الإنتاج.

**معايير القبول:**

1. كاشير مخول ينشئ منتجًا باسم وسعر؛ يظهر فورًا في الكتالوج ويُضاف للسلة، مع `product.value` واحد متوقع للتكلفة وبلا `stock.move` أو `stock.quant` أو `account.move`.
2. المنتج وخياره ومفضلته محصورة في الشركة النشطة. `product.category` كيان مشترك في Odoo؛ يتحقق الخادم من وجود الفئة وصلاحية قراءتها فقط، ولا يدعي عزلها حسب الشركة.
3. فشل التحقق أو تعارض الاسم أو أي استثناء يترك المنتج والخيار والتكلفة دون أثر جزئي.
4. المفضلة لا تتسرب بين المستخدمين أو الشركات، والنقر أو Enter/Space على نجمة `type=button` مع وقف الانتشار لا يفتح البطاقة ولا يضيف المنتج للسلة؛ وتتغير `aria-pressed` وتسمية الوصول بعد الحفظ.
5. المنطقة العليا محدودة بـ12 بطاقة، المفضلة قبل الاستخدام، ثم الأكثر شراءً تنازليًا، وبترتيب مستقر عند التعادل.
6. لا كسر للبحث الخادمي أو pagination أو الخيارات المتعددة، وتعمل العربية/الإنجليزية وRTL/LTR على 360 و390 و1280؛ هدف النجمة اللمسي 44px ولا يتداخل مع الاسم أو عداد السلة.
7. سباق إنشاء الاسم نفسه في جلستين ينشئ منتجًا وخيارًا واحدين فقط؛ وحفظ المفضلة المعاد بالحالة نفسها لا يبدلها عكسيًا.

### G1 — السعة والاستمرارية

يبقى الكتالوج 48 منتجًا للصفحة ولا تُحمّل البطاقات الكاملة لكل المنتجات. استعلام المنطقة العليا محدود بـ12 نتيجة؛ قائمة المفضلة مقيدة بالمستخدم والشركة، وتجميع الاستخدام هو lifetime count لعدد سجلات السعر (لا مجموع الكمية)، مفلتر بالمنتجات المؤهلة exact-company، ويعتمد فهرسًا مركبًا `(company_id, product_id, purchase_date)`. الهدف دون ثانيتين لتحميل الكتالوج في حجم آلاف المنتجات ومئات آلاف سجلات الأسعار. لا عداد قابل للانحراف يكتب على المنتج، ولا مكتبة أو خدمة جديدة. استعادة QA من لقطة قاعدة+filestore قبل الترقية.

### G3/G4 — التقنية وعقد الواجهة

**التصنيف:** CONTROLLED/ERP DATA LIFECYCLE؛ يغير مسار حذف سيد المنتج مع الحفاظ على التاريخ التشغيلي.

### G0 — عقد التصحيح والقبول

- عند طلب حذف منتج من Odoo لا يحذف التصحيح أي منتج تلقائيًا عند الترقية. تصبح خيارات الشراء التابعة للمنتج `ondelete='cascade'` لأنها إعداد تابع لا معنى له بلا المنتج، سواء أُنشئ المنتج سريعًا أو عاديًا.
- إذا لم يُستخدم أي خيار للمنتج في `baseer.procurement.request.line` أو `baseer.procurement.price.history`، تحذف قاعدة البيانات الخيار التابع ضمن معاملة حذف المنتج القياسية. علاقات الهوية والمفضلة التابعة تزول بقيود cascade الحالية، بينما يبقى `product.value` وفق سلوك Odoo القياسي كسجل تكلفة بمرجع منتج فارغ.
- إذا وجد طلب أو سجل سعر، يرفض الحذف كله برسالة واضحة تطلب الأرشفة؛ لا تمحى خطوط الطلب أو سجل السعر أو التكلفة التاريخية.
- أي قيد Odoo آخر على المنتج يبقى نافذًا. تفحص حواجز `ondelete` في القالب والمتغير وجود الاستخدام لإظهار رسالة الأرشفة، وتبقى قيود FK سلطة نهائية ضد السباق. حذف دفعة مختلطة ذري: إذا استُخدم خيار واحد ترفض قاعدة البيانات العملية كلها.

**معايير القبول:** منتج سريع أو عادي غير مستخدم يمكن حذفه مع خياراته التابعة؛ منتج له خط طلب أو سجل سعر يبقى كاملًا ويُرفض الحذف؛ الدفعة المختلطة ذرية؛ ولا يتغير `stock.move` أو `stock.quant` أو `account.move`. المنتج الحالي رقم 1027 باسم `Test` فُحص قراءة فقط: خيار واحد، 0 خطوط طلب، 0 سجل سعر، ولم يُحذف آليًا.

### G1–G4 — السعة والمعمارية والتقنية والتجربة

- الفحص محدود بمعرفات المنتجات الجاري حذفها ويستخدم الحقول المفهرسة `product_id` و`option_id`؛ لا تحميل شامل ولا أثر سعة جديد.
- مصدر حقيقة الاستخدام هو خط الطلب وسجل سعر الشراء في الخلفية. لا مكتبة أو واجهة جديدة؛ يتغير FK الخيار إلى cascade، بينما تبقى مراجع خط الطلب وسجل السعر إلى الخيار والمنتج restrict.
- حاجزا حذف صغيران على `product.template` و`product.product` يحسنان الرسالة فقط، ولا ينفذان حذفًا بصلاحية النظام. الرسالة عربية عبر الترجمة الحالية وتعمل في واجهة Odoo القياسية والجوال.
