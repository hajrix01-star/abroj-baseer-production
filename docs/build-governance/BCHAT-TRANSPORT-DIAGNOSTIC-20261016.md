# BChat QA transport diagnostic — 2026-10-16

Candidate `0.7.49-qa-transport-diagnostic (65)` was a QA-only Android diagnostic build. It did not modify QA, Live, database records, permissions, or cookies. Its safe, fixed stage codes established that v1 authentication and the direct v2 bootstrap both returned HTTP 200, while the next transferred `WebMessagePort` request (`/rooms`) failed and caused the misleading generic connection shell.

Recovery candidate `0.7.50-qa-direct-read-recovery (66)` made bounded, authenticated idempotent GET reads use the same verified direct WebView callback that succeeded for bootstrap. It did not resolve the affected-device outcome, so no production conclusion was drawn.

Candidate `0.7.51-qa-read-path-diagnostic (67)` adds fixed route-stage labels for only v2 bootstrap, v2 rooms, and the v1 confirmation probe. It still logs no URL parameters, account identifiers, cookies, response bodies, or chat data. POST routes retain the existing port path and uncertain-write safeguards; no write is retried or converted. This remains QA-only and requires real-device evidence before any promotion decision.

The affected-device trace proved the direct v2 bootstrap returned 200 but no rooms read started. Source inspection identifies the race: `verifiedAccount` intentionally clears push-registration state, then `maybeRegisterPush()` starts a v2 POST before `loadRooms()`. The active POST sets `v2Busy`; `loadRooms()` immediately receives a local status 0 and incorrectly invokes the network-failure path. Candidate `0.7.52-qa-push-queue-recovery (68)` starts chat loading before optional push registration, marks direct reads as busy too, and defers task-only registration through the existing busy-aware scheduler. Diagnostic UI is disabled. No server, QA, Live, database, permission, or cookie change is included.
