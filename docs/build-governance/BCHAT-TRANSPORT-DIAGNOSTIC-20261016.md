# BChat QA transport diagnostic — 2026-10-16

Candidate `0.7.49-qa-transport-diagnostic (65)` was a QA-only Android diagnostic build. It did not modify QA, Live, database records, permissions, or cookies. Its safe, fixed stage codes established that v1 authentication and the direct v2 bootstrap both returned HTTP 200, while the next transferred `WebMessagePort` request (`/rooms`) failed and caused the misleading generic connection shell.

Recovery candidate `0.7.50-qa-direct-read-recovery (66)` made bounded, authenticated idempotent GET reads use the same verified direct WebView callback that succeeded for bootstrap. It did not resolve the affected-device outcome, so no production conclusion was drawn.

Candidate `0.7.51-qa-read-path-diagnostic (67)` adds fixed route-stage labels for only v2 bootstrap, v2 rooms, and the v1 confirmation probe. It still logs no URL parameters, account identifiers, cookies, response bodies, or chat data. POST routes retain the existing port path and uncertain-write safeguards; no write is retried or converted. This remains QA-only and requires real-device evidence before any promotion decision.

The affected-device trace proved the direct v2 bootstrap returned 200 but no rooms read started. Source inspection identifies the race: `verifiedAccount` intentionally clears push-registration state, then `maybeRegisterPush()` starts a v2 POST before `loadRooms()`. The active POST sets `v2Busy`; `loadRooms()` immediately receives a local status 0 and incorrectly invokes the network-failure path. Candidate `0.7.52-qa-push-queue-recovery (68)` starts chat loading before optional push registration, marks direct reads as busy too, and defers task-only registration through the existing busy-aware scheduler. Diagnostic UI is disabled. No server, QA, Live, database, permission, or cookie change is included.

Field evidence from v68 confirms that chats load but the device remains locally unlinked to notifications while Android notification permission, sound, and lock-screen delivery are enabled. The failed operation is therefore the optional registration POST, which still used the same transferred `WebMessagePort` proven faulty by the earlier trace. Candidate `0.7.53-qa-push-direct-registration (69)` routes only `POST /bchat/api/v2/notifications/register` through the verified direct WebView callback. The server registration contract is idempotent for the authenticated `(user, installation_id)` pair; the client sends exactly one request per attempt and only polls for that request's result, never replaying an uncertain POST. Other writes—including messages, tasks, orders, avatars, and unregister—retain their existing port and uncertain-write behavior. The header company label is also constrained to the remaining header width so the notification bell and the account ⋮ menu remain reachable on narrow screens. No QA, Live, database, permission, cookie, or Firebase-service change is included.

The v69 field screenshot confirmed the header fix but also exposed a second client-state defect: returning from Android notification settings forced a bridge recheck that cleared the locally confirmed push account key before re-authentication completed. Android therefore discarded an otherwise valid generic FCM wake-up during that gap, and the dialog kept its initial “linking” wording even if the asynchronous registration later succeeded. Candidate `0.7.54-qa-push-link-continuity (70)` preserves a confirmed route only for the same account through that recheck; a changed account, token replacement, logout, or failed authentication still clears it. The dialog observes local registration completion while it is open without submitting another request. No external state, server route, permission, Firebase configuration, QA, or Live change is included.
