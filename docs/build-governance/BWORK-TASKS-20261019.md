### Goal, acceptance and ERP scope

Restaurant manager assigns a concrete action to one internal authorized employee (e.g. repair air conditioner, obtain equipment next month); assignee optionally starts it and marks it executed with an optional note. No mandatory approval workflow. A task is one company, one creator and one current assignee. Existing user permissions task_view and task_manage remain authoritative, independent from chat/order capabilities. No new role grants and no manager-wide visibility bypass. Standalone visibility stays creator/current assignee; existing room-linked tasks remain readable only through existing membership rules when they match the user's list perspective. No new room-linked creation surface or rescue UI in this scope.

- Default list is all currently authorized companies, with mine/created perspectives and open/done/cancelled server filters. Optional company filter intersects that scope before pagination, never changes a task's company or authorizes a write. Company is labeled per row. A single company is selected automatically and its picker omitted; multiple-company creation requires an explicit valid company (a verified last selection may be reused), never company0/all.
- New screen uses approved compact list/detail/create design, Arabic/English and RTL/LTR, numeric dates0–9, small/large touch surfaces. Title, assignee, optional due timestamp; description/reminder under additional details. Date/time input converts to UTC for transport, backend validates and owns final values/time/state.
- task_manage requires task_view. Candidate assignee must currently hold both effective task rights plus active/internal/company eligibility, rechecked at create/reassign/transition. View-only can read; no hidden UI or stale callback may write. Start and complete are only current-assignee actions; cancel/reassign only creator. New modern workflow permits new→done directly; old task API keeps its previous transition semantics. Closed means cancelled and final, not local archive/hide/delete. No task deletion or reopening.
- Completion returns stored done_at, actor and completion_note from Odoo; UI does not invent a time or person. Creator can inspect result. No financial approvals, purchase/stock moves, accounting entries, product changes or receipt side effects: the word 'purchase' inside task text does not create a procurement order. All existing orders/chat flows are outside the change except narrow shell wiring with regression coverage.
- Network writes are durable manual intents before HTTP, unique UUID, immutable payload, revision checking and server locking. Lost ACK/storage failure stays unresolved, same UUID retry only, no automatic POST after reconnect and no unknown intent eviction. Definite server rejection can close that local intent only after a durable record. Corrupt storage fails closed, never silently wipes. Same actor verification fences HTTP and actions but retains workspace state privately; no task data/action exposure in background/unverified/offline. No new offline task cache is necessary for this connected workflow.
- Task-only accounts must log in and use tasks without chat_view/order_view; reuse the existing alternate authenticated section session, broadening only its task admission criteria and adding tests. Never enter ChatEngine's chat-only identity/cache paths to gain task authority. Bootstrap/permissions changes revoke tasks reads/choices and obsolete writes immediately; durable ACK settlement may complete for the original actor but never expose payload under a new identity.

**Durability/replay:** modern digest operation namespace includes workflow and all normalized payload fields, separate from legacy digest, sharing existing creator/UUID and actor/UUID unique constraints to reject cross-protocol UUID reuse. Retry keeps exact original expected_revision/UUID/payload even after a terminal outcome; duplicate matching receipt is checked before revision/state transition, after current actor/company/visibility/rights checks. Unknown intents never auto-expire/evict/replay. Per-task unresolved transition blocks another transition on that task; matching pending create intent blocks duplication, unrelated operations remain possible. Definitive rejection can be recorded only if proof covers the original intent;401/403/409 alone are not proof a prior uncertain request never executed. Manual retry is available after verified authority returns. Different-account late responses may settle only their original durable journal and are never returned/rendered in the new account.

**Reminder transaction/audience:** one reminder_at fixed at creation, optional due prerequisite; past-but-unemitted allowed, server clock authoritative. Cron has a small indexed limit, first identifies candidates, then locks room before task and rechecks open state, due reminder, marker and current assignee's effective rights/company/membership. It writes persistent change/push intent and reminder_emitted_at in the same transaction/savepoint; rollback reverts both and commit prevents duplicate scheduling. Marker means queued hint, never actual device delivery. Unsent reminders go to the current eligible assignee after reassignment; an already emitted reminder is not emitted again after reassignment (normal assignment notification handles it). Queued reminder to a former assignee or terminal/revoked/ineligible scope is discarded at delivery, even if still a room member. In-app reminder_due derives from current open state and server time and remains true after emission until completion/cancellation, so lack of a device never loses the visible reminder. Existing push provider availability is not silently activated or certified. Indexes cover creator/state/id and partial unemitted reminder_at/id; no new scheduler model, copied task table or general task comment/audit expansion.
