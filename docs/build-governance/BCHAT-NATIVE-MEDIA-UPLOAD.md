# BCH-NMU-1 — الرفع الأصلي لمرفقات BChat

الحالة: **G0–G3 معتمدة؛ التنفيذ G4–G8** · المالك: قائد بناء BChat · التاريخ: 2026-10-17

## عقد البناء (G0)

### الهدف

إزالة اعتماد رفع مرفقات المحادثة على جسر `WebMessagePort` داخل WebView. العطل المرصود
هو M01: يصل الملف أو يبدأ مساره، لكن التطبيق لا يملك تأكيد رفع صالح فيبقى السجل المحلي
معلّقاً ويمنع الرسالة التالية.

### النطاق

- تطبيق Android: عميل رفع أصلي متدفق، يعمل خارج WebView ولا يقرأ كوكيز الجلسة.
- BChat/Odoo: تفويض رفع قصير العمر ومحدود لرفع منطقي واحد، ثم نقطة رفع أصلية تتحقق منه.
- الاحتفاظ بمعرّف `upload_uuid` الحالي كمفتاح منع التكرار ومصدر حقيقة لحالة الرفع.
- حالات عربية/إنجليزية واضحة للرفض أو انقطاع النقل من دون عرض أسرار أو ردود خادم خام.

### خارج النطاق

- لا تغيير لرسائل المحادثة، الصلاحيات التشغيلية، بيانات QA أو الإنتاج، أو تصميم المحادثة.
- لا نقل كوكيز WebView ولا كلمة مرور أو مفتاح ثابت إلى Android.
- لا مكتبة جديدة أو نقل bytes عبر WebView. بعد فقد رد الرفع أو إعادة تشغيل التطبيق، يبقى الملف
  المحلي ومعرّف `upload_uuid` محفوظين ويستعيد التطبيق نتيجة المرفق عبر قراءة جلسية مقيّدة قبل
  أن يسمح بأي إعادة رفع يدوية.

### القبول

1. ترفع صورة حتى 5 MB وملف/صوت حتى 10 MB من التطبيق إلى الغرفة المصرح بها.
2. لا يمر محتوى الملف أو رده عبر `WebMessagePort` أو Base64 أو JavaScript.
3. لا تخرج كوكيز جلسة WebView؛ الذي يصل للعميل هو تفويض عشوائي قصير العمر ومقيد بالحساب
   والغرفة والعضوية والـ UUID والبصمة والحجم والنوع.
4. إعادة المحاولة بعد انقطاع لا تنشئ مرفقاً أو رسالة ثانية؛ الخلفية تحكم الـ UUID.
5. يرفض الخادم التفويض المنتهي أو المختلف عنه، ولا يسجل الرمز أو محتوى الملف في السجل.
6. تثبت فحوص العقد المصدرية حدود النطاق، وتنجح ترجمة Android وفحوص Python المركزة.

### الدليل والتصنيف

التصنيف: عيب نقل هجين متقطع، لا عطل صلاحية أو رفض خادم. لقطة الإصدار 83 تعرض M01،
وسجل معمارية BChat يثبت أن `WebMessagePort` يفقد ردوداً في جهاز الهاتف رغم نجاح fetch.
المسار المباشر: عميل HTTP أصلي بتفويض دقيق بدلاً من إصلاحات إضافية على القناة المفقودة.

## ملف السعة والاستمرارية (G1)

| بند | قرار أو افتراض محافظ |
|---|---|
| الرحلة الحرجة | اختيار ملف → تفويض → بث upload → تأكيد media_id → رسالة موجودة مسبقاً |
| حجم العملية | 5 MB للصور و10 MB للملف/الصوت؛ لا توجد ذاكرة بحجم الملف في JavaScript أو Android |
| الذروة المفترضة | رفع واحد نشط لكل عملية تطبيق؛ لا ادعاء بسعة إنتاج أو 10 رفوع متزامنة قبل قياس معزول |
| هدف التجربة | تأكيد 1 B و5 MB و10 MB في بيئة محلية معزولة؛ الاتصال 2 Mbps يجعل 10 MB نحو 40 ثانية للبيانات وحدها، لذلك مهلة العميل 90 ثانية لا وعد زمن إنتاج |
| التزامن | تفويض واحد نشط لكل مستخدم في وقت واحد، و`upload_uuid` خادمي يمنع مضاعفة media/message |
| الاستمرارية | الملف المرحلي و`upload_uuid` يبقيان محلياً؛ القراءة الجلسية تعيد `media_id` للمستخدم والعضوية نفسيهما بعد فقد الرد، ولا تعيد bytes |
| الرصد | سجل حالة منقح `issued/uploading/resolved/expired/denied` ومدة الرفع؛ لا رمز أو اسم أو محتوى في السجل |

خدمة Odoo الحالية تحفظ bytes الملف ثم ترمّزها للتخزين؛ لذلك لا يزعم هذا العقد أن الخادم
يعمل streaming end-to-end أو أنه يحتمل عدداً عالمياً من الرفوع. يقتصر ضمان هذه الشريحة
على أن Android لا يحتجز الملف في WebView/ذاكرة Java، وأن كل طلب يملك حداً واحداً. لا يوجد
اختبار حمل على QA المشترك. فحص G6 سيكون على بيئة محلية/معزولة فقط بملفات صناعية 1 B و5 MB
و10 MB ورفعَين متوازيَين كحد أولي. مسار BChat المعزول يملك `client_max_body_size 16m`؛
يوفر مصدر Nginx حد `11m` قبل التطبيق ذي حد 10 MiB؛ يُثبت تطبيقه في بيئة الإصدار قبل النشر ولا
يغيّر هذا المرشح إعداد تشغيل حي مباشرة.

## المعمارية والعقود (G2)

```text
WebView session ── POST /mobile-upload-grants ──► BChat server
      │                    │ returns short-lived opaque ticket only
      ▼                    ▼
Android native uploader ── raw HTTPS stream + ticket ──► BChat server
      │                                                   │ validates ticket + room scope
      └──────── media_id / structured result ◄─────────────┘
                         │
                    existing message acknowledgement
```

### ملكية البيانات

- Odoo/BChat يملك التحقق من العضوية وسياسة الغرفة وحجم/بصمة الملف وحالة التفويض و`media_id`.
- Android يملك bytes الملف المرحلي فقط وتقدم الرفع؛ لا يقرر صلاحية أو سياسة أو حالة رسالة.
- سجلات Odoo الحالية للمرفق و`upload_uuid` تبقى مصدر منع التكرار؛ لا يوجد مصدر حقيقة موازٍ.

### التفويض

النقطة الجلسية تصدر `grant_id.secret` عشوائياً (256-bit) بعد التحقق المعتاد، عبر `fetch`
صغير ومقيّد بالأصل داخل WebView مع callback من `evaluateJavascript` لا يتجاوز 8 KiB. لا
تستخدم هذه المرحلة `WebMessagePort` ولا تحمل بايتات ملف؛ وظيفتها الوحيدة تسليم التذكرة إلى
ذاكرة عملية Android. يمسح التطبيق السر عند اكتمال العملية أو إلغائها أو تسجيل الخروج أو
تبديل الغرفة أو انتهاء العملية.

يخزن الخادم
معرّف التفويض وSHA-256 للسر فقط، مع `user_id`, `company_id`, `room_id`, `membership_id`,
`upload_uuid`, `sha256`, `mime`, `name`, `size`, ووقت انتهاء 120 ثانية. حالات التفويض هي
`issued → uploading → resolved|expired`. الانتقال إلى `uploading` ذري وقصير قبل قراءة
الجسم؛ لا يحتفظ الخادم بقفل SQL أثناء بث 10 MB. يعيد endpoint الحالة `202 uploading` خلال
الرفع، و`200 resolved` مع النتيجة المحفوظة بعده. تبقى نتيجة `resolved` قابلة للقراءة بالتذكرة
نفسها لمدة 15 دقيقة على الأقل، حتى لو انتهت صلاحية **الرفع** البالغة 120 ثانية؛ ولا يسمح
انتهاء صلاحية الرفع ببايتات جديدة.

يستخدم التفويض لرخصة **رفع منطقي واحد**؛ لا يصدر من العميل أي metadata في مرحلة النقل، بل
يستعيدها الخادم من التفويض. يصدر الخادم التذكرة بقفل ذري لكل مستخدم ويحده بتذكرة نشطة واحدة؛
لا يلغي إصدار بديل جسماً في `uploading`، وتنتهي محاولة خادم تجاوزت مهلة 90 ثانية قبل الحفظ.
لا يصلح التفويض لرسالة أو غرفة أو ملف آخر.

نقطة الرفع الأصلية تقرأ `Authorization: BChatUpload <grant_id>.<secret>` فقط عبر HTTPS،
ولا تقبل Cookie أو CSRF كبديل. يرفض الخادم query/form/multipart ويقارن طول الجسم وMIME
والبصمة مع التفويض قبل استدعاء خدمة BChat الحالية. عند redemption يعيد مسار الخدمة، تحت
مستخدم grant نفسه، فحص `chat_send` و`media` والعضوية النشطة والشركة والغرفة؛ لذلك يفشل grant
إذا أزيلت العضوية أو سحبت الصلاحية بعد الإصدار. نجاح `_v2_upload` وحفظ `media_id` كـ`resolved`
في المعاملة نفسها. نقطة الحالة تقبل التفويض نفسه فقط وتعيد النتيجة المحفوظة أثناء بقاء السر في
ذاكرة العملية. بعد فقد السر أو إعادة التشغيل، يقرأ التطبيق فقط
`GET /rooms/<room_id>/uploads/<upload_uuid>/reconcile` من جلسته؛ الخادم يعيد media خاصاً
بالمستخدم والغرفة وحقبة العضوية الحالية فقط، أو `missing`، من دون كشف grant أو metadata أو
إعادة رفع bytes.

مسارات النقل الأصلية `auth='none'`, `csrf=False`, `save_session=False`؛ تعتمد Authorization
فقط وترفض Cookie وquery وform وmultipart قبل دخول الخدمة. تستدعي الخدمة بـ`with_user(grant.user)`
ولا تستعمل أي trust أو hostname override.

### الفشل والأمان

- 401/403/410: يفشل التفويض، يعاد إصداره للطلب المحلي نفسه فقط.
- 413/415/409: رفض محدد يظهر للمستخدم ويوقف الإعادة التلقائية.
- انقطاع/مهلة: لا يعاد POST تلقائياً؛ يستعلم العميل النتيجة بتراجع محدود حتى مهلة 90 ثانية ثم
  يستعمل reconcile الجلسي. لا تظهر إعادة المحاولة اليدوية إلا بعد أن تعيد القراءة `missing`.
- Android يستخدم `HttpsURLConnection` بالبث من الملف في executor عبر
  `setFixedLengthStreamingMode(long)`، ومهلة وصل/قراءة محددة، ومنع redirect، ورد JSON
  أقصاه 8 KiB؛ لا ينسخ الملف إلى الذاكرة ولا يستخرج CookieManager أو يضبط trust/hostname.
- فهرس تفويض فريد على `grant_id` وفهارس انتهاء/حالة، وتنظيف tombstones المنتهية والمحلولة
  بحد دفعة بعد احتفاظ 24 ساعة؛ لا تغيير مالي أو ترحيل بيانات.
- فحوص العقد تشمل: عضو سحبت عضويته بعد الإصدار، سر/غرفة/MIME/حجم/بصمة مختلفة، `expired` مقابل
  `resolved`، POST خام مكرر، وغياب Cookie، إلى جانب انتقال `uploading` وقراءة النتيجة بعد
  انتهاء صلاحية الرفع.

## التقنية والمكتبات (G3)

| البديل | القرار |
|---|---|
| WebMessagePort/رفع WebView | مرفوض: الدليل الفعلي يثبت فقد الرد على الهاتف. |
| fetch مباشر داخل WebView | مسار توافق قصير فقط؛ مرفوض كمعيار دائم لأنه يمرر bytes عبر JS. |
| نسخ كوكي WebView لعميل HTTP | مرفوض أمنياً؛ يوسع نطاق جلسة المستخدم. |
| OkHttp/Retrofit جديد | مرفوض حالياً؛ لا حاجة لمكتبة مع منصة Android الحالية. |
| `HttpsURLConnection` + تفويض قصير العمر | معتمد: API منصة، بث ثابت الطول، TLS، اعتماد صفر، وعقد واضح. |

المصادر المراجعة: Android networking (`HttpsURLConnection` وstreaming)، Android WebView
security (حصر الأصل وعدم كشف الجسور/الكوكيز)، Android WorkManager (مرحلة لاحقة للرفع
الأطول). لا توجد مكتبة أو رخصة أو تغيير رصة في هذه الشريحة.
