# BCR-20261020 — التوحيد الداخلي إلى BWork قبل اللايف

## عقد العمل وحدود التفويض — G0 مسودة

طلب المالك توحيد أسماء BChat الداخلية أيضًا قبل نشر BWork على الأصلية، وبدء الحصر والتحويل بالفريق الحالي. المرجع الوظيفي هو المصدر المختبر `d989a71164c02709ad9c0ce0197732aadc89ed7c` على QA؛ أساس فرع العمل `3b0feb1aafe41479e4f33378c1745a5b0a96b811` (سياسة فقط فوق المصدر نفسه). الفرع `codex/bwork-canonical-rename-20261020`.

الغاية: اسم BWork تقني واحد قابل للصيانة، دون موديولين أو محركي محادثة يؤديان الوظيفة نفسها؛ الحفاظ على كل السلوك المعتمد والبيانات. لا يسمح هذا الطلب بتحديث QA/Live أو تشغيل ترحيل على بيانات المالك أو نشر APK أو تفعيل حذف أو منح دور. التنفيذ المحلي ومرشح الاختبار يأتيان فقط بعد اعتماد G0–G3 بصورة مستقلة.

يشمل الجرد: أسماء المجلدات والموديولات والنماذج والجداول والحقول وXMLIDs والمجموعات وقواعد الشركات وروابط المرفقات والمهام/الطلبات/Push/API، ملفات التطبيق وbridges ومفاتيح التخزين وأوامر البناء/CI وحراس الإصدار. أسماء `baseer_bwork_admin` و`baseer_bwork_dashboard` الحالية لا تنشأ نسخ ثانية منها. لا تتغير الحسابات أو الألوان أو الخطوط أو رحلات الإرسال أو صلاحيات المحتوى.

تستثنى من الاستبدال الأعمى: تاريخ Git، السياسات والإصدارات والأدلة المجمدة وتوثيقها التاريخي، بصمات وشهادات التوقيع، هوية حزمة Android اللازمة للترقية، معرّفات UUID والصفوف ومحتوى الملفات ومفاتيح الأمان. أي اسم قديم لازم للترحيل أو توافق عميل موزع يوضع في قائمة مسماة ومحدودة مع سبب وشرط إزالة؛ لا يصبح مصدر حقيقة ثانياً. الجرد يقرر ما هو نشط فعلًا وما هو مرجع قديم، لا يفترض أن مجلد Android القديم مهمل.

## القبول ومسارات الحماية

1. يوجد تطبيق/خدمة محادثة canonical واحد بأسماء BWork؛ فحص tracked-source يمنع BChat خارج قائمة التراث/الترحيل/التوافق المحددة.
2. ترحيل معرّفات الأسماء يحفظ IDs وUUID وروابط الردود/الرسائل/المرفقات/الغرف/العضويات/الشركات والمهام/الإشعارات وسلسلة التدقيق؛ لا فقد أو استيراد نسخة موازية.
3. لا تتغير ACL أو record rules أو صلاحيات المالك/المستخدم؛ لا تعيين أو implied role جديد، والحذف غير مفعل قبل/بعد العملية.
4. حسابات الطلبات والمبيعات والتقويم وأهدافه تبقى من مصادر أودو الحالية؛ لا نسخ بيانات QA إلى اللايف ولا إنشاء مستند مالي بسبب إعادة التسمية.
5. العميل الموزع يحتفظ بقابلية التحديث بتوقيعه وهويته؛ انتقال التخزين يحفظ العمل غير المرسل ومرفقاته وإقراراته، ولا يخلط حسابًا أو شركة أو realm بآخر. لا ينقل ملفًا قبل تحقق ملكيته أو يحذف مجلدًا عامًا.
6. إثبات ترقية من المصدر القديم المثبت، تثبيت جديد، تكرار المحول بلا مضاعفة، رفض التعارض/الحالة غير المعروفة، وتعافٍ من فشل مع زوج قاعدة+filestore مطابق. نجاح source tests وحده ليس نجاح ترحيل فعلي.
7. تبقى204ثوابت التطبيق ومرجع guard الخادم موجودة بلا حذف أو skip أو تخفيف؛ الأسماء في روابط الفحوص يمكن ترحيلها، وليس تغيير معناها. لا شهادة جهاز/مالية/FCM/استعادة فعلية دون دليل.

## G1 — السعة والاستمرارية (مسودة)

الأعداد المرصودة مؤخرًا على QA:5غرف/9عضويات/81رسالة/32وسيطًا؛ ليست شهادة حجم أقصى. لا نمو جديد أو تخزين مكرر مطلوب؛ تبقى ميزانيات المصدر/الكاش/الصفحات كما هي. المطلوب ترحيل اسم مضبوط تحت توقف الكتابة، ومعاملة/قفل محدد ورفض التعارض، دون جلب أجسام المرفقات إلى الذاكرة أو إعادة كتابة بايتاتها. قبل اختبار جديد يُسجل الفرق والخطر غير المغطى والحجم؛ فحص runtime القديم لا يغطي تغيير أسماء module/model/DB أو مفاتيح العميل. لا حمل جديد على QA/Live، ولا إعادة benchmark غير متغير. يُحسم البروتوكول الدقيق بعد جرد الخلفية والعميل.

## G2 — الهوية والبيانات والعقود (مسودة)

الهدف المرشح: `baseer_bchat`→`baseer_bwork` و`baseer_bchat_procurement`→`baseer_bwork_procurement`، مع اسم `baseer.bwork.*` للنماذج وعائلة الجداول/المراجع الموافقة. هذه خريطة أولية وليست أوامر استبدال. يجب حصر كل metadata/string-reference/M2M/SQL/ACL/foreign key/ir.attachment/mail.model/XMLID/schema قبل تثبيتها.

البديل المباشر المفضل: تحويل واحد يحفظ الهوية بدل إعادة إنشاء البيانات أو الاحتفاظ بمحركين. استعمال واجهات ترقية Odoo19 الرسمية إن كانت متاحة ومناسبة ومثبتة، وإلا محول محدد ومراجع ومختبر، لا كتابة QA يدوية أو إعادة تسمية الجداول فقط. عقود العميل القديم وما يلزم بقاؤه مؤقتًا تعزل صراحة. لا تغيير endpoint/namespace أو مفتاح كاش دون منتج/مستهلك وترحيل مثبتين.

خطر تشغيل مثبت: غلافا QA/production الحاليان يربطان حارس المصدر باسم ومسار `baseer_bchat`. تغيير اسم الموديول وحده قد يُسقط استدعاء الحارس. يجب إثبات مسار نشر محمي للتسمية الجديدة وتحديث control-plane المطلوب بصورة معتمدة؛ لا يتجاوز التنفيذ الشرط أو يعدّل root-owned wrapper حيًا يدويًا. يمنع هذا الخطر إعلان مرشح قابل للنشر قبل إغلاقه.

## G3 — الرصة والفحوص (مسودة)

لا حزمة أو UI أو قاعدة بيانات جديدة. تبقى Odoo19/PostgreSQL/React Native وملفات الأقفال والثيم/القواميس الحالية. الحصر من Git والمسارات المعمارية؛ المراجع الخارجية الرسمية فقط لتفاصيل rename/upgrade المتغيرة أو الدقيقة. لا بناء APK أو تشغيل تحديث بيانات خارجية في مرحلة الحصر. فحوص native migration/fresh install وruntime/replay والصلاحيات والشركات والتخزين ومعاينة AR/EN إن تأثرت النصوص هي دليل قبول جديد؛ يعاد استخدام الأدلة غير المتغيرة مع ربطها بالمصدر، لا ادعاء نجاح commit جديد بالفحوص القديمة.

G4: لا إعادة تصميم؛ مكونات BWork المركزية والقاموس AR/EN وRTL/LTR نفسها. تثبت سلامة العرض الضيق عند تغيير أسماء يراها المستخدم فقط. سياسة الكسور والحسابات والأسعار والأرقام0–9 غير متأثرة؛ لا يعاد تنفيذها في الواجهة.

قرار client/API: الجديد مع الجديد يستعمل المسار canonical؛ القديم مع الخادم الجديد يستعمل aliases مصادقة تستدعي **الخدمة نفسها** بنفس IDs/UUID/ACL/الشركات/CSRF، دون dual-writer. العميل الجديد مع الخادم القديم غير متوافق صراحة إذا أعاد canonical bootstrap حالة404/405: رسالة محلية تطلب تحديث الخادم، ولا POST fallback أو حذف هوية/كاش/طابور أو تجديد مهلة offline. يبقى `odoo-chat/v1` و`odoo-chat-media` فعليًا في مالك توافق مسمى؛ لا نقل مسارات لاسم فقط، وتظل URI/stage/UUID/ACK/pins/highwater كما هي.

قرار حارس CI: تشغيل canonical واحد، وجسر status باسم الفحص القديم يحتاج نجاحًا فعليًا من التشغيل canonical في head/event نفسيهما؛ لا نجاح عند skip/cancel/failure أو تخطي path filter. يتقاعد الجسر بعد تفويض نقل required check في GitHub، ولا تتغير حماية main هنا. قراءة history تستخدم mapping صريحًا لمسار registry القديم والجديد، وتتحقق من ثبات IDs/scopes/suites والتغطية؛ غياب المسار الجديد في base ليس إذنًا لتخطي المرجع.

## سجل البوابات

### BCR-021 — مسار التثبيت الجديد وشهادة التحويل

اعتمدت المراجعة المستقلة ملحق G2 محدودًا: `--pre-upgrade-scripts` لا يعمل مع `-i` وحده، لذلك لا نضيف `-u base` ولا نشغّل ترحيلًا وهميًا. التثبيت الجديد canonical يستخدم `post_init_hook` لشهادة metadata-only عبر SQL للموديول الأساسي فقط، بعد إثبات غياب الأسماء القديمة والأيتام والتصادمات. تربط الشهادة الخريطة وبصمتها ونوع fresh ونطاق core الفعلي، ولا تدعي اكتمال admin/procurement/الحارسين قبل تحميلهما، ولا تمنح صلاحيات أو تغيّر أعمالًا أو تفعّل الاحتفاظ. الترقية اللاحقة تعيد فحص نطاق الموديولات المثبتة فعلًا، لا الثقة بالـledger وحده. يلزم إثبات fresh→next-upgrade/no-op وorphan STOP معزولًا قبل G5. يبقى old-installed على المدخل السابق للـregistry بعد النسخة الاحتياطية وإيقاف العمال.

### قرارات إغلاق التصميم المحلي — ملحق لاحق

اختار المالك تطبيق BWork إنتاجيًا مستقلًا عن QA. هوية الإنتاج المرشحة `com.baseer.bwork`، وتوقيع release مخصص مطلوب: يفشل بناء/نشر الإنتاج عند غياب إعداد توقيع معتمد، ولا يرجع إلى Debug أو مفتاح QA. لا إنشاء أسرار أو نشر حزمة هنا. تبقى هوية الحزمة التجريبية الحالية وتوقيعها ومخازنها صالحة لتحديث QA؛ لا cross-container import أو نسخ قاعدة QA إلى Live. نص السؤال السابق يبقى في الدفتر كتاريخ، وقد أُغلق بهذا القرار.

- أسماء core/bridge والنماذج والجداول والحقول وXMLIDs المحلية canonical؛ لا ORM model أو addon قديم ثانٍ. كل collision أو mixed/partial state غير مثبت أو orphan أو فقد مرجع يفشل قبل الكتابة؛ لا دمج سجلات ولا uninstall/reinstall.

- المفتاح القديم `baseer_bchat.retention_ready` ينقل إلى المفتاح canonical نفسه بقيمة/غياب مكافئين مع رفض وجود المفتاحين. value1 أو سياسة مفعلة أو عملية queued/running تمنع الترحيل؛ لا تحويل ON إلى OFF بصمت، ولا تفعيل أو تنظيف أو إرسال أثناء المحول.
- bootstrap محدد SQL-only في معاملة مستقلة بلا commit داخلي، يستخدم `--pre-upgrade-scripts` المثبت في مصدر Odoo19 الرسمي قبل registry/module graph؛ لا يعتمد حزمة upgrade-util غير مثبتة ولا helper قد يلتزم أو يسقط قيودًا. صورة الاختبار الحالية مثبتة `odoo@sha256:f99ffac95cb39a0924622ea4118481c95651d9c84187e5b30a21c2cc4419c7dd` وPostgreSQL المثبت نفسه. التنفيذ المعزول لهذا المدخل هو شرط G5 وليس ادعاءً سابقًا له.
- المحول يستعمل lock ثابتًا وmapping ledger وpostconditions: old-only يرحل مرة، verified new-only no-op، collision/mixed/ledger mismatch STOP. لا يسقط PK/FK/unique/check ولا يغير OIDs/row IDs أو المرفقات. تحفظ الأسماء canonical المسبقة للجداول M2M. يحدّث سجل module/dependency/metadata/generic references قبل تحميل المصدر الجديد، ويغطي الاختبار attachment/mail/reference/field/XMLID والعلاقات الخاصة.
- الترقية الكاملة لأودو ليست ذرية؛ loader قد يلتزم لكل موديول. لا يفتح التطبيق قبل اكتمال المطابقة، وفشل بعد الالتزام يستدعي زوج backup+filestore ومصدره المطابق، لا code rollback أو inverse SQL غير مثبت.
- تغيير الغلافين في المصدر جزء صريح من المرشح: اختيار guard قديم أو canonical بقائمة ثابتة، رفض وجود الاثنين أو غياب الحارس، تصنيف renamed installed كـupgrade وfresh كـinstall، ومدخل bootstrap محدد فقط. لا shell حر أو policy توسع تبعيات. تثبيت الغلاف root-owned وتشغيله على QA/Live خارج التفويض، لذلك لا إعلان deployable GO حتى اعتماد مسار control-plane لاحقًا.
- حارس history يقرأ المرجع القديم المربوط صراحة عند انتقال المسار، ويقارن نفس invariant IDs/scopes/suites بعد تطبيع خريطة الاسم وحدها؛ لا bootstrap-skip لمرجع مفقود. حماية الفرع الحالية تبقى، وجسر context القديم لا ينجح إلا مع نجاح canonical الفعلي.
