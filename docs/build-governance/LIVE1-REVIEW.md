## Minimal contract for destination integration

1. **Initial migration only:** identify the exact host, DB name, empty target storage and source manifest. Check the target exists/contains data before any write; an existing nonempty or unrecognized target aborts without deleting, cleaning or recreating it. Under a deployment lock and a short source write freeze, take the final coherent original-MAIN DB+filestore backup, transfer privately with digest verification, restore both, reconcile business records and attachment references, and validate the candidate before admitting traffic. Transfer no QA database or fixture. Preserve the source snapshot until acceptance.
2. **Authority after cutover:** the live DB becomes authoritative. Disable the old writable operational entry point so two divergent copies cannot accumulate transactions. Later code updates must never overwrite live DB/filestore from local copies. Fresh development copies, if needed, are a separate controlled process.
3. **Code releases:** build and verify an immutable commit/artifact, serialize deployments, verify expected installed versions and destination identity, back up the live DB/filestore coherently, update only declared changed modules, then check health, module state and critical affected behavior. For changes that intentionally alter data, review the declared migration effect; do not force a universal zero-delta guard that would misrepresent a legitimate migration.
4. **Recovery:** a failed migration does not justify an automatic old-code restart against newer schema. Keep maintenance active and select a compatible recovery using the saved database/filestore/source bundle. Once live writes resume, restoring an older snapshot would lose those writes and requires a distinct assessed recovery plan. Backup retention and off-host storage must be explicit, with restore evidence and no destructive default.
5. **GitHub boundary:** export source/templates only, keep deployment credentials in environment secrets or host-controlled storage, pin actions, minimize token/SSH privileges, verify SSH host keys and serialize the production workflow. Deploy only trusted accepted-branch commits after checks; do not expose deployment secrets to untrusted pull requests or publish unfinished local saves. User-authorized automation can run without a new manual confirmation for each ordinary tested release.

Official reference checks support HTTPS/proxy/database-selection requirements and CI privilege isolation: [Odoo19 deployment source](https://github.com/odoo/documentation/blob/19.0/content/administration/on_premise/deploy.rst), [GitHub Actions secure use](https://docs.github.com/en/actions/reference/security/secure-use). These references guide the new hosting boundary; they do not replace inspection of the eventual target.
