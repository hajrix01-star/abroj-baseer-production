# عقد بناء: ربط عدة فئات نقاط بيع بطابعة تحضير واحدة

**البيئة المستهدفة:** QA أولاً. لا ترقية للأصلية ضمن هذا العقد.

## G0 — الحوكمة وعقد البناء

### الهدف

تجميع فئات نقاط البيع الفرعية التي تتجه إلى الطابعة نفسها في سطر إعداد واحد، مع زر اختبار واضح لكل طابعة تحضير. لا يغيّر ذلك مالك الطباعة: أودو يظل مصدر مسار المهمة، ووكيل Windows يظل منفذها فقط.

### المستخدم والرحلات

المستخدم هو مسؤول نقطة البيع. يفتح إعداد الطباعة، يختار عدة فئات فرعية (مثل بيتزا ومعجنات) في سطر واحد، يختار طابعة المطبخ، ثم يحفظ ويشغّل اختبار طابعة المطبخ. عند إرسال المطبخ، تتجه كل فئة مختارة إلى الطابعة نفسها.

### النطاق

- إضافة حقل اختيار متعدد `pos_category_ids` لمسار التحضير، مع إبقاء `pos_category_id` مصدراً تاريخياً مؤقتاً لا يُستخدم في التوجيه الجديد.
- ترحيل الربوط القائمة بأمان إلى الصيغة الجديدة عند ترقية الموديول، مع فحص مسبق يوقف الترقية عند وجود تداخل تاريخي بدلاً من اختيار وجهة صامتة.
- منع الفئة نفسها من الارتباط بمساري تحضير نشطين في نقطة البيع نفسها.
- زر اختبار لطابعة مسار التحضير، بلا طلب أو عملية مالية.
- الحفاظ على التوجيه المجمد للمهام التي أُنشئت سابقاً.

### خريطة مرشح التسليم

```mermaid
flowchart LR
    A[إعداد نقطة البيع<br/>فئات فرعية صريحة] --> B[baseer.print.route<br/>تحقق وقفل معاملاتي]
    B --> C[اختيار توجيه الخادم]
    C --> D[baseer.print.job<br/>وجهة مجمدة]
    D --> E[وكيل Windows]
    E --> F[طابعة المطبخ]
```

**مثبت بالدليل:** اختيار التوجيه في `models/route.py`، ومهمة الطباعة والوكيل القائمان في الموديول نفسه.
**خارج النطاق:** الإيصال والدفع والمخزون والحسابات وإعدادات Windows؛ لا يمر أي منها عبر هذا التغيير.

### خارج النطاق

- لا تغيير للإيصالات أو الدفع أو الضرائب أو القيود أو المخزون أو صلاحيات نقاط البيع.
- لا تغيير لعقود الوكيل أو بروتوكول الطباعة أو إعدادات طابعات Windows.
- لا نشر إلى الأصلية قبل اختبار QA ومراجعة تسليم مستقلة.

### معايير القبول

1. يمكن اختيار عدة فئات في سطر تحضير واحد على سطح المكتب والجوال.
2. لا يمكن حفظ فئة في مسارين نشطين لنقطة البيع نفسها.
3. تستمر الربوط المفردة التاريخية بعد الترقية ولا تفقد وجهتها.
4. ترسل فئة فرعية مختارة إلى الطابعة المعينة؛ والفئة غير المختارة لا تتجه إليها إلا عبر مسار افتراضي صريح.
5. ينشئ زر الاختبار مهمة `test` للطابعة المختارة فقط، ولا يغيّر أي طلب أو جلسة أو بيانات مالية.

### الافتراضات

- عدد الفئات في نقطة البيع محدود عملياً (عشرات لا آلاف).
- يمكن أن تتشارك فئات متعددة طابعة واحدة، لكن الفئة لا تملك إلا وجهة تحضير نشطة واحدة لكل نقطة بيع.
- الواجهة الحالية لأودو 19 تتيح Many2many tags/native selection ولا نحتاج مكتبة جديدة.

## G1 — السعة والاستمرارية

الرحلة الحرجة هي حفظ مسار تحضير ثم اختيار مسار إرسال الطبق. السعة المستهدفة: حتى 100 فئة نشطة و20 مساراً لكل نقطة بيع، و10 مسؤولين متزامنين كحد محافظ. القراءة تظل نطاقاً محدوداً حسب نقطة البيع؛ لا queue أو خدمة أو فهرس جديد مطلوب. التزامن يحسمه تحقق خادمي وunique/بحث متداخل قبل الحفظ. تبقى المهام المنشأة ذات الوجهة الملتقطة؛ تعديل الربط لاحقاً لا يعيد توجيهها.

**الرجوع:** لا يسمح بتخفيض الموديول وحده، لأن الإصدار السابق لا يقرأ الربط متعدد الفئات. قبل أي ترقية QA أو أصلية، ينشئ غلاف النشر زوج استرجاع متسقاً: قاعدة البيانات + filestore + معرف إصدار المصدر. الرجوع المعتمد هو استعادة الزوج السابق ثم إعادة تفعيل إصدار المصدر السابق؛ لا توجد عملية «ترقية عكسية» على قاعدة تغيرت. يثبت هذا المسار على QA قبل أي قرار للأصلية.

## G2 — المعمارية والعقد

```text
إعداد POS (فئات متعددة + طابعة واحدة)
        │ حفظ خادمي وتحقيق عدم التداخل
        ▼
مسار تحضير يملك Many2many للفئات
        │
طلب POS → فئات المنتج المباشرة → مسار واحد أو افتراضي صريح
        ▼
مهمة طباعة مجمدة الوجهة → وكيل Windows → طابعة Windows
```

- نموذج `baseer.print.route` هو مالك الربط؛ لا منطق توجيه في المتصفح.
- المطابقة تبقى مباشرة مع فئات المنتج؛ الفئة الأم لا تعني ضمنياً أبناءها حتى لا تظهر وجهة غير مرئية.
- ترقية schema تنسخ قيمة `pos_category_id` التاريخية إلى المجموعة الجديدة، ثم تستخدم المجموعة وحدها للقراءة الجديدة.
- التحقق من التداخل يتم خادمياً لكل فئة/نقطة بيع/مسار تحضير نشط عبر advisory lock ثابت لكل زوج (نقطة البيع، الفئة) قبل بحث التعارض وكتابته؛ لا تعتمد سلامة التزامن على `@api.constrains` وحده.
- لا يوجد إلا مسار افتراضي نشط واحد (بلا فئات) لكل نقطة بيع؛ الترقية تفحصه وتفشل برسالة قابلة للتصحيح عند وجود أكثر من واحد.
- لا أرقام تجارية أو محاسبية في هذه الرحلة، ولا تغيير في مصدر حقيقة Jobs.
- حمولة POS تبقى قائمة مسطحة آمنة من `{category_id, category_name}` لكل فئة مختارة، أو مدخل افتراضي واحد `false`؛ لا تمرر route أو printer أو agent إلى الكاشير.

## G3 — التقنية والمسار المباشر

نستخدم Odoo ORM وMany2many والـviews الحالية فقط؛ لا حزمة أو خدمة أو مكتبة واجهة جديدة. البديل (ترك سطر لكل فئة) يحقق الدقة لكنه يفشل في رحلة المسؤول المتكررة. البديل (ربط الفئة الأم وراثياً) غير مباشر وقد يرسل فئات غير مقصودة. الاختيار المباشر هو مجموعة فئات صريحة في السطر نفسه مع منع التداخل خادمياً.

## G4 — التجربة

- الحقل: **فئات نقاط البيع**، اختيار متعدد بالوسوم مع بحث.
- الطابعة تبقى في السطر نفسه مع نسخ وأولوية وحالة نشطة.
- الإجراء: **اختبار طابعة التحضير**، وتظهر نتيجته كـjob عادي يمكن تدقيقه.
- العربية والإنجليزية من ترجمة الموديول الحالية، وRTL/LTR وجوال/سطح مكتب عبر widgets أودو الأصلية.

## مصفوفة تحقق G5

1. ترحيل رابط مفرد نشط/غير نشط والافتراضي، وإعادة تشغيله بلا تكرار؛ فشل واضح عند تداخل تاريخي أو أكثر من افتراضي نشط.
2. فئتان في مسار واحد تتجهان للطابعة ذاتها؛ افتراضي للفئة الثالثة؛ لا وراثة تلقائية من الأب إلى الابن.
3. رفض التداخل عند الإنشاء والتعديل والتفعيل، وعبر معاملتين متزامنتين؛ يسمح بالتداخل غير النشط وبنقاط بيع أخرى.
4. مهمة تم إرسالها قبل التعديل تحتفظ بالطابعة والنسخ، بينما الخط الجديد يقرأ الربط الجديد.
5. واجهة tags وحمولة POS المسطحة وترجمة الزر، مع دخان عرض ضيق.
6. زر اختبار المسار ينشئ مهمة اختبار واحدة للطابعة الصحيحة ولا يغير طلباً أو جلسة أو دفعة، ويرفض الطابعة غير النشطة أو غير المصرح بها.
