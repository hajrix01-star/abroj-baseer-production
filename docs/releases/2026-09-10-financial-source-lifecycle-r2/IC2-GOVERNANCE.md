## Independent G0–G4 gate decision

Decision: G0, G1, G2, G3 and G4 approved for the bounded IC2 implementation below. Reviewer: icons_release. This is design approval, not implementation or release acceptance. No application code or MAIN records were changed by this reviewer.

G0: cancellation means correcting erroneous bookkeeping with an explicit preview and acknowledgement; it never asserts that real money was refunded. If the recorded payment reflects a real movement, this cancellation path must explain the native credit/refund alternative rather than silently remove that movement. No automatic repair of existing MAIN records is authorized by deployment. Per-row batch cancellation and summary edit/cancel are required; whole-batch cancellation is optional and must be clearly omitted if not implemented. If provided, it is one atomic, prevalidated operation and must not partially cancel a batch.

G1: retain bounded, indexed source resolution and existing row/method limits. Competing edit/cancel must serialize on the same owning source and accounting graph; stale or duplicate requests must not create a second lifecycle transition or leave a partial result. Measure only the implemented bounded cases. Avoid all-history lookups, broad financial retesting of unchanged releases and unnecessary infrastructure.

G2: native ORM remains authoritative. Ordinary native invoice/payment cancellation is acceptable only after proving the exact supported states, cancelled posting exclusion and resulting residual/cash-report behavior; it must not generate a fictitious incoming cash line. Resolve an already-cancelled invoice's payment from its native invoice relation, preserved owned link and reconciliation graph, merging evidence and rejecting conflicting, shared or ambiguous candidates. Preserve document IDs/history as appropriate; do not infer actual paid amount from the invoice total or clear a real relationship merely to pass eligibility. Active batch totals exclude cancelled rows while original row values, document links and audit remain visible. Summary editing reverses the original and validates/posts the replacement atomically through the existing source engine; cancelling makes no replacement. Exact native reversal checks, external-settlement refusal, date locks and current privacy remain mandatory.

Source-owned financial guards must cover direct native reset/cancel/reverse and financial write/create/unlink paths on linked invoices, payments and move lines, including caller-supplied defaults and attempts to remove/reassign ownership links. Any internal exception uses an unforgeable Python capability scoped to the already validated source and operation; no broad client context flag or sudo financial mutation. Preserve ordinary native reconciliation and approval. Apply the existing correction toggle and unconditional cashier denial both at shared entries and the old source-specific correction path, with a recheck during confirmation; adapting the summary access hook must not grant broad POS/accounting manager membership or expose payroll.

G3/G4: extend the installed correction addon and the minimal reviewed summary hooks only; no Odoo core patch/library. Reuse native fields, forms and responsive list/kanban, source-specific reason/errors, explicit payment effect and default edit mode. Source, accounting, payment and immutable audit changes belong to one transaction; an injected failure after posting/reversal must restore all of them. Actual Arabic/English and 480px evidence remains required.

Final acceptance must include the declared accounting/parity and permissions/bypass cases, a cancelled-invoice/posted-payment fixture, cancellation after partial payment, summary cash/bank/apps edit and cancel, retained row/history with accurate active totals, and source-conflicting concurrency. Unsupported states must fail before mutation. Exact candidate review and protected MAIN/source-only publication checks remain separate required release steps.
