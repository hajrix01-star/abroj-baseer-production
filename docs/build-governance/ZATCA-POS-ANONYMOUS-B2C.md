# عقد بناء: بيع POS للمستهلك بلا اختيار عميل مع زاتكا

**النطاق:** QA فقط أولاً. لا تغيير في اللايف أو الشهادات أو بيانات الفواتير القائمة.

## G0 — الحوكمة وعقد البناء

**الحالة:** معتمدة لـQA

### الهدف

تمكين الكاشير من إنهاء بيع المستهلك في نقاط البيع من دون اختيار سجل عميل، مع أي طريقة دفع متاحة، مع بقاء الفاتورة مبسطة وترحيلها عبر مسار ZATCA الحالي. الفاتورة المطلوبة باسم منشأة أو عميل معيّن تبقى رحلة اختيار العميل المعتادة.

### سبب التغيير المثبت

موديول أودو الرسمي `l10n_sa_edi_pos` يجعل كل طلب سعودي منتظماً `to_invoice=True`. تحقق الدفع القياسي في `point_of_sale` يرفض الطلب المفوتر بلا `partner`. هذان الملفان من مستودع Odoo الرسمي غير المعدل محلياً. زاتكا تذكر أن الفاتورة المبسطة B2C لا تتضمن عادة بيانات المشتري؛ القيد الحالي إذن قيد واجهة/تكامل أودو، وليس وجوب جمع بيانات المستهلك.

### داخل النطاق

- إعداد صريح لكل نقطة بيع، مغلق افتراضياً، يسمح ببيع B2C غير المسمّى.
- سجل «مستهلك نقدي» داخلي لكل شركة/نقطة بيع يختاره النظام فقط عند الدفع إذا لم يختَر الكاشير عميلاً.
- إبقاء `to_invoice=True` ومسار إنشاء `account.move` وEDI وزاتكا كما هو.
- اختبار QA لكل طريقة دفع متاحة، مع/بدون عميل، والتحقق من حالة EDI ومحاكاة زاتكا قبل أي اقتراح للايف.

### خارج النطاق

- لا تعديل في Odoo core أو موديول `l10n_sa_edi_pos` الرسمي.
- لا تعطيل للفوترة أو إرسال زاتكا أو تغيير شهادة أو OTP أو بيئة الإنتاج.
- لا تعديل فواتير/طلبات سابقة ولا تغيير طرق الدفع أو دفاترها.
- لا شحن، تسوية ذمم، مرتجعات، أو فواتير B2B ضمن هذه الشريحة الأولى.

### معايير القبول

1. عند تفعيل الإعداد لنقطة بيع QA، بيع عادي بلا اختيار عميل يكتمل لكل طريقة دفع مفعلة ويُنشئ فاتورة مبسطة وEDI صالحاً.
2. اختيار فرد أو منشأة يبقى كما هو؛ لا يُستبدل العميل المختار.
3. عند إيقاف الإعداد أو غياب سجل المستهلك الداخلي، يبقى رفض أودو القياسي بلا عميل كما هو.
4. لا يتغير حساب مبلغ/ضريبة/دفتر أو تسوية الدفع؛ مصدر الحقيقة يبقى ORM أودو.
5. لا تعتبر تجربة QA إثبات امتثال للايف حتى قبول محاكاة زاتكا ومراجعة مستقلة.

### خريطة الدورة والرقابة المحاسبية

`طلب POS` → `دفع` → (عند عدم وجود عميل ومع تفعيل صريح: إسناد سجل مستهلك داخلي) → `فاتورة أودو` → `EDI/ZATCA` → `إيصال`.

لا يُنشئ التعديل قيداً أو ضريبة أو مبلغاً. إنشاء الفاتورة، الترحيل، ومنع التكرار وإرسال EDI تبقى عند Odoo. بعد الترحيل لا يعدّل التعديل الفاتورة؛ التصحيح يبقى إشعار دائن/مدين أودو الأصلي.

### افتراضات يجب إثباتها في QA

- السجل الداخلي شخص (`company_type=person`) ولا يحمل VAT أو معلومات شخص حقيقي.
- زاتكا تقبل مستنداً مبسطاً ناتجاً عن المسار، أو تُظهر سبب الرفض القابل للعلاج.
- لا تسري الشريحة على شحن/تسوية/طلب مؤجل؛ هذه تظل آمنة بالسلوك الأصلي.

## G1 — ملف السعة والنمو

**الحالة:** معتمدة لـQA

| بند | تقدير التشغيل | قرار التصميم |
|---|---|---|
| الرحلة الحرجة | دفع POS ثم إنشاء فاتورة/EDI | لا RPC جديد ولا طابور جديد؛ يستعمل إنشاء الطلب القائم |
| التزامن | كاشيرات متزامنة محتملة | لا إنشاء عميل عند الدفع؛ سجل داخلي قائم ومقيّد بالنقطة/الشركة |
| نمو البيانات | طلب وفاتورة أصليان لكل بيع | لا نموذج حركات جديد ولا سجل شخصي إضافي لكل بيع |
| الأداء | لا زيادة في خطوات الكاشير | الإسناد محلي في كائن الطلب قبل التحقق القياسي؛ لا بحث غير محدود |
| الاستمرارية | أخطاء EDI تظهر في المسار الأصلي | لا retry مخصص ولا إخفاء أخطاء زاتكا |

لا يتطلب هذا الفارق اختبار حمل جديد: لا يضيف رحلة شبكة أو استعلاماً جماعياً؛ الخطر غير المغطى هو سلامة الفاتورة/EDI، ويغطيه اختبار QA المتحكم به لكل طريقة دفع.

## G2 — المعمارية والعقد

**الحالة:** معتمدة لـQA

### العقد

- موديل `pos.config`: `baseer_zatca_allow_anonymous_b2c` (افتراضي `False`) و`baseer_zatca_anonymous_partner_id`.
- شرط الإسناد: شركة سعودية، بيع عادي غير شحن/تسوية، `to_invoice=True`، لا عميل مختار، الإعداد مفعّل والسجل الداخلي من نفس الشركة.
- عند غياب أي شرط، لا يتدخل الموديول.
- حماية خادمية على بيانات POS الواردة تكافئ الحماية في الواجهة، لمنع تجاوز شرط الإعداد عبر RPC.

### منع التكرار والصلاحيات

لا ينشئ مسار الدفع سجلات عملاء. مسؤول النظام وحده يغير الإعداد/السجل؛ أمين الصندوق لا يملك صلاحية تغييرهما. طلب POS يحتفظ بعميله الأصلي أو السجل الداخلي مرة واحدة، ويظل منع التكرار والذرية عند Odoo.

## G3 — التقنية والمكتبات

**الحالة:** معتمدة لـQA

- موديول Baseer صغير مستقل يعتمد على `l10n_sa_edi_pos` و`point_of_sale`؛ لا تعديل core ولا مكتبات أو خدمات أو API جديدة.
- بديل مرفوض: إلغاء `to_invoice`؛ لأنه يفصل الطلب عن مسار الفاتورة/EDI الحالي.
- بديل مرفوض: إنشاء عميل جديد لكل بيع؛ لأنه يلوث بيانات العملاء ويزيد مخاطر التكرار.
- المسار المباشر: إعداد opt-in + سجل داخلي ثابت + حماية واجهة وخادم بالحد الأدنى.

## G4 — التجربة

**الحالة:** معتمدة لـQA

لا شاشة كاشير جديدة ولا حركة. تسمية الإعداد بالعربية والإنجليزية، ولا يظهر سجل المستهلك كإجراء مطلوب للكاشير. عند تعطيل الإعداد تبقى رسالة أودو الأصلية. الاختبار يشمل واجهة عربية ضيقة وسطح مكتب.

## سجل القرارات

|---|---|---|
| الإعداد لكل POS ومغلق افتراضياً | تفعيل عالمي أو تعديل core | أقل أثر ويحمي الشركات غير المهيأة |
| سجل داخلي ثابت | لا عميل أو عميل جديد لكل بيع | Odoo يحتاج partner لإنشاء فاتورة؛ الثابت يمنع تضخم البيانات |
| الإبقاء على `to_invoice` | تعطيل الفاتورة | يحافظ على الفاتورة وEDI وزاتكا |
