# Independent security, authorization and compatibility audit

Date: 2026-09-09. Scope: frozen candidate in `candidate.json`, Odoo 19 runtime in `baseer_odoo_dev-reports_qa-1`, exclusive disposable database `baseer_audit_security_20260909`. This is an audit report, not permission to change or deploy the application.

**Decision for this discipline: NOT READY.** Two P1 findings require correction: a Payroll Officer can read confidential child rows of a payslip whose parent access is denied, and an ordinary invoice operator cannot complete service category/supplier onchanges in purchase entry. A P2 vendor contribution report is also broken. Root's source/runtime comparison establishes a further P2 reproducibility issue. No source changes were made. No unauthorized cross-company read was reproduced in the tested paths.

## Findings

### SECURITY-001 — P1 — Payroll Officer reads restricted payslip details through child models

- **Status:** confirmed, open. **Owner:** Baseer payroll integration/security owner; inherited defect originates in Odoo Mates access design.
- **Source:** `third_party_addons/odoomates_19/om_hr_payroll/security/hr_payroll_security.xml:27` limits the Officer's parent payslip to self, employees without a department, or employees in a department managed by that officer. Child ACLs at `third_party_addons/odoomates_19/om_hr_payroll/security/ir.model.access.csv:7` grant the Officer read access. `custom_addons/baseer_payroll/security/security.xml:11`, `:12`, `:13` add company rules for lines, inputs and worked days but do not carry the parent's employee/department restriction.
- **Trigger:** an internal user with Payroll Officer, without Payroll Manager, selects or guesses an unrelated department's payslip/child identifiers. The fixture employee belongs to a department with no relationship to the attacker; it is not covered by the vendor's no-department exception.
- **Expected:** the scope of payslip child reads matches the scope of readable parent payslips. An inaccessible parent's detailed salary, input bonuses and attendance must not be returned by child `read` or `search_read`.
- **Actual:** `hr.payslip.read([restricted_id], ['name'])` raises AccessError. In the same user environment, child `read` and `search_read` return salary line amount/total **12345.67**, bonus input **765.43**, and worked days/hours **23.5/188**. A read of `hr.version.wage` is denied, making the child route an actual bypass of the visible salary boundary.
- **Impact:** confidential intra-company pay and attendance data is exposed to an officer who is explicitly prevented from reading the parent payslip. This is an authorization defect, not merely a proposed role policy.
- **Evidence:** first matrix `officer_cannot_read_unrelated_department_parent` passes; the three `officer_cannot_read_restricted_child_*` assertions fail and corresponding `restricted_child_search_read_*` observations contain the synthetic data. Second matrix captures the actual installed rules, not only XML source.
- **Fix proposal:** add child read rules reflecting the current parent officer rule, plus the corresponding manager allowance, while retaining the global company restriction. Alternatively enforce parent read scope centrally for child searches/reads using an Odoo-compatible rule domain. Validate manager, self, managed department, no-department policy, unrelated department, and foreign company through both `read` and `search_read`/exports. Avoid merely hiding fields in views.
- **Limits:** ordinary HR without Payroll Officer cannot read these child models; child writes by the Officer were denied. Foreign-company child direct reads were denied and search returned no rows. No cross-company leakage is claimed. The vendor no-department exception is an explicit broader policy and is not the trigger used here.

### SECURITY-002 — P1 — Service purchase defaults and onchanges require Access Rights administration

- **Status:** confirmed, open. **Owner:** `baseer_service_seed` owner.
- **Source:** `custom_addons/baseer_service_seed/models/purchase_batch.py:12` calls `ir.model.data.search_count` in the caller's environment. The helper is reached by category onchange at `:19`, partner-default onchange at `:25`, and omitted entry-type creation at `:31`.
- **Trigger:** a normal internal Invoice user, with the native rights that permit purchase-batch creation, selects a service category or a supplier whose company-specific default points to that category. The user does not have the Access Rights administration group.
- **Expected:** service detection reads trusted catalog identity metadata without requiring the operator to administer model data. The category/partner onchange should propose Expense; omitted `entry_type` should obtain its supported server default.
- **Actual:** native `call_kw(..., 'onchange', ...)` fails for both `category_map_id` and `partner_id` with AccessError on `ir.model.data`. Creating a batch with either an explicit service category or a supplier-derived category and omitted `entry_type` fails the same way. A control request with **explicit `entry_type='expense'` succeeds**, proving the user has batch access and isolating the failed metadata lookup.
- **Impact/severity rationale:** the ordinary employee's primary service-purchase entry path is blocked at interactive supplier/category selection. It cannot be resolved by giving broad Access Rights administration to accounting operators. This is a workflow availability/authorization integration failure, not a data disclosure.
- **Evidence:** second matrix's four failed checks: `invoice_operator_can_create_with_service_default`, `invoice_operator_supplier_default_category_create_works`, `invoice_operator_onchange_category_map_id_works`, `invoice_operator_onchange_partner_id_works`; the explicit-entry-type control passes. The supplier default mapping is an audit-only fixture and is rolled back.
- **Fix proposal:** resolve the predefined catalog identities through a private, narrowly elevated metadata-only lookup or known XMLID resolution, after normal mapping/company access is established. Do not sudo the batch, supplier, financial records or caller. Retest a real non-admin native form plus both direct create variants. Add these cases to the existing operator acceptance suite; admin-only or non-service category tests miss this failure.
- **Limits:** no UI screenshot was captured in this subtask; the exact public native onchange method used by the web client was invoked through Odoo RPC dispatch. A prefilled explicit entry-type API request succeeds, but the interactive onchange still fails. No finance rows persisted from failed tests.

### SECURITY-003 — P2 — Vendor contribution-register report has incorrect module identifiers

- **Status:** confirmed, open. **Owner:** third-party Odoo Mates compatibility/integration owner.
- **Source:** `third_party_addons/odoomates_19/om_hr_payroll/wizard/hr_payroll_contribution_register_report.py:23` references `om_om_hr_payroll.action_contribution_register`. The real action is defined at `third_party_addons/odoomates_19/om_hr_payroll/views/hr_payroll_report.xml:4` under `om_hr_payroll`. The Python report handler at `third_party_addons/odoomates_19/om_hr_payroll/report/report_contribution_register.py:9` also has the erroneous `report.om_om_hr_payroll...` model name.
- **Trigger:** Payroll Officer creates the native contribution-register date wizard and invokes its `print_report` RPC.
- **Expected:** return the installed native report action, with a report handler that matches its `report_name`.
- **Actual:** `ValueError: External ID not found in the system: om_om_hr_payroll.action_contribution_register`. Registry observation confirms expected handler model absent and typo handler model present.
- **Impact:** the installed external contribution-report journey cannot print. This is separate from Baseer's monthly payslip/settlement report and is not evidence of wrong payroll calculation.
- **Evidence:** first matrix `vendor_contribution_report_action_resolves` and `vendor_contribution_handler_registry`.
- **Fix proposal:** correct both external-ID and report-model namespace references in a controlled integration fix; then verify native wizard invocation and full report rendering with actual register lines. Fixing only the XMLID leaves the handler mismatch.
- **Limits:** rendering was not reached because the public action failed first; no claim that correcting both identifiers alone completes all downstream compatibility work.

### SECURITY-004 — P2 — Native source checkout differs from the running Odoo build

- **Status:** confirmed operational/version issue from root's independent provenance audit; open. **Owner:** release/operations owner. Consolidate this with root's corresponding finding rather than counting it twice.
- **Source:** `compose.reports-qa.yaml:3` uses floating `odoo:19.0`; [core-provenance.json](core-provenance.json) and [core-native-runtime.diff](core-native-runtime.diff) compare the actual runtime with the local native checkout after line-ending normalization.
- **Trigger/actual:** reviewing local `odoo` sources as if they were the code executed by QA, or recreating QA after the floating image tag changes. Three of seven inspected critical native files differ: `orm/models.py`, `account_move.py`, `account_payment.py`. The local default relational-command access checks are absent from the running ORM in this comparison. Mounted custom/vendor files do match (1082 files), and Odoo Mates/Legion baseline files remain unchanged.
- **Expected/impact:** a frozen release identifies and reproduces the exact native engine, and audit source matches runtime. The saved actual digest identifies this audit but the floating compose tag does not preserve it on future pulls; conclusions based only on a different local checkout can be invalid.
- **Fix proposal:** pin the QA/release image digest and retain its native source identity or matching source archive; explicitly decide which patch level is the intended candidate and rerun behavior affected by any subsequent engine update.
- **Limits:** this is not a demonstrated exploit and no security impact is inferred merely from a missing source hunk. This report's findings use executed `call_kw` behavior in the actual clone. Root owns broader native diff assessment; no new native code was changed or deployed.

## Code quality, explicit policy and remaining limits

- The small addons remain appropriately separate: category display changes only category naming; navigation uses native menu/user services; the purchase date widget re-exports the layout owner's implementation rather than registering another widget; Legion compatibility is CSS-only. No cleanup rewrite is justified by this review.
- Financial workflows consistently prefer ORM, native invoices/payments and unforgeable Python object capabilities. The tested Boolean context forgeries did not confer authority. Approved HR/batch source controls are enforced server-side. Parameterized SQL and identifier-aware SQL composition were observed in reviewed locks/migration code; no untrusted SQL-string interpolation was found in this scan.
- The Payroll module uses compact multi-statement formatting and the vendor carries long blocks of commented historical implementations. These make reviews and upgrades harder, but are maintainability observations, not additional security defects. Keep any later cleanup separate from urgent behavioral fixes and preserve vendor provenance.
- POS users can confirm operating closures while only POS managers can cancel/archive them. Runtime confirms this behavior, which matches the documented chosen role policy; it is not labeled privilege escalation. HR users can read a narrow same-company linked-bill status/balance projection with sudo read, but native invoice content/action remains denied. Shared supplier identity is intentionally global while category/account properties and financial records remain scoped.
- No network message, WhatsApp send, secret-value inspection, deployment, QA/main database write, application change or privileged production action was performed by this reviewer. No HTTP authentication penetration test, dependency CVE certification, browser asset compilation, exhaustive inherited native RPC audit or fresh concurrency test is claimed here. Financial formulas and legal payroll policy were intentionally not reassessed in this subtask.
- Corrections remain unimplemented and require new frozen source/evidence plus independent retesting. In particular, successful financial regression tests as administrator cannot close SECURITY-001 or SECURITY-002.
