## G0 contract

Native POS app provides direct-sale entry and external-summary entry. Summary company defaults active header, readonly/immutable; only its methods/config and authorized data. Summary has business date, ALL/MORNING/EVENING, external report reference, customer count, notes/attachment and up to25 native payment-method allocations. Amounts are gross including configured native sales tax. Cash/bank/apps classified by company-owned payment category. Service summary product means no inventory movement; customer count independent of synthetic order count. Parent summary approved only when one dedicated native POS order and session are posted/closed successfully. Platforms marked paid at POS into separate clearing balances, not fictitious bank cash. Commissions and clearing-to-bank transfers later use native accounting; transfers never create sales again. No hidden sends: WhatsApp Web opens a prepared persisted-summary message, employee selects conversation and sends. Re-sharing does not repost. No AI/API/library/recurring job.

## G1 capacity and operational limits

At most25 methods per summary; gross max999999999.99 SAR with server Decimal validation before native ORM floats. Customer count integer0..10000000; division byzero shows0 rather than error. One ALL or distinct MORNING/EVENING per company/config/date; forbid overlapping ALL/shift entries. Source summary-config is dedicated and unavailable for ordinary cashier sessions; ordinary POS remains native. Company/config/date indexed; source link unique/order/session as appropriate. Concurrent approvals use row/company serialization and idempotent return; shared config prevents parallel session conflict. Native account tables remain monetary authority. Measure1/10/25 method behavior in rollback QA, not production stress.

## G2 data and financial map

Native UI summary → validated company allocations → service pos.order.line + pos.payment records → dedicated pos.session close → native account.move/payment/statement records. Summary totals read native order; journal/payment/tax dates must equal business date (native hooks require verification; date_order alone insufficient). Locked dates, taxes, configuration, permissions, currency and exact gross reconciliation validated before final approval. Failed approval leaves no posted summary, order or cash partial state. No framework bypass or core monkeypatch. Approved summary immutable; original native documents remain linked. Corrections must use native reversal flow or controlled follow-up, no silent edit.

Summary reporting uses company/date/scope + native linked allocation values grouped by method category. Customer count/average computed once at summary grain; not multiplied by payment count. Cash-report adapter inherits existing handler in new addon, supplies evidenced POS-sale lineage on dedicated one-order-session receivable edge; does not rewrite oldcashaddon or treat clearing assets as cash. Cash total/reconciliation and tax exclude/unclassified semantics retained. Application balances displayed separately from actualbank receipts. All amount cells/actions link to original summary/order/financial evidence.
