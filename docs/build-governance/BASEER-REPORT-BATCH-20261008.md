# حزمة تقارير بصير — عقد التنفيذ الدفعي 2026-10-08

## الهدف وحدود الدفعة

يبني هذا العقد التقارير العشرة داخل المسار الواحد: **الفوترة ← التقارير ← تقارير
بصير**. تكون كل صفحة تقرير حقيقية من بيانات أودو المصرح بها، وبواجهة قراءة
مطابقة لسلوك تقرير Odoo القياسي: شريط فترة أصلي، مقارنة خادمية، فلاتر الشركة
والدفاتر، صفوف هرمية قابلة للتوسيع، وفتح التفاصيل المصرح بها. لا يغير أي تقرير
قيدًا أو فاتورة أو دفعة.

Excel مرحلة لاحقة مستقلة. يبقى PDF الموجود دون تعطيل، ولا يظهر زر تصدير جديد قبل
عقده وفحوصه الخاصة. يطبق PDF/A4 عند اكتمال كل تقرير بعد قبول مستقل، لا كزر صوري.

## دورة المال والرقابة

- المسودة أو عرض السعر أو طلب POS غير المعتمد لا يدخل أي تقرير مالي.
- P&L وGL وBalance Sheet وTrial Balance تقرأ قيودًا مرحّلة فقط، تحت ACL وقواعد
  السجل، ومن دون `sudo` أو إعادة حساب في JavaScript.
- العمليات الإجمالية تختلف عن التحصيل: البيع في تقرير العمليات بحدثه المعتمد؛
  الدفعة في تقرير المقبوضات/المدفوعات بحدث دفعها الحقيقي. لا تجمع كليهما ولا تجعل
  تخصيص تطبيق التوصيل قبضًا تلقائيًا.
- الذمم تعرض كل فاتورة مفتوحة كما هي عند تاريخ القطع؛ المقدمات والأرصدة الدائنة
  قسم منفصل ولا تخصم صامتًا.
- أي عكس أو إشعار دائن أو فرق عملة يظهر من مصدره المرحّل؛ لا يغيّر التقرير المستند.

## خطة الشرائح القابلة للنشر

1. **إغلاق P&L وGL:** فحوص CI الحقيقية، مراجعة مستقلة، ثم PR وسياسة QA محمية
   لكل موديول. لا دمج أو QA عند فشل/غياب الدليل.
2. **قالب الواجهة المشترك:** يستخرج فقط ما ثبت عموميته بعد نجاح التقريرين، مثل
   شريط الفترة/المقارنة وبناء الرأس؛ لا ينقل حاسبة مالية إلى العميل أو مكوّن عام.
3. **Balance Sheet وTrial Balance:** يثبت عقد تصنيف الحسابات/نتيجة السنة ثم
   يبنيان مع اختبار جسر التوازن بينهما وGL.
4. **الذمم:** عقدا العملاء والموردين المنفصلان، ثم اختبار الفاتورة الجزئية
   والإشعار الدائن والعملات والمقدمات وتاريخ القطع.
5. **العمليات والتحصيل:** لا يبدأ الحساب حتى يثبت جرد QA أن POS والفواتير
   والدفعات لا تتكرر وأن تاريخ كل حدث معلوم.
6. **VAT والتبغ:** مواءمة واجهة فقط مع الحفاظ على حاسباتهما الحالية، ثم قبول
   بصري منفصل.
7. **التصدير والطباعة:** بعد اكتمال كل تقرير، عقد PDF/A4 ثم Excel منفصل؛ لا تؤخر
   بناء التقرير الأساسي ولا تعيد حساب أرقامه في طبقة التصدير.

## البوابات والسعة

هذا العقد يوثق **مسودة G0/G1/G2/G3 للدفعة**، وليس إذنًا لحساب تقارير 5–10. كل
حاسبة تملك قرار G0–G3 مستقلًا ومراجعة مستقلة قبل كتابة كودها. الفرضية المبدئية
الموحدة: شركة واحدة لكل طلب، فترة محددة، صفحات خادمية، وقياس معزول قبل QA عند
100,000 سطر/5,000 حساب/10 قراء حيث ينطبق. لا حمل على QA أو الإنتاج.
