# BASEER-SMS-MOBILE-REBUILD-2026-09-27

## القرار والنطاق

- **المالك:** فريق بصير أودو. **البيئة:** QA فقط حتى اعتماد مرشح تسليم مستقل.
- **النطاق:** إعادة بناء تطبيق Android «بصير SMS» وعقد الصحة التشغيلي في
  `baseer_bank_sms` داخل أودو. لا يشمل هذا المرشح قيوداً، يوميات، دفعات، أو
  توجيهاً مالياً؛ الهاتف ينقل الدليل وأودو يحلل الرسالة فقط.
- **المشكلة المثبتة:** الهاتف المركب يعمل بالإصدار `1.0.2` ويعرض 1,400 رسالة
  معلقة وحالة مبهمة. المصدر المتاح `1.0.4` لا يثبت نبضة اتصال حية ولا يسجل سبب
  الفشل لكل رسالة. في QA استلم الخادم 789 رسالة؛ آخر رسالة مؤرخة من الهاتف لا
  تثبت استلام الرسائل الأحدث، فلا يجوز تسميتها «مُحللة ومفقودة».
- **الحفاظ على البيانات:** ترقية موضعية للتطبيق نفسه وتوقيعه نفسه لاحقاً؛ لا
  حذف ولا إعادة إنشاء لمفاتيح التكرار ولا إعادة ربط تلقائية. طابور الـ1,400
  يهاجر ذرّياً قبل أن يرسل أي صف.

## G0 — عقد النجاح والحواجز

| بند | عقد القبول |
| --- | --- |
| اتصال حي صادق | «متصل الآن» يظهر فقط بعد heartbeat مؤكد خلال 120 ثانية. دون ذلك تظهر حالة متدهورة/غير متصل، لا تخمين من فراغ الطابور. |
| سلامة الرسائل | كل رسالة لها حالة محلية: ملتقطة، انتظار، إرسال، مؤكدة، إعادة محاولة، محظورة أو تحتاج إصلاح. لا يحذف النص المشفر إلا بعد ACK صريح أو تكرار مؤكد. |
| التشخيص | آخر التقاط، آخر ACK، أقدم انتظار، رمز آخر فشل، الصلاحيات والبطارية والشبكة مرئية. لا يسجل نص SMS أو رقم حساب أو سر جهاز في diagnostics. |
| بيئات واضحة | QA وLive تعريفان منفصلان؛ الشارة والـpackage/QR لا تسمح بالخلط. هذا المرشح QA فقط. |
| عدم حجب الطابور | أخطاء 400 والسياسة والتوثيق تصبح حالات مستقلة ولا تحجب الرسائل السليمة اللاحقة. 429/5xx/الشبكة فقط تعيد المحاولة بمهلة. |
| السعة الأولية | جهاز QA واحد حالياً، تصميم قابل لخمسة أجهزة × 1,500 رسالة في الاختبار. دفعات بحد أقصى 50 ورسائل idempotent. لا ادعاء بسعة أكبر قبل G6. |

**قرار منصة الخلفية:** WorkManager للاستمرار والتعافي. المراقبة الحية الدقيقة
تتطلب خياراً صريحاً للمستخدم مع إشعار foreground ظاهر؛ لا نستعمله من الإقلاع أو
نعد باتصال دائم يخالف قيود Android. عند غياب هذا الخيار تعرض الواجهة «آخر تأكيد
من الخادم» بدلاً من «متصل الآن».

## G1 — مسارات الاستخدام والاستمرارية

1. التقاط SMS مفرد/متعدد الأجزاء وحفظه مشفراً في أقل وقت ممكن.
2. heartbeat مستقل عن الرسائل؛ يعرض بيئة QA وصحة الصلاحيات والطابور.
3. إرسال دفعات، ACK لكل مفتاح، retry قابل للاستئناف، وميزة استيراد فجوة محددة.
4. ترحيل `queue` الحالي مع 1,400 صف من دون حذف أو إعادة ترتيب غير قابلة للتدقيق.
5. إعادة pairing آمنة وتدوير السر من دون تسريب أو محو للطابور.

## G2 — المعمارية المعتمدة

```text
SMS_RECEIVED → intake + policy revision → encrypted local outbox
→ sync orchestrator (foreground monitoring اختياري / WorkManager fallback)
→ HTTPS v2 → Odoo QA inbox + device-health view
```

- Android هو مصدر حقيقة حالة الالتقاط والطابور؛ Odoo مصدر حقيقة قبول الرسالة
  وتحليلها فقط.
- API v2 يبقى بجانب v1: `heartbeat`، config بإصدار/ETag، وbatch messages <=50
  مع ACK لكل رسالة (`accepted`, `duplicate`, `blocked`, `retryable`).
- Odoo يحتفظ ببيانات صحة غير حساسة فقط: heartbeat، آخر ingest/ACK، إصدار التطبيق،
  أعداد الطابور ورمز الفشل. لا raw SMS في events أو السجلات.

## G3 — قرارات البناء والأمان

- لا مكتبة واجهة جديدة في الشريحة الأولى: Android Java/XML والمكونات الموجودة،
  مع design tokens ومكونات واجهة مشتركة. يمنع هذا مخاطرة تبعية غير لازمة.
- سر الجهاز يرحل من SharedPreferences إلى تخزين مشفر مدعوم بـAndroid Keystore؛
  يبقى مفتاح AES/GCM الحالي قابلاً للقراءة للطابور القديم.
- سياسة إرسال عادلة: لا `REPLACE` يلغي عامل إرسال؛ لا `catch` صامت؛ 401/403
  يحتاجان إصلاح pairing، 400/سياسة تصبحان blocked، و429/5xx/انقطاع الشبكة retry
  بتراجع أسي وjitter.
- لا certificate pinning قبل امتلاك دورة تدوير شهادة؛ TLS ورفض cleartext
  إلزاميان.
- شاشة التطبيق: الحالة، الرسائل، الفجوات، الإعدادات. تعرض الحالة الزمنية
  والصلاحيات وسبب الفشل، ولا تعرض نصوص رسائل في شاشة التشخيص.

## G4 — تصميم الاستخدام المعتمد

| الشاشة | ما يراه المستخدم | الإجراء الآمن |
| --- | --- | --- |
| الحالة | شارة QA، آخر heartbeat مؤكد، آخر SMS التقطها الهاتف، آخر ACK من QA، انتظار/مجدول/محظور، وأقدم رسالة معلقة | اختبار اتصال الآن، تشغيل مراقبة حية اختيارية، فتح سبب الفشل. |
| الرسائل | timeline للحالة والوقت ورمز السبب فقط؛ لا نص SMS داخل قائمة التشخيص | إعادة محاولة رسالة صالحة أو تصدير diagnostics آمن. |
| الفجوات | نافذة زمنية قابلة للتحديد وعدد الرسائل المكتشفة قبل الإرسال | فحص/استيراد النطاق المحدد؛ لا «مزامنة شهر» عمياء. |
| الإعدادات | البيئة والـdevice code بشكل مقنّع، صلاحيات SMS والشبكة/البطارية، إصدار قائمة المرسلين | إعادة pairing واعتماد مراقبة foreground بشكل صريح. |

**الحالات المرئية:** أخضر = heartbeat مؤكد خلال دقيقتين مع مراقبة حية مفعلة؛
أصفر = آخر تأكيد قديم أو WorkManager فقط؛ أحمر = لا اتصال/صلاحية/توثيق؛ رمادي =
غير مربوط. ولا تغيّر حالة القلب بمجرد عدم وجود رسالة. يستخدم التصميم كلمات واضحة
مثل «آخر تأكيد من QA» بدل «آخر مزامنة».

## مراجعة لجنة التحليل — 2026-09-27

### نتائج مثبتة

- لا تعني مزامنة سابقة أو فراغ الطابور اتصالاً حياً. العقد الوحيد المسموح لكلمة
  «متصل الآن» هو ردّ `heartbeat` موثّق حديثاً من الخادم؛ وتبقى الواجهة دقيقة
  بعرض «آخر تأكيد من QA» إن غاب ذلك الرد.
- يقطع `ExistingWorkPolicy.REPLACE` عامل إرسال قائم عند وصول رسالة أو طلب مزامنة.
  كما أن العمل الدوري يحمل اسماً مختلفاً، فيمكن أن يتوازى مع عمل الإرسال الفوري.
- الربط يقبل أي عنوان `https` من QR، كما تخزن بيانات الربط السرية في
  `SharedPreferences` غير مشفرة. لا يبدأ أي عميل جديد بتجميع SMS قبل ربط موثوق
  وموافقة صريحة، ولا يستبدل ربطاً قائماً من دون تأكيد المستخدم والتحقق من الجهة.
- أساس Odoo لا ينشئ قيوداً أو دفعات، ورسالة الدليل لها منع تكرار فريد في قاعدة
  البيانات. يبقى هذا حدّاً ثابتاً؛ فلا يصنع هذا العمل أثراً مالياً.
- `heartbeat` v2 يفصل حالياً عن وصول الرسائل، لكنه يحتاج عقداً كاملاً لنتيجة
  الدفعة، واختبارات HTTP، ومراقبة حالة عالقة/إنذار تشغيلي قبل ادعاء جاهزية لايف.

### G4 — مواصفة التجربة (مسودة قيد المراجعة)

- شاشة «الحالة»: شارة البيئة، حالة صادقة، آخر heartbeat مؤكد، **آخر رسالة
  مؤكدة في QA مع تاريخها ووقتها**، وأعداد حالات الطابور.
- شاشة «الرسائل»: قائمة خفيفة لحالات التسليم؛ لا تعرض محتوى SMS في القائمة أو
  التشخيص. يفتح المستخدم آخر رسالة فقط بعد مصادقة الجهاز/تأكيده، مع تمويه
  افتراضي للأرقام الحساسة.
- شاشة «الفجوات»: فحص/استيراد نطاق زمني محدد فقط؛ لا مزامنة شهر عمياء.
- شاشة «الإعدادات»: الربط والبيئة، قائمة المرسلين، الصلاحيات، البطارية، الفصل
  الآمن، وتصدير diagnostics منقّح. التطبيق ظاهر وقابل للإيقاف؛ لا إخفاء متعمد
  من قائمة التطبيقات.
- مبادئ الجودة: Java/XML ومكونات المنصة فقط في هذه الشريحة؛ حالة واحدة بارزة
  لكل صفحة، تسلسل بصري بسيط، دعم RTL/LTR، نصوص ثنائية اللغة، وأرقام غربية
  `0-9`. لا رسوم متحركة إلا لتغذية راجعة قصيرة ومفيدة.

### ترتيب الشريحة الأولى

1. عقد دفعة v2 وACK مفصل يضمن منع التكرار ولا يحجب الرسائل السليمة.
2. outbox Android بحالات وclaim ذري وdispatcher واحد؛ لا `REPLACE`.
3. heartbeat حقيقي، وآخر ACK/رسالة مؤكدة، مع تصنيف أخطاء قابل للتشخيص.
4. اختبارات Odoo للـHTTP/التحقق، ثم اختبارات Android للطابور والـretry.
5. شاشة الحالة المحترفة فوق الحالات المثبتة، ثم بقية الشاشات تدريجياً.

## القيود والافتراضات المفتوحة

- قناة توزيع APK والتوقيع المطابق للتطبيق المثبت يجب إثباتهما قبل ترقية الهاتف؛
  release غير موقّع لا يعد مرشح تثبيت.
- الاحتفاظ بالنصوص في الإنتاج ومدة diagnostics قرار مالك بيانات قبل Live؛ في QA
  تستخدم بيانات اختبار فقط عند اختبارات القياس.
- تطبيق Play Store يحتاج مراجعة أهلية صلاحيات SMS منفصلة إن اختيرت تلك القناة.

## قرار بديل معتمد من المالك — تطبيق v2 نظيف

أكّد المالك في 2026-09-27 أنه **يقبل فقد طابور v1 الحالي وإعادة الربط**. لذلك
لا تترحل قاعدة بيانات v1 أو أسرارها أو حالة طابورها إلى العميل الجديد. يبنى
`baseer-sms-v2` كتطبيق مستقل ذي معرّف حزمة منفصل، ويبقى مصدر v1 في الشجرة
للمراجعة فقط ولا يعدل أو يحذف ضمن هذا العمل. تبقى واجهات Odoo v1 متاحة للأجهزة
القديمة إلى أن يزيلها المالك؛ العميل الجديد لا يستدعي إلا عقد v2.

أعيدت G1 وG2 وG3 وG4 إلى **قيد المراجعة** بسبب تغير حدود الترحيل ومعرّف العميل
وعقده. المسار المباشر الجديد أقل مخاطرة: لا ترحيل بيانات حساسة، لا توافق محلي
صوري، وQR/ربط مستقلان؛ لكن لا يزال يمنع أي فقد لرسائل v2 بعد نجاح الربط.
